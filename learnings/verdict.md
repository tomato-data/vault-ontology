# Verdict — Phase 1~9를 마치며 내린 판단

이 프로젝트는 vault를 두 번 모델링했다. Phase 1~5는 SQLite 속성 그래프로,
Phase 6~9는 RDF/OWL 온톨로지로 구현했다. 두 모델을 나란히 구현해야
데이터 자체의 성질과 도구의 제약을 구분할 수 있다. 이제 처음에 남겨둔 질문에 답한다.

## 프로젝트가 열어둔 질문

| 질문 | 답 |
|---|---|
| 재귀 CTE로 부족한 순간이 있었나 | **없었다.** Phase 7에서 여섯 질의 전부 재귀 CTE로 0.5ms에 답했다. property path는 더 짧을 뿐, 못 하던 걸 하게 하지 않았다. |
| 추론이 SQLite로 못 얻던 사실을 만들었나 | **질적으로 새로운 사실은 없었다.** 이행 폐쇄(`builds_on+`)는 `learning_path`, 역링크(`linked_by`)는 `near`가 질의 시점에 이미 계산했다. 추론은 그 결과를 트리플로 저장했을 뿐이다. |
| 그 사실이 실제로 필요했나 | **아니다.** 질의 시점 계산으로 충분했다. 물질화에는 16.6초가 걸렸고 트리플 수는 약 3배가 됐지만, 새로 답할 수 있는 질의는 없었다. |
| v1(rdflib 상시 운용)으로 갈 가치가 있나 | **없다.** SQLite가 모든 질의에서 10~600배 빠르다. 추론은 16.6초가 들고, 늘어난 트리플의 절반(`rdfs:Resource`·`owl:Thing` 14,656개)은 실제 질의에 도움이 되지 않는다. 이 규모와 질의에서는 rdflib를 상시 운용할 이유가 없다. |
| v2(Rust + Oxigraph)의 근거는 성능인가 학습인가 | **학습이다.** 실측이 스키마 정본의 사전 가설을 지지했다. 성능이 목적이라면 SQLite를 바꿀 근거가 없다. Oxigraph를 선택한다면 추론·SHACL·표현력을 더 배우기 위해서다. |
| vault의 `type` 13가지 값에 계층이 있었나 | **있다. 다만 의미가 아니라 역할에 따른 계층이다.** Content/Imported/Structural 3역할은 "내가 쓴 내용만" 같은 질의에 쓰인다. 가이드가 제안한 6개 의미 묶음은 실제 질의로 이어지지 않았다. |
| 분리된 두 코퍼스(vault·800 TRPG)를 한 그래프로 합칠 가치가 있나 | **합치기는 쉽지만, 아직 병합이 필요한 질의는 없다.** RDF 그래프는 집합이므로 두 트리플 집합을 더하면 되고 IRI 네임스페이스가 충돌을 막는다. 두 코퍼스를 함께 조회해야 하는 질의가 생길 때 합친다. |

## 왜 0건이었나 — 도구와 목적이 어긋나 있었다

숫자만 보면 「추론이 별로였다」로 읽히지만, 원인은 더 구조적이다. **「온톨로지」라는
말이 최소 세 가지를 가리키는데, 우리는 그중 하나를 지어 다른 하나의 목적에 썼다.**

| | 무엇 | 목적 |
|---|---|---|
| ① 철학 | 존재론 | — |
| **② Gruber 의 정의** | *"formal specification of a shared conceptualization"* — 클래스·속성·공리 | **지식 표현과 공유** |
| **③ 업계 용법**(Palantir 식) | 데이터 + 로직 + 액션 + 권한을 묶은 **운영 계층**. 쓰기 가능 | **실시간 의사결정과 실행** |

**이 프로젝트가 지은 것은 ②다.** RDFS/OWL 공리를 `.ttl` 로 적고 추론기를 돌렸다.

**그런데 애초의 목적은 ③에 가까웠다.** 「AI 에이전트가 vault 를 탐색하게 한다」는 것은
지식 표현이 아니라 운영이다. 매일 쓰는 도구를 원한 것이지, 남과 공유할 형식 명세를
원한 게 아니었다.

```
②의 도구  →  ③의 목적
   형식 추론이 강하고 실시간 운영이 약한 물건으로
   실시간 운영을 풀려 했다
```

그래서 「유용한 새 사실 0건」은 우연이 아니다. ②가 잘하는 일(정적 추론·상호운용)을
이 사용 사례가 요구하지 않았을 뿐이다. **도구가 나쁜 게 아니라 자리가 아니었다.**

그렇다고 헛일도 아니다. **직접 지어봤기 때문에 그 어긋남을 말할 수 있게 됐다.**
안 지어봤으면 「온톨로지를 도입하면 좋아진다더라」에 계속 끌렸을 것이다. 이 판단서가
그 값이다.

> 개념 정리는 vault 의 `「온톨로지」라는 말의 세 갈래 — 철학·Gruber·업계`.

## 그렇다고 온톨로지에 가치가 없었던 것은 아니다

위 표는 **운용 가치**를 묻는다. 답은 "이 규모에선 SQLite로 충분". 그러나
이 프로젝트는 처음부터 **개념 이해가 목적**이었다(2부는 개념이 먼저, 구현은
확인 수단). 그 관점에서 온톨로지가 준 것:

1. **그래프는 집합이다.** `links_to`가 10,622 → 9,359로 줄고, `kinds`가
   bag/set 차이로 달라지고, `builds_on+`가 순환에서 저절로 멈춘 것은 모두
   집합이라는 성질에서 나온다.
2. **domain/range는 검증이 아니라 추론이다.** 지나치게 넓게 선언한 domain
   하나가 폴더 764개를 잘못된 Document로 분류했다. SQLite에서는 드러나지 않을
   종류의 실패였다.
3. **OWA와 CWA는 목적이 다르다.** OWL로는 "summary가 없으면 위반"이라고 검증할
   수 없다. Phase 4의 lint가 실질적으로 SHACL의 역할을 하고 있었음을 확인했다.
4. **표준 어휘와 상호운용.** dcterms를 재사용하고, 고유 관계는
   `subPropertyOf`로 표준 어휘에 연결했다.
   "온톨로지"와 "사설 스키마"의 차이가 여기 있다.

**SQLite로는 얻을 수 없던 유용한 사실은 0건이었지만, 개념적 교훈은 네 가지였다.**
운용 성과와 학습 성과를 구분해야 최종 판단이 흐려지지 않는다.

## 결정

- **v1 (rdflib 상시 운용): 하지 않는다.** SQLite 구현을 상시 운용한다. RDF
  산출(.vault.ttl)은 상호운용·백업 용도로만 남긴다.
- **v2 (Oxigraph): 보류하되 근거를 학습으로 한정한다.** 성능 때문이 아니라
  추론·SHACL·표현력을 더 배울 필요가 생길 때 진행한다.
- **스키마 계층: 3역할을 정본에 반영한다.** 6묶음은 문서로만 남긴다.

## 아직 측정하지 못한 항목

프로젝트가 스스로 정한 성공 기준은 실제 사용량이다.

- Phase 4 이후 2주간 CLI를 몇 번 썼나 — **미측정.** 이번에는 학습용 재구축에
  집중해 2주 실사용 시험을 진행하지 않았다. v1을 진행하지 않기로 한 만큼, 이 기준은 v2를
  진지하게 고려할 때 다시 꺼낸다.
- 그중 Dataview·grep으로 못 했을 질의가 몇 건인가 — 같은 이유로 미측정.

**0건이면 운영 도구를 하나 더 만든 것에 그친다.** 이 프로젝트가 남긴 핵심 성과는
새 운영 도구가 아니라 온톨로지에 대한 구체적인 이해다. 그것이 애초의 목적이었다.
