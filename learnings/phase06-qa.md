# Phase 6: Q&A

RDF 로 다시 모델링하면서 나온 질문과 답.

## 설계

### Q: 왜 `resolve` 를 함수로 받나? Phase 3 에서 인자를 더한 것과 반대 아닌가

```python
def edge_triples(relative, text, resolve, folder_note=None):
```

`resolve(target) -> 경로 | None` 이라는 **계약만** 받는다. 그래서 `rdf.py` 는
`scan.py` 를 아예 import 하지 않는다.

```
vault/graph.py        vault/rdf.py
  frontmatter           frontmatter
  links                 links
  scan                    ← 없다
```

**우리 이력이 그 값어치를 말한다.** `scan.py` 의 공개 시그니처가 두 번 바뀌었다.

| 커밋 | 무엇 | 같이 고친 파일 |
|---|---|---|
| `f1257d2` | `resolve_link` 에 `source` 추가 | 3개 |
| `f63c5f0` | `scan_vault` 반환값 2 → 3 | **6개** |

`rdf.py` 는 둘 다 안 걸린다. 계약이 안 바뀌었으니까.

### Q: 그럼 Phase 3 에서 인자를 더한 건 뭐였나 — 반대 방향 아닌가

**같은 원칙이다. 「함수는 자기 일에 필요한 것만 받는다.」**

| | 무엇을 했나 | 왜 |
|---|---|---|
| Phase 3 Step 5 | 인자를 **더했다** (`source`) | 링크가 어디서 왔는지 모르면 **제 일을 못 한다** |
| Phase 6 Step 3 | 의존을 **덜었다** (`resolve`) | 해석 방법은 **제 일과 무관하다** |

```
Phase 3   부족했다   → 채웠다     링크 126개가 제자리를 찾았다
Phase 6   넘칠 뻔했다 → 안 받았다   scan.py 를 모른다
```

두 방향 다 **필요한 것에 정확히 맞추는 일**이다.

### Q: 이걸 뭐라고 부르나

의존성 역전이지만, 이름보다 유용한 개념은 **이음매(seam)** 다 —
**코드를 고치지 않고 동작을 바꿀 수 있는 자리.**

Phase 6 에서 이음매를 둘 만들었다.

```python
doc_iri(relative)                    Step 1 — 정체성의 이음매
edge_triples(..., resolve, ...)      Step 3 — 해석의 이음매
```

`doc_iri` 는 IRI 정책이 바뀔 자리를 **하나로 모았고**, `resolve` 는 해석 방식이
바뀔 자리를 **바깥으로 뺐다.** 같은 발상의 두 적용이다.

### Q: 테스트가 얼마나 달라지나

```python
RESOLVE = {"CIDR": "200 Dev/CIDR.md"}.get      # 한 줄
```

직접 부르는 구조였다면 파일을 만들고 `scan_vault` 를 돌려야 한다. **엣지 모델링을
시험하려는데 파일시스템이 끼어든다.** 느려지고, 스캔이 깨지면 모델링 테스트도 같이
빨개져 **어디가 틀렸는지 안 보인다.**

### Q: 언제 이렇게 빼나 — 공짜는 아닐 텐데

**비용**

- 조립하는 자리가 양쪽을 알아야 한다
- import 면 정의로 점프하는데 인자면 호출부를 뒤져야 한다
- 남용하면 함수가 무슨 일을 하는지 안 보인다

**판정** — 셋 중 둘 이상이면 뺀다.

1. 진짜 갈아끼울 수 있나 — 딕셔너리 · 캐시 · 다른 vault ✅
2. 테스트에서 만들기 어려운가 — 파일시스템이 필요하다 ✅
3. 모양이 바뀔 것 같은가 — **이미 두 번 바뀌었다** ✅

셋 다 맞아서 뺐다. `fm_get` 이나 `link_target` 은 하나도 안 맞아서 그냥 import 한다.

## 모델링

### Q: `part_of` 가 왜 형제 파일을 가리키나

Step 3 데모에서 나온 질문. `200 Dev/Network/CIDR.md` 의 `part_of` 가
`200 Dev/Network/Network.md` 를 가리킨다. **폴더가 아니라 같은 폴더의 다른 파일이다.**

실측이 지적을 뒷받침한다 (2026-08-24).

```
part_of 1,020 건 중
   968  형제를 가리킨다   (같은 폴더 안)
    52  삼촌을 가리킨다   (한 단계 위 폴더 — 「폴더 옆」 관례)
```

결정적인 증거.

```
600 .../독서/도해 연금술/도해 연금술.md
   ← 104개 문서가 이걸 part_of 로 가리킨다
   그런데 이 노트 자신도 도해 연금술/ 안에 있다
```

**「A에 속한다」고 하면서 A가 그 안에 있다.** 진짜 포함 관계라면 자기 자신에도
속해야 하고, 자기 루프를 막느라 걸러냈을 뿐이다.

### Q: 왜 그렇게 됐나

**SQLite 가 강요한 타협이다.** Phase 5 의 노드는 파일뿐이다.

```sql
CREATE TABLE node (path TEXT PRIMARY KEY, ...)
```

`200 Dev/Network/` 는 디렉토리라 노드가 되려면 **가짜 행**이 필요했다.
그래서 **폴더 노트를 폴더의 대역으로 썼다.** 답안지도 같은 선택이었다.

`Network.md` 가 두 역할을 겹쳐 맡는다.

| 역할 | |
|---|---|
| 폴더 안의 문서 하나 | `CIDR.md` 와 나란히 있다 |
| 폴더의 대표 | Obsidian 에서 폴더를 누르면 열린다 |

**모델은 두 번째만 담았고 첫 번째를 무시했다.**

### Q: 그래서 계층이 생기나

안 생긴다.

```
part_of 사슬 깊이:  1 → 968건 · 2 → 52건 · 최대 2
경로 깊이는 최대 6단
```

`Network.md` 의 `part_of` 는 `200 Dev/Network.md` 를 찾는데 그런 파일이 없으니
거기서 끊긴다. **폴더 노트가 있는 폴더끼리만 이어져서 대부분 한 칸이다.**

지금 `part_of` 는 **계층이 아니라 「같은 폴더 표시」** 다.

### 결정 (2026-08-24) — 폴더 IRI 를 만든다

**RDF 에서는 IRI 가 공짜다.** 파일이 없어도 이름을 줄 수 있다.

```turtle
doc:200%20Dev/Network/CIDR      v:part_of  folder:200%20Dev/Network .
folder:200%20Dev/Network        v:part_of  folder:200%20Dev .
folder:200%20Dev/Network        v:hub      doc:200%20Dev/Network/Network .
doc:200%20Dev/Network/Network   v:part_of  folder:200%20Dev/Network .
```

마지막 줄이 요점이다. **폴더 노트도 그 폴더 안의 문서다.** 자기 루프가 아니라
서로 다른 리소스를 가리키니 이제 적을 수 있다. 겹쳤던 두 역할이 갈렸다.

**얻는 것 셋**

1. `part_of` 가 **참이 된다**
2. **계층이 6단까지 이어진다.** Phase 7 의 `v:part_of+` 로 「이 문서의 모든 상위
   구역」을 한 줄에 묻는다 — **지금은 불가능한 질의다**
3. 겹친 두 역할이 갈린다

**대가** — 폴더는 문서가 아니므로 새 종류의 리소스가 생긴다 (736개).
`?d a v:Document` 에 안 섞이게 해야 하고, Phase 5 와 트리플 수가 달라지며,
Phase 8 에서 `v:Folder` 클래스를 어떻게 놓을지 결정거리가 하나 는다.

**마지막이 오히려 이 Phase 의 목적에 맞는다** — 「속성 그래프에서는 못 하던 걸
RDF 에서는 한다」의 두 번째 실물이고, 네임스페이스 예시와 나란히 놓인다.

### Q: `v:hub` 도 넣을까 — 넣는다

근거는 「새 기능」이 아니라 **「잃지 않기」** 다. 지금 `part_of` 의 **목표 자체가**
폴더 노트 정보를 담고 있다. 목표를 폴더 IRI 로 바꾸면 **아무것도 안 더할 때 그
정보가 사라진다.** 정본의 「필요한 질의가 없으면 안 넣는다」는 없던 걸 추가할 때
거는 관문이지, 담고 있던 사실을 버리라는 뜻이 아니다.

**`type: hub` 로 대신할 수 없다** (2026-08-24 실측).

```
폴더 노트 158개의 type:  hub 131 · source-note 12 · project-doc 11 · 기타 4
vault 전체 type=hub 207 · 그중 폴더 노트 131
```

두 방향으로 어긋난다.

- **`hub` 인데 폴더 노트가 아닌 게 76개** — `type: hub` 는 「링크를 모으는 문서」지
  「어느 폴더의 대표」가 아니다
- **폴더 노트인데 `hub` 가 아닌 게 27개** — `도해 연금술.md` 는 `source-note` 인데
  104개 문서의 대표다. 책 원전이면서 그 폴더의 얼굴이다

**`type: hub` 는 「이 문서가 무엇인가」, `v:hub` 는 「어느 폴더의 것인가」다.**
하나로 못 줄인다.

방향은 폴더를 주어로 둔다 — **폴더당 하나**라는 성질이 주어 쪽에 있는 게 자연스럽다.

**이름은 Phase 8 에서 다시 본다.** 표준 어휘 재사용이 그 Phase 의 주제고,
`foaf:primaryTopic`(「이 문서가 무엇에 관한 것인가」)이 후보다.
