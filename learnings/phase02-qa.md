## 재볼 것

### 이름에 `#` 나 `^` 가 든 문서가 vault 에 있는가

`link_target` 은 `\|` → `|` → `#` → `^` 순으로 첫 구분자 앞까지만 남긴다.
자르는 게 맞는 이유는 편의가 아니라 **문법이 그렇게 정해져 있어서**다.

- `|` 는 Obsidian 이 파일명에 금지한다
- `#` · `^` 는 파일명에 들어갈 수 있지만, 위키링크 안에서는 구분자로 먼저
  읽힌다. 이름에 `#` 가 든 문서는 **위키링크로 가리킬 방법 자체가 없다**

그래서 파서는 안 틀렸다. 대신 그런 문서가 있으면 **구조적으로 고아가 된다.**
링크를 받을 길이 없다.

Step 4 실측에서 센다. 0건이면 [[phase01-qa]] 의 「깨지는 지점」 A 칸
(재보고 안 고친 것)으로 내려간다.

### `strip_code` 가 지금 안 다루는 것

GREEN 은 최소 구현이다. 셋을 의도적으로 뺐다.

| 입력 | 지금 어떻게 되나 |
|---|---|
| ` ``` ` 로 연 블록을 `~~~` 로 닫음 | `in_fence` 토글이라 서로 닫아준다. 마크다운은 **같은 종류로만** 닫힌다 |
| 백틱 4개 이상 펜스 | ` ```` ` 안에 ` ``` ` 를 넣는 문법. 지금은 그냥 토글 |
| 이중 백틱 인라인 (`` `` ``) | `` `[^`]*` `` 가 빈 스팬으로 오인한다 |

셋 다 **틀리게 세는 쪽으로 깨진다.** 크래시가 안 난다. 진짜 링크를 코드로
착각해 지우거나(엣지 소실), 코드를 산문으로 착각해 가짜 엣지를 만든다.

Step 4 실측에서 vault 에 실제로 있는지 센다. 0건이면
[[phase01-qa]] 의 A 칸(재보고 안 고친 것)으로 내려간다.

### `fm_list` 와 `link_target` 이 위키링크를 다르게 읽는다

Phase 1 Step 3 REFACTOR 에서 「위키링크 벗기기를 함수로 뽑을까」를 미뤘다.
근거는 「Phase 2 의 `link_target` 이 나오면 모양이 보인다」였다. 이제 보인다.

```
fm_list      -> ['CIDR|what it is', 'Subnet mask#Notation']
link_target  -> ['CIDR', 'Subnet mask']
```

`fm_list` 는 `[[ ]]` 만 벗기고 구분자를 안 자른다. 그래서 frontmatter 가

```yaml
builds_on:
  - "[[CIDR|what it is]]"
```

이렇게 적혀 있으면 엣지의 대상이 `CIDR|what it is` 가 된다. 그런 이름의
문서는 없으니 **멀쩡한 관계가 미해결 링크로 잡힌다.** 크래시는 안 나고
숫자만 틀리는, Phase 2 내내 본 그 모양이다.

**지금 안 고친다.** 동작 변경이라 REFACTOR 가 아니고, 그런 문서가 실제로
있는지 모른다. `vault new` 가 `builds_on` 에 별칭을 넣는지에 달렸다.

Step 4 실측에서 센다 — `builds_on` 항목 393개 중 `|` · `#` · `^` 를 품은 것.
0건이면 안 고친다. 있으면 `fm_list` 결과를 `link_target` 에 통과시킨다.

## 스키마

### Q: 링크 관계는 그냥 위키링크로 두는 철학인가? `builds_on` 을 더 채워야 하나?

**둘 다 맞는데 층위가 다르다.** 정본을 읽고 정리했다.

위키링크는 정본의 「그래프 빌더가 **유도하는** 관계」 칸에 있다. 이름을 안 주기로
설계된 것이지 아직 못 준 게 아니다. 근거는 이 원칙이다.

> 파생 가능한 사실은 frontmatter 에 쓰지 않는다. frontmatter 에는
> **어디에도 없는 사실만** 적는다.

| | 담는 사실 | 어디서 나오나 |
|---|---|---|
| 위키링크 | "A 가 B 를 언급했다" | 본문에 이미 있다 |
| `builds_on` | "B 를 모르면 A 를 이해할 수 없다" | 어디에도 없다. 사람의 판단 |

**여기까지는 맞았다. 그 다음이 틀렸다.**

처음에 "271/911 은 설계 의도 안이다" 라고 했는데 근거가 없었다.
「수집은 원본의 10%」는 **문서당 필드 수**를 제약하는 원칙이다
(정본 표현: "필드 상한 6개, 대부분 파일은 2~3개만 갖는다").
「몇 개의 문서가 `builds_on` 을 갖느냐」와는 다른 얘기다. **두 희소성을 섞었다.**

이행 폐쇄 폭발 논증도 같은 실수다. 폭발을 좌우하는 건 문서당 분기 수(≤3)와
사슬 깊이지 커버리지가 아니다. 900개가 각각 2개씩 가져도 다룰 만하다.

정본이 `builds_on` 을 "선택" 이라 한 건 **전제가 없으면 억지로 만들지 말라**는
뜻이지 **있어도 비워두라**는 뜻이 아니다. 640개가 빈 건 설계가 아니라
마이그레이션이 거기까지 간 것이다.

### Q: 그러면 많은 후보 중 뭘 고르나

vault 는 A→B 로 파생된 깔끔한 트리가 아니다. 문서 하나에 관련 문서가 수십 개다.
그래서 진짜 문제는 「더 넣지 마라」가 아니라 **「뭘 고르냐」** 였고, 그 자리에
규칙이 없었다.

2026-08-18 에 정본 v1.8 로 확정했다 (통과 조건 3 + 고르는 규칙 3 + 금지 4).
전문은 vault 의 `Vault 온톨로지 — 스키마 정본` 「`builds_on` — 무엇을 넣나」.

가장 중요한 건 **직접 부모만 적는다**(이행 축약)다. 후보가 열 개여도 대부분은
다른 후보를 거쳐 도달된다. 한 단계 위만 남기면 보통 1~3개로 줄어든다.
**상한 3은 억지 제약이 아니라 이 규칙의 결과다.**

그 다음이 **이행 건전성**이다. `builds_on` 은 이행적으로 선언되므로
간선 하나를 넣는 순간 그 위 전부와의 관계를 함께 주장한다. 위키링크에는
없는 부담이고, Phase 8~9 에서 이게 실제로 트리플이 된다.

### 미뤄둔 판단 셋이 닫혔다

| 질문 | 결과 | 판단 |
|---|---:|---|
| 이름에 `#` · `^` 가 든 문서 | 0 | 안 고친다 |
| `builds_on` 안의 구분자 | **1** | 정본에 「별칭 금지」 명문화. `fm_list` 는 안 고친다 |
| ` ``` ` 와 `~~~` 혼용 | 10 파일 · **파싱 차이 0** | 안 고친다 |

**`fm_list` 를 안 고치는 이유**가 이번의 소득이다. 답안지가 이미 답을 갖고 있었다.

```python
if not resolve_link(link_target(t), index, paths):
```

`link_target` 을 `fm_list` **안**이 아니라 **호출부**에서 적용한다.
`fm_list` 는 `tags:` 도 읽는다. 태그에 `link_target` 을 씌우면 `Stack/C#` 이
`Stack/C` 로 잘린다. 지금 vault 에 그런 태그가 0건이라 당장은 안 깨지지만,
`fm_list` 는 「YAML 리스트 블록을 읽는 함수」지 「위키링크를 읽는 함수」가 아니다.

Phase 1 Step 3 REFACTOR 에서 미뤄둔 질문의 답이다. **미룬 게 옳았다** —
그때는 `tags:` 충돌이 안 보였다.

### 배운 것 — 「있는가」가 아니라 「결과가 달라지는가」

` ``` ` 와 `~~~` 가 같이 있는 파일이 10개 있었다. 존재만 보면 "고쳐야 하나" 싶다.
그래서 종류 맞춤 버전을 따로 구현해 **링크 수를 비교**했다.

```
차이 나는 파일 0
```

존재하는데 영향이 없다. **존재 여부가 아니라 산출물 차이를 재야 한다.**
