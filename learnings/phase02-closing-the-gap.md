# Phase 2 회고: 간극을 메우는 일

위키링크 파서 세 함수(`link_target` · `strip_code` · `iter_links`).
테스트 42개. 실측에서 링크 10,731개를 셌고 답안지 10,702와 맞았다.

**그런데 이 Phase 의 실제 산출물은 파서가 아니라 스키마 정본 v1.8 이었다.**

## 이 프로젝트가 무엇인가

`builds_on` 개수를 두고 의견이 갈렸다. Claude 는 "271/911 은 설계 의도 안" 이라
주장했고 근거로 「수집은 원본의 10%」를 들었다. **틀린 논증이었다.**
그 원칙은 문서당 필드 수를 제약하지 커버리지를 정하지 않는다. 두 종류의 희소성을
섞은 것이다.

사용자가 밀어붙였고, 그 이유가 이 프로젝트의 정의였다.

> 애초에 이 프로젝트는 '저만의 vault' 를 강화하는 작업입니다. 그에 있어서 저의
> 이해와 상충되는 부분이 보이는 것 같아서 지적한 것 뿐입니다. 즉, 제가 상정하고
> 원하는 방향성과 claude code agent 가 build 한 구조의 간극을 메워가는 작업으로
> 이해하고 작업하고 있습니다.

여기서 답안지의 지위가 정해진다. `reference/` 와 스키마 정본은 **권위가 아니라
검토 대상**이다. Claude 가 만든 것이고, 동작하지만 사용자의 의도와 어긋난 자리가
남아 있다. "정본에 그렇게 적혀 있다" 는 논증의 끝이 아니라 시작이다.

실제로 정본에는 `builds_on` 의 **개수만 있고 선택 기준이 없었다.** 그 빈칸이
"640개가 왜 비었나" 를 답할 수 없게 만들었다. 규칙을 정해 v1.8 로 넣었다 —
통과 조건 3(막힘·비대칭·이행 건전성), 고르는 규칙 3, 금지 4.

**코드가 아니라 vault 자체가 개선된 첫 사례다.**

## 정규식이 아직 생소하다

Claude 가 Phase 2 내내 「같은 규칙이 또 나왔다」고 강조했다. `\|` 를 `|` 보다
먼저, ` ``` ` 를 `` ` `` 보다 먼저 — 「포함 관계가 있으면 긴 것부터」라는 하나의
규칙이라고.

> regular expression(정규표현식) 의 문법에 익숙하지 않은 것도 있고, 생소해서
> 이것이 계속 같은 것을 하는 작업이라는 느낌을 받지는 못했습니다.

**바닥이 생소하면 그 위의 패턴도 안 보인다.** 추상에 이름을 붙이는 건 이미 조각을
읽을 수 있는 사람에게 먹히는 방법이다. 순서가 거꾸로였다.

Phase 1~5 는 전부 손으로 짠 파서라 정규식이 계속 나온다. 그래서
[[regex-reference]] 를 따로 만들어 누적하기로 했다. 조각마다 무엇을 하는지
먼저 읽고, 패턴 이름은 그 다음이다.

## 기술적으로 남은 것

Phase 1 의 함정은 티가 났다. `\s` 가 개행을 먹으면 값이 이상해진다.
**Phase 2 의 함정은 크래시를 안 낸다.** 숫자만 조용히 틀린다.

두 함정이 만든 오차가 357개였다. 총수 10,731 대비 3.3% 라 "그 정도야" 싶지만
구역별로 보면 다르다.

- 표 안의 `\|` — 101개 링크. 몰린 곳이 `500 Mind Compiler` 다.
  **정본이 「45.7% 고아 오측정」의 원인으로 지목한 바로 그 구역**이다
- 코드 예제 — 256개 가짜 엣지. 전부 스킬 정의·템플릿·가이드라인 문서다.
  "이렇게 쓰세요" 라며 보여준 예시가 진짜 관계로 둔갑할 뻔했다

`phase02.md` 가이드는 `000 Index` 를 위험 지대로 지목했는데 실측해보니 2개뿐이었다.
**가이드의 예상보다 실측이 정확했다.** Phase 1 의 교훈이 그대로 반복됐다.
