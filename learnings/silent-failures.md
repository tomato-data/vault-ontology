# 조용히 틀리는 실패 — 의심하는 법

1부에서 다섯 번 나왔다. **크래시가 없고 숫자도 그럴듯한데 틀린** 종류다.
「감이 안 잡힌다」가 정상이다 — 이름을 붙인다고 감이 생기지 않는다.
**무엇을 언제 의심하는지**를 적어둔다.

## 다섯 사례와, 무엇이 그걸 잡았나

| Phase | 무엇이 틀렸나 | 어떻게 잡혔나 |
|---|---|---|
| 1 | `\s` 가 개행을 먹어 빈 `summary:` 가 다음 줄을 읽는다 | **경계 테스트** — 값이 비어 있는 경우를 따로 썼다 |
| 2 | 표 안의 `\|` 하나가 링크 101개를 깨진 것으로 만든다 | **구역별로 나눠 셌다** — 총수로는 3.3% 라 안 보였다 |
| 3 | NFD/NFC 가 링크 5,341개(21.9%)를 깨뜨린다 | **0 을 의심했다** — 테스트가 통과했는데 진짜 검증하는지 되물었다 |
| 4 | 거짓 경보 582건이 진짜 위반 318건을 묻는다 | **목록을 눈으로 봤다** — 상위 20개가 전부 `.png` 였다 |
| 5 | `NOT IN` 에 NULL 하나가 고아 목록을 통째로 비운다 | **미리 알고 막았다** — 이건 밟지 않았다 |
| 부록 | `800 TRPG` 분리 영향 예측이 **8배 빗나갔다** (32회 → 260회) | 옮기고 나서 다시 셌다 — **예측을 검산할 테스트가 없었다** |

## 의심하는 법 여섯

### 1. 숫자 하나로 판정하지 않는다. 나눠서 센다

Phase 2 에서 오차가 총수의 3.3% 였다. "그 정도야" 싶은 크기다.
**구역별로 보니 `500 Mind Compiler` 한 문서에서 14개씩 몰려 있었다.**

> 총수가 맞는 것과 각 구역이 맞는 것은 다른 얘기다.

나누는 축: 디렉토리 · 파일 유형 · 값의 종류 · 시간.

### 2. `0` 과 `100%` 를 의심한다

둘 다 두 가지 뜻이다.

```
0        「없다」   또는  「안 셌다」
100%     「완벽」   또는  「검사가 안 걸렸다」
```

Phase 3 에서 `frontmatter 엣지 미해결 0` 이 나왔는데, 오타 난 키를 읽고 있었다.
**「없다」가 아니라 「한 번도 올라간 적 없다」였다.**

> 0 이 나오면 그 지표가 **한 번이라도 올라간 적이 있는지** 확인한다.

Phase 1 의 `summary 80자 초과 0건` 은 반대로 진짜였다. **분포를 내서 갈랐다** —
`max` 가 정확히 80 이면 누가 80 에서 막은 것이다.

### 3. 실패의 **모양**을 읽는다

| 모양 | 뜻 |
|---|---|
| 전부 비어 있다 (`[]` · `{}`) | **채우는 코드가 안 돌았다.** 필터·파싱이 아니다 |
| 전부 같은 예외 | 한 함수 안이다 |
| 하나만 다르다 | 그 입력의 특성이다 |
| 결과가 입력보다 크다 | 어딘가에서 두 번 센다 |

Phase 3 에서 7개 테스트가 **전부 빈 값**이었다. `for` 루프가 거르기만 하고
`append` 를 안 했다. 「필터가 과한가」를 의심할 필요가 없었다 — 균일하게 비어 있었다.

### 4. 숫자 말고 **목록**을 본다

Phase 4 에서 「깨진 링크 900건」은 그럴듯했다. 상위 20개를 찍어보니
`가상화의 종류.jpg` · `디플로이먼트-레플리카셋-파드-관계.webp` 였다.

> 집계를 낼 때는 항상 **상위 N개 원본**을 같이 찍는다. 한 줄이면 된다.

### 5. NULL · 빈 문자열 · 부재가 지나는 자리를 따로 센다

세 값은 코드에서 조용히 갈린다.

```python
if not summary:          # None · "" · 둘 다 걸린다
if summary is None:      # "" 는 안 걸린다
```

```sql
x NOT IN (…, NULL)       -- FALSE 가 아니라 NULL. 결과가 통째로 빈다
count(column)            -- NULL 을 안 센다
```

**우리 설계가 `dst` 에 NULL 을 허용하기로 했으므로 이 자리를 반드시 밟는다.**

### 6. 「안 만들어야 하는 것」을 테스트한다

검출기·필터는 **과하게 잡는 쪽으로** 틀린다. 그래서 테스트가 두 벌 필요하다.

```
잡아야 하는 것    3개
잡으면 안 되는 것  8개     ← Phase 4 태그 검출기
```

비율이 뒤집힌 게 정상이다. **어려운 건 검출이 아니라 자제다.**

### 7. 일회용 스크립트가 본 코드보다 위험하다

2026-08-23 `800 TRPG` 분리 전에 「끊길 링크」를 예측했다. **32회 / 17종.**
옮기고 재보니 **260회 / 175종.** 8배다.

원인은 Phase 3 이 이미 잡아둔 NFD/NFC 함정이었다. 예측 스크립트가 `os.walk` 결과로
인덱스를 만들고 링크 문자열로 조회했는데 **정규화를 안 걸었다.** 대부분이 「해결 안 됨」
으로 빠졌고, 그래서 「800 을 가리킨다」로 세어지지 않았다.

```
vault/scan.py     nfc() 를 건다        <- 테스트 162개가 지킨다
일회용 분석 스크립트  안 걸었다            <- 아무도 안 지킨다
```

**본 코드에는 교훈이 반영돼 있는데 곁다리 스크립트에는 안 걸렸다.** 그리고 곁다리
쪽이 더 위험하다 — **검산할 테스트가 없어서 틀려도 안 드러난다.**

같은 실수를 `grep -c` 로 아카이브 존재 여부를 볼 때 또 했다. NFC 패턴으로 NFD 파일명을
찾으니 멀쩡히 있는 파일이 0 으로 나왔다. **여기서도 0 이 신호였다.**

> 분석 스크립트를 쓸 때는 **본 코드의 함수를 import 한다.** 같은 일을 다시 짜지 않는다.
> `scan_vault` · `iter_links` · `resolve_link` 이 이미 함정을 알고 있다.

## 언제 이 목록을 꺼내나

- **집계를 처음 냈을 때.** 숫자가 그럴듯해 보일 때가 가장 위험하다
- **테스트가 초록인데 실제 데이터로 처음 돌릴 때**
- **0 이나 100% 를 봤을 때**
- **문서에 적힌 숫자와 다를 때** — 어느 쪽이 낡았는지부터 본다

**초록은 「구현이 테스트와 맞는다」만 말한다.** 「테스트가 옳다」는 말하지 않는다.
그건 실제 데이터만 안다.
