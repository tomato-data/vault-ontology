# Phase 3: Q&A

vault 스캔과 링크 해석을 짜면서 나온 질문과 답.

## 온톨로지

### Q: RDF 가 정확히 뭔가

**모든 사실을 「주어 · 술어 · 목적어」 셋으로만 적는 데이터 모델.** 그 셋을
**트리플**이라 부르고, 그래프는 트리플을 모아둔 것이다. 그게 다다.

지금 만드는 SQLite 그래프는 사실의 **종류마다 자리가 다르다.**

```
type       -> node 테이블의 컬럼
builds_on  -> edge 테이블의 행
태그        -> tag 테이블의 행
```

RDF 는 자리가 하나뿐이다.

```
CIDR  type       Concept
CIDR  summary    "서브넷 마스크로 호스트 수를 세는 법"
CIDR  builds_on  Subnet mask
CIDR  tagged     Stack/Python
```

**이득 셋**

1. 스키마를 안 고치고 새 사실을 담는다. 술어 하나를 새로 쓰면 끝. `ALTER TABLE` 이 없다
2. **합치는 데 설계가 필요 없다.** 두 그래프를 합치는 건 트리플 집합의 합집합이다.
   JOIN 설계가 없다. RDF 가 웹 규모 데이터 통합을 위해 만들어져서 그렇다
3. **스키마도 트리플로 적는다.** 이게 속성 그래프와의 결정적 차이다

셋째가 핵심이다.

```
builds_on  is-a  TransitiveProperty
```

「`builds_on` 은 이행적이다」라는 **규칙 자체가 데이터**다. 코드 안에 숨어 있지
않다. 그래서 **추론기**가 규칙을 읽고 새 트리플을 만들 수 있다.

```
CIDR builds_on Subnet mask
Subnet mask builds_on Network layer
builds_on is-a TransitiveProperty
                    ↓
CIDR builds_on Network layer      <- 아무도 안 적었는데 참이다
```

**여기가 「지식 그래프」와 「온톨로지」가 갈리는 자리다.** Phase 5 까지는 질의할
때마다 재귀 CTE 로 계산한다. Phase 9 에서는 추론기가 아예 트리플로 만들어 넣는다.

**대가** — 타입 안전이 없다(뭐든 어디든 들어간다), SPARQL 을 배워야 한다,
저장 효율이 나쁘다.

### Q: IRI 는 뭔가

**주소 모양으로 생긴 전역 이름.** Internationalized Resource Identifier —
유니코드를 쓸 수 있게 확장한 URI 다. RDF 는 주어와 술어를 IRI 로 적으라고 요구한다.

왜 필요한지는 Phase 3 Step 1 이 그대로 보여준다.

```python
build(tmp_path, "000 Index/Hub.md", "500 Mind/Hub.md")
```

이름 하나가 파일 둘을 가리킨다. 그래서 인덱스 값을 리스트로 만들었다. 그런데
트리플을 적으려면 주어가 하나여야 한다.

```
Hub  type  Concept      <- 어느 Hub 인가?
```

IRI 가 이 모호함을 없앤다.

```
https://tomato.vault/doc/000%20Index/Hub
https://tomato.vault/doc/500%20Mind/Hub
```

**오해하기 쉬운 점 — 접속되는 주소가 아니다.** 브라우저에 넣어 뭔가 열릴 필요가
없다. 도메인을 소유하지 않아도 된다.

그러면 왜 URL 모양인가. **전역 유일성을 값싸게 얻으려고.** 도메인은 이미 세상에
하나씩만 있다. 내 `tomato.vault` 아래 것은 남의 `example.org` 아래 것과 절대
안 부딪힌다. **소유권 체계를 빌려 이름 충돌을 없앴다.**

`w3id.org` · `purl.org` 같은 영구 식별자 서비스가 왜 있는지도 여기서 나온다.

### Q: 네임스페이스가 800 TRPG 문제를 푼다

Phase 5 에서 `800 TRPG` 를 통째로 버린다. `type:` 을 게임 아이템 분류로 써서
축이 깨지기 때문이다. RDF 에서는 안 버려도 된다.

```
v:type      = https://tomato.vault/schema/type    문서 유형
trpg:type   = https://tomato.vault/trpg/type      아이템 분류
```

**같은 이름, 다른 네임스페이스, 충돌 없음.** SQLite 컬럼으로는 불가능했다.
컬럼 이름은 테이블 안에서 하나뿐이다.

되찾을지는 Phase 6 의 판단이다. 「필요한 질의가 없으면 안 넣는다」가 정본의 원칙.

### Q: 리터럴과 리소스의 차이

```
CIDR  summary    "서브넷 마스크로 호스트 수를 세는 법"   <- 리터럴
CIDR  builds_on  <doc/Subnet-mask>                    <- 리소스
```

**리터럴은 막다른 길이다.** 문자열·숫자·날짜고, 그것을 주어로 삼는 문장을 못 쓴다.
**리소스는 이어진다.** 다른 트리플의 주어가 될 수 있다.

판단 기준은 하나 — **"이것에 대해 나중에 더 말할 일이 있는가."**

태그가 애매하다. 리소스로 하면 **태그끼리 관계를 맺을 수 있다** —
`Stack/Python` 이 `Stack` 의 하위라는 사실을. Phase 8 의 SKOS `skos:broader` 가
그 자리다.

### 그래서 Phase 3 이 Phase 6 의 입력이다

Phase 6 에서 진짜 어려운 건 **"무엇을 문서의 IRI 로 삼을 것인가"** 다.

| 후보 | 문제 |
|---|---|
| 파일 경로 | 문서를 옮기면 **다른 것**이 된다. vault 는 계속 재배치된다 |
| 파일 이름 | **동명이인.** `Hub` 가 여럿 |
| 새 UUID | 안정적이지만 frontmatter 필드가 는다. 「필드 상한 6」과 충돌 |
| 내용 해시 | 문서를 고치면 다른 것이 된다. 최악 |

정답이 없다. **지금 NFC/NFD · 동명이인 · 대소문자를 손으로 겪어봐야** "이름을
식별자로 쓰면 안 된다" 가 실감이 나고, 그때 근거를 갖고 고를 수 있다.

## 실측 — NFC 정규화가 얼마나 중요한가 (2026-08-18)

Step 1 GREEN 직후, `test_a_name_is_indexed_in_nfc` 가 **진짜로 검증하는지**
의심스러워서 확인했다. APFS 는 정규화를 무시하고 비교하므로, 파일시스템이 NFC 를
돌려주면 우리 코드가 아무 일 안 해도 통과할 수 있었다.

### 1. 파일시스템은 준 대로 돌려준다

```
NFD 이름으로 만들어 rglob 로 읽으면  ->  NFD
NFC 이름으로 만들어 rglob 로 읽으면  ->  NFC
```

APFS 는 **넣은 그대로 보관하고 비교만 정규화 무시로 한다.** 그러니 테스트는
가짜 초록이 아니었다. `normalize` 를 빼면 실제로 실패한다.

### 2. 실제 vault 가 섞여 있다

```
NFC   3,871
NFD   1,091      <- 한글 파일명의 22%
ascii 1,503
```

한 vault 안에서 왜 갈리나. **만들어진 경로가 달라서다.** HFS+ 시절에 생긴 것,
iCloud 를 거친 것, 다른 도구가 만든 것이 섞였다. 사람은 구분할 방법이 없다.
눈에 똑같이 보인다.

NFD 목록에 이런 게 있었다.

```
100 Private Log/199 Private Kernel/Vault 온톨로지 — 스키마 정본.md
```

**스키마 정본 자신이 NFD 다.**

### 3. 정규화가 링크 5,341개를 살린다

```
본문 링크            24,371
정규화 없이 해석됨    17,116
NFC 정규화 후 해석됨  22,457
정규화가 살린 링크     5,341  (21.9%)
```

안 했으면 링크의 22% 가 깨진 것으로 잡혔다. Phase 2 의 `\|` 사고가 101개였으니
**50배**다. 가이드의 「실패하면 대량으로 깨진다」는 과장이 아니었다.

이건 **한국어 vault 라서** 생기는 문제다. 영어권 도구를 그대로 쓰면 안 되는 자리고,
답안지도 여기서 `nfc()` 헬퍼를 따로 뒀다.

### 「이름은 식별자가 아니다」의 증거가 쌓인다

| 증거 | 규모 |
|---|---|
| 같은 이름, 다른 파일 | `Hub.md` 등 — Step 3 에서 센다 |
| 같은 글자, 다른 코드포인트 | **파일 1,091개 · 링크 5,341개** |
| 대소문자 | Step 3 에서 센다 |

Phase 6 에서 IRI 를 고를 때 이 표가 근거가 된다 — [[phase03-qa]] 의 「RDF / IRI」 절.

### 배운 것 — 테스트를 의심하는 것도 일이다

「통과했다」와 「검증했다」는 다르다. 이 테스트는 **환경에 따라 아무것도 검증하지
않을 수 있었다.** Phase 1 의 오타 난 테스트(`buildes_on`)와 같은 종류의 위험인데,
그때는 오타라 눈에 보였고 이번엔 **플랫폼 동작에 달려 있어** 코드만 봐서는 알 수 없었다.

초록을 보고 넘어가지 않고 **전제를 재본 것**이 이번의 소득이다.
