# Phase 3: Q&A

vault 스캔과 링크 해석을 짜면서 나온 질문과 답.

## 온톨로지

### Q: RDF 가 정확히 뭔가

**모든 사실을 「주어 · 술어 · 목적어」 셋으로만 적는 데이터 모델.** 그 셋을
**트리플**이라 부르고, 그래프는 트리플을 모아둔 것이다. 그게 다다.

지금 만드는 SQLite 그래프는 사실의 **종류마다 자리가 다르다.**

```
type       -> node 테이블의 컬럼
builds_on  -> edge 테이블의 행
태그        -> tag 테이블의 행
```

RDF 는 자리가 하나뿐이다.

```
CIDR  type       Concept
CIDR  summary    "서브넷 마스크로 호스트 수를 세는 법"
CIDR  builds_on  Subnet mask
CIDR  tagged     Stack/Python
```

**이득 셋**

1. 스키마를 안 고치고 새 사실을 담는다. 술어 하나를 새로 쓰면 끝. `ALTER TABLE` 이 없다
2. **합치는 데 설계가 필요 없다.** 두 그래프를 합치는 건 트리플 집합의 합집합이다.
   JOIN 설계가 없다. RDF 가 웹 규모 데이터 통합을 위해 만들어져서 그렇다
3. **스키마도 트리플로 적는다.** 이게 속성 그래프와의 결정적 차이다

셋째가 핵심이다.

```
builds_on  is-a  TransitiveProperty
```

「`builds_on` 은 이행적이다」라는 **규칙 자체가 데이터**다. 코드 안에 숨어 있지
않다. 그래서 **추론기**가 규칙을 읽고 새 트리플을 만들 수 있다.

```
CIDR builds_on Subnet mask
Subnet mask builds_on Network layer
builds_on is-a TransitiveProperty
                    ↓
CIDR builds_on Network layer      <- 아무도 안 적었는데 참이다
```

**여기가 「지식 그래프」와 「온톨로지」가 갈리는 자리다.** Phase 5 까지는 질의할
때마다 재귀 CTE 로 계산한다. Phase 9 에서는 추론기가 아예 트리플로 만들어 넣는다.

**대가** — 타입 안전이 없다(뭐든 어디든 들어간다), SPARQL 을 배워야 한다,
저장 효율이 나쁘다.

### Q: IRI 는 뭔가

**주소 모양으로 생긴 전역 이름.** Internationalized Resource Identifier —
유니코드를 쓸 수 있게 확장한 URI 다. RDF 는 주어와 술어를 IRI 로 적으라고 요구한다.

왜 필요한지는 Phase 3 Step 1 이 그대로 보여준다.

```python
build(tmp_path, "000 Index/Hub.md", "500 Mind/Hub.md")
```

이름 하나가 파일 둘을 가리킨다. 그래서 인덱스 값을 리스트로 만들었다. 그런데
트리플을 적으려면 주어가 하나여야 한다.

```
Hub  type  Concept      <- 어느 Hub 인가?
```

IRI 가 이 모호함을 없앤다.

```
https://tomato.vault/doc/000%20Index/Hub
https://tomato.vault/doc/500%20Mind/Hub
```

**오해하기 쉬운 점 — 접속되는 주소가 아니다.** 브라우저에 넣어 뭔가 열릴 필요가
없다. 도메인을 소유하지 않아도 된다.

그러면 왜 URL 모양인가. **전역 유일성을 값싸게 얻으려고.** 도메인은 이미 세상에
하나씩만 있다. 내 `tomato.vault` 아래 것은 남의 `example.org` 아래 것과 절대
안 부딪힌다. **소유권 체계를 빌려 이름 충돌을 없앴다.**

`w3id.org` · `purl.org` 같은 영구 식별자 서비스가 왜 있는지도 여기서 나온다.

### Q: 네임스페이스가 800 TRPG 문제를 푼다

Phase 5 에서 `800 TRPG` 를 통째로 버린다. `type:` 을 게임 아이템 분류로 써서
축이 깨지기 때문이다. RDF 에서는 안 버려도 된다.

```
v:type      = https://tomato.vault/schema/type    문서 유형
trpg:type   = https://tomato.vault/trpg/type      아이템 분류
```

**같은 이름, 다른 네임스페이스, 충돌 없음.** SQLite 컬럼으로는 불가능했다.
컬럼 이름은 테이블 안에서 하나뿐이다.

되찾을지는 Phase 6 의 판단이다. 「필요한 질의가 없으면 안 넣는다」가 정본의 원칙.

### Q: 리터럴과 리소스의 차이

```
CIDR  summary    "서브넷 마스크로 호스트 수를 세는 법"   <- 리터럴
CIDR  builds_on  <doc/Subnet-mask>                    <- 리소스
```

**리터럴은 막다른 길이다.** 문자열·숫자·날짜고, 그것을 주어로 삼는 문장을 못 쓴다.
**리소스는 이어진다.** 다른 트리플의 주어가 될 수 있다.

판단 기준은 하나 — **"이것에 대해 나중에 더 말할 일이 있는가."**

태그가 애매하다. 리소스로 하면 **태그끼리 관계를 맺을 수 있다** —
`Stack/Python` 이 `Stack` 의 하위라는 사실을. Phase 8 의 SKOS `skos:broader` 가
그 자리다.

### 그래서 Phase 3 이 Phase 6 의 입력이다

Phase 6 에서 진짜 어려운 건 **"무엇을 문서의 IRI 로 삼을 것인가"** 다.

| 후보 | 문제 |
|---|---|
| 파일 경로 | 문서를 옮기면 **다른 것**이 된다. vault 는 계속 재배치된다 |
| 파일 이름 | **동명이인.** `Hub` 가 여럿 |
| 새 UUID | 안정적이지만 frontmatter 필드가 는다. 「필드 상한 6」과 충돌 |
| 내용 해시 | 문서를 고치면 다른 것이 된다. 최악 |

정답이 없다. **지금 NFC/NFD · 동명이인 · 대소문자를 손으로 겪어봐야** "이름을
식별자로 쓰면 안 된다" 가 실감이 나고, 그때 근거를 갖고 고를 수 있다.

## 실측 — NFC 정규화가 얼마나 중요한가 (2026-08-18)

Step 1 GREEN 직후, `test_a_name_is_indexed_in_nfc` 가 **진짜로 검증하는지**
의심스러워서 확인했다. APFS 는 정규화를 무시하고 비교하므로, 파일시스템이 NFC 를
돌려주면 우리 코드가 아무 일 안 해도 통과할 수 있었다.

### 1. 파일시스템은 준 대로 돌려준다

```
NFD 이름으로 만들어 rglob 로 읽으면  ->  NFD
NFC 이름으로 만들어 rglob 로 읽으면  ->  NFC
```

APFS 는 **넣은 그대로 보관하고 비교만 정규화 무시로 한다.** 그러니 테스트는
가짜 초록이 아니었다. `normalize` 를 빼면 실제로 실패한다.

### 2. 실제 vault 가 섞여 있다

```
NFC   3,871
NFD   1,091      <- 한글 파일명의 22%
ascii 1,503
```

한 vault 안에서 왜 갈리나. **만들어진 경로가 달라서다.** HFS+ 시절에 생긴 것,
iCloud 를 거친 것, 다른 도구가 만든 것이 섞였다. 사람은 구분할 방법이 없다.
눈에 똑같이 보인다.

NFD 목록에 이런 게 있었다.

```
100 Private Log/199 Private Kernel/Vault 온톨로지 — 스키마 정본.md
```

**스키마 정본 자신이 NFD 다.**

### 3. 정규화가 링크 5,341개를 살린다

```
본문 링크            24,371
정규화 없이 해석됨    17,116
NFC 정규화 후 해석됨  22,457
정규화가 살린 링크     5,341  (21.9%)
```

안 했으면 링크의 22% 가 깨진 것으로 잡혔다. Phase 2 의 `\|` 사고가 101개였으니
**50배**다. 가이드의 「실패하면 대량으로 깨진다」는 과장이 아니었다.

이건 **한국어 vault 라서** 생기는 문제다. 영어권 도구를 그대로 쓰면 안 되는 자리고,
답안지도 여기서 `nfc()` 헬퍼를 따로 뒀다.

### 「이름은 식별자가 아니다」의 증거가 쌓인다

| 증거 | 규모 |
|---|---|
| 같은 이름, 다른 파일 | `Hub.md` 등 — Step 3 에서 센다 |
| 같은 글자, 다른 코드포인트 | **파일 1,091개 · 링크 5,341개** |
| 대소문자 | Step 3 에서 센다 |

Phase 6 에서 IRI 를 고를 때 이 표가 근거가 된다 — [[phase03-qa]] 의 「RDF / IRI」 절.

### 배운 것 — 테스트를 의심하는 것도 일이다

「통과했다」와 「검증했다」는 다르다. 이 테스트는 **환경에 따라 아무것도 검증하지
않을 수 있었다.** Phase 1 의 오타 난 테스트(`buildes_on`)와 같은 종류의 위험인데,
그때는 오타라 눈에 보였고 이번엔 **플랫폼 동작에 달려 있어** 코드만 봐서는 알 수 없었다.

초록을 보고 넘어가지 않고 **전제를 재본 것**이 이번의 소득이다.

### 계측 스크립트가 세 번째로 거짓말했다

이번이 가장 위험한 형태였다.

```python
count["frontmatter edgess unresolved"] += 1   # 올리는 키
...
print(count["frontmatter edges unresolved"])  # 읽는 키
```

**출력이 0 이었다.** 앞의 두 번(Phase 1 라벨, Phase 2 정규식)은 숫자가 이상해서
눈에 띄었는데, 이건 **0 이라 안심시킨다.** 「없다」와 「안 셌다」가 같은 모양으로 나온다.

같은 스크립트에 `count["body links"]` 자리에 `count["body links unresolved"]` 를
쓴 오타도 있었다. 그쪽은 미해결이 전체보다 커져서 바로 티가 났다.

**교훈: 0 이 나오면 그 지표가 한 번이라도 올라간 적이 있는지 확인한다.**

### 숨어 있던 4건 — 셋은 위반이 아니었다

```
Ansible 인벤토리 — 호스트 그룹과 -i 옵션.md
    supersedes: 'backend-deployment.yml에서 backend_server를 참조하는 방식'
    supersedes: '`-i` 인자에 대해서'
Transformer.md
    supersedes: 'Transformer Self-Attention 학습 노트'
Docker - Go 프로덕션 이미지 distroless vs alpine.md
    builds_on: 'Docker.md'
```

**앞의 셋은 위반이 아니다.** 처음에 산문이라고 판단했는데 실물을 열어보니 셋 다
형식이 올바른 위키링크였다. 사라진 문서의 이름이다.

정본이 `supersedes` 를 「통합·분리 마이그레이션 산물만」이라 정의했다. 문서를
합치면서 옛 문서를 지웠고, 이 필드가 **무엇을 지웠는지 기록**한다.

| 관계 | 목표 | 없으면 |
|---|---|---|
| `builds_on` | 살아 있는 문서 | **위반** |
| `supersedes` | **죽은 문서** | **정상** |

`supersedes` 는 과거를 가리킨다. **목표가 없는 게 정상이다.** 고치면 이력이 사라진다.

답안지도 이걸 안다 — `vault lint` 는 `builds_on` 만 해결 검사를 하고 `supersedes`
는 하지 않는다. (다만 `vault.py` 463행 주석은 "builds_on·supersedes는 위에서 이미
검사했다"고 적어놨다. **답안지에도 낡은 주석이 있다.**)

실측 스크립트에서 둘을 같은 카운터로 묶으면서 이 구분을 잃었다.
**세는 단위를 잘못 묶으면 의미가 사라진다.**

마지막 하나는 파서 얘기다. `[[Docker.md]]` 처럼 확장자가 붙은 타깃을 Obsidian 은
허용하지만 `resolve_link` 는 못 받는다. **안 받기로 했다.**

- 실측 1건
- 정본이 `builds_on` 에 `"[[문서]]"` 형식을 못박았다
- 파서가 받아주면 **위반이 안 보이게 된다.** lint 가 잡아야 할 것을 파서가 먹는다

Phase 1 의 「인라인 리스트 미지원」과 같은 판단이다. **관대하게 받는 것이 늘 좋은 게
아니다.** 여기서는 거부가 정보다.

## 이름을 식별자로 쓸 때의 문제 — Phase 6 IRI 설계의 입력

Phase 3 의 진짜 산출물. 실측 근거를 붙여 정리한다.

| 고장 | 규모 | 왜 생기나 |
|---|---:|---|
| **같은 이름, 다른 파일** | 67 이름 · 244 파일 | 구조가 만든다. 실수가 아니다 |
| **같은 글자, 다른 코드포인트** | 파일 1,091 · 링크 5,341 | macOS 가 NFD 로 저장한 이력이 섞였다 |
| **대소문자만 다른 이름** | 4 무리 | Obsidian 은 무시하고 우리는 구별한다 |

### 1. 동명이인은 우연이 아니라 구조다

```
17개  SKILL              스킬마다 SKILL.md
16개  Hub                프로젝트마다 Core Files/Hub.md
13개  Worklog
12개  Quick Reference
10개  Tech Overview
 7개  architecture-design · database-design · program-design
 7개  _Insights · _Patterns
```

**이 이름들은 디렉토리 안에서만 뜻이 있다.** `Worklog` 하나로는 어느 프로젝트인지
알 수 없다. 이름을 고쳐 유일하게 만드는 건 해법이 아니다 — 구조가 그렇게 설계됐다.

**Phase 6 결론: IRI 는 경로를 포함해야 한다.** 이름만으로는 절대 안 된다.

그런데 경로 기반 IRI 는 **문서를 옮기면 다른 것이 된다.** vault 는 계속 재배치된다.
이 긴장이 Phase 6 의 실제 결정이고, 정답이 없다.

### 2. NFD 는 사람이 만든 문제가 아니다

파일 1,091개가 NFD 로 저장돼 있다. 같은 vault 안에서 갈리는 이유는 **만들어진 경로가
달라서**다 — HFS+ 시절, iCloud, 다른 도구. 사람은 구분할 방법이 없다. 눈에 똑같다.

정규화를 안 하면 링크 **5,341개(21.9%)** 가 깨진 것으로 잡힌다.

**IRI 에 이름이 들어가면 정규화 형태를 정본으로 못박아야 한다.** 안 그러면 같은
문서가 두 개의 IRI 를 갖는다. RDF 에서 그건 **다른 리소스**다.

### 3. 대소문자는 도구마다 답이 다르다

```
['WORKLOG', 'Worklog']        13대 2. Ideas/ 아래 둘만 표기가 다르다 — 고칠 만하다
['Python', 'python']          200 Dev vs _Archive 일본/ガクチカ
['00-Overview', '00-overview']
['_INDEX', '_index']          800 TRPG(제외) vs 400 Logic Forge
```

macOS 는 같은 디렉토리에서 공존을 막지만 다른 디렉토리는 허용한다. **Linux 로
clone 하면 전부 공존한다.** Obsidian 의 링크 해석은 대소문자를 무시하고 우리
`resolve_link` 는 구별한다 — **같은 링크에 두 도구가 다른 답을 낸다.**

### 그래서 IRI 후보를 다시 본다

| 후보 | 이 실측이 말하는 것 |
|---|---|
| 파일 이름 | **불가능.** 67 이름이 244 파일을 가리킨다 |
| 파일 경로 | 지금 유일하다. 다만 이동에 약하고, **정규화 형태를 못박아야** 한다 |
| 새 UUID | 이동·개명·정규화에 전부 강하다. 대신 필드가 는다 |
| 내용 해시 | 문서를 고치면 다른 것이 된다. 최악 |

**경로로 시작하되 무엇이 깨지는지 적어두는 것**이 실용적 출발점이다.
그 「무엇」이 방금 잰 세 가지다.

### 고친 것 (2026-08-18)

실측이 찾아낸 것 중 둘을 vault 에서 고쳤다.

| 고침 | 결과 |
|---|---|
| `builds_on: "[[Docker.md]]"` → `"[[Docker]]"` | frontmatter 미해결 4 → **3** |
| `Ideas/WORKLOG.md` 2건 → `Worklog.md` | 대소문자 충돌 4 → **3** 무리 |

`WORKLOG` 는 같은 역할의 파일 15개 중 둘만 표기가 어긋난 경우라 답이 명확했다.
이름 종류가 하나 줄고 `Worklog` 가 가진 파일이 13 → 15 가 됐다.

남은 충돌 셋(`Python`/`python` · `00-Overview`/`00-overview` · `_INDEX`/`_index`)은
**안 고친다.** 서로 다른 문서고 구역도 달라 어느 쪽이 옳다고 할 근거가 없다.
이름을 바꿔 없앨 문제가 아니라 **Phase 6 에서 IRI 에 대소문자를 어떻게 넣을지
정할 때 쓸 재료**다.

## Step 5 — 이름을 고칠까, 해석기를 고칠까

회고 중에 나온 질문에서 시작했다.

> 새로운 시스템을 도입함에 따라, 그 동명이인 파일들을 수정하여 동명이인 문제를
> 아예 해소하는 게 맞을까

**이름을 안 고친다. 해석기를 고쳤다.** 근거 셋.

1. **경로가 이미 그 정보를 갖고 있다.** `302.6 M-Project/302.6.0. Core Files/Hub.md`
   에서 프로젝트를 파일명에 또 넣는 건 정본의 「파생 가능한 사실은 쓰지 않는다」에
   정면으로 어긋난다
2. **템플릿이 이 이름들을 만든다.** `project-init` 이 프로젝트마다 Hub · Worklog ·
   Quick Reference 를 찍는다. 이름에 프로젝트를 넣으면 프로젝트 개명 시 파일 10개를
   같이 바꿔야 한다
3. **Obsidian 에서는 잘 된다.** 문제는 우리 `resolve_link` 가 **링크가 어디서 왔는지를
   안 받았다는 것**이다. 모호함이 아니라 **버린 정보**가 원인이었다

### 측정하지 않은 규칙을 구현했다

여기서 실수했다. 「고칠 만하다」고 판단한 근거는 이렇게 잰 126건이었다.

```python
near = [p for p in dupes[name] if p.startswith(here + "/")]   # 소스 디렉토리 아래
```

그런데 구현은 **접두사를 한 칸이라도 공유하면** 우대하는 규칙으로 썼다. 다른 규칙이다.
그리고 테스트도 그 넓은 규칙에 맞춰 써서 초록이었다.

**테스트가 스펙을 고정한다는 건, 스펙이 틀리면 틀린 것을 고정한다는 뜻이다.**

실제 vault 로 세 규칙을 비교했다.

| 규칙 | 바꾸는 링크 |
|---|---:|
| 접두사 1칸 이상 (처음 구현) | **1,443** |
| 접두사 2칸 이상 | 1,435 |
| **소스 디렉토리 아래에 있는 후보만** | **126** |

깊이로는 못 가린다. `300 Runtime/302 BNV Solutions` 처럼 두 칸까지 그냥 겹치는
경로가 많다.

넓은 규칙이 만든 결과가 이랬다.

```
소스  300 Runtime/301 Day Notes/2026-04-17.md
      [[Flutter FCM 딥링크 패턴]]
전:   200 Dev Knowledge Base/204 Frontend/Mobile/Flutter/...
후:   300 Runtime/302 BNV Solutions/302.7 E-Project/302.7.4. Learnings/...
```

공유하는 게 최상위 `300 Runtime` 하나뿐이다. **vault 의 10분의 1이 거기 있으니
사실상 정보가 없다.**

### 동명이인이 두 종류였다

이걸 구분 못 한 게 근본 원인이다.

| 종류 | 예 | 성질 |
|---|---|---|
| **구조** | Hub · Worklog · SKILL · architecture-design | 같은 역할의 파일이 프로젝트마다 하나씩 |
| **중복** | Flutter FCM 딥링크 패턴 | 같은 문서가 두 곳에 (Learnings → Dev KB 승격) |

앞은 위치로 풀린다. 뒤는 **「어느 게 가깝나」가 아니라 「어느 게 정본인가」**의 문제라
위치로 못 푼다. 넓은 규칙은 뒤쪽까지 건드리다 망가졌다.

### 최종 규칙

**소스와 같은 폴더 안에 후보가 있으면 그것. 아니면 정렬 첫 번째.**
형제 폴더는 「가깝다」로 안 친다.

좁은 규칙이 코드도 짧다 — `max` 와 점수 함수가 사라지고 루프 하나가 됐다.

126건이 실제로 이런 것들이었다.

```
소스  302.6 M-Project/302.6.1. Architecture/Tech Overview.md
      [[architecture-design]]
전:   302.5 bnvsglobal/302.5.1. Architecture/architecture-design.md   <- 다른 프로젝트
후:   302.6 M-Project/302.6.1. Architecture/architecture-design.md    <- 같은 폴더
```

Phase 5 에서 이게 그대로 엣지가 된다. 안 고쳤으면 「M-Project 의 아키텍처 문서」를
물었을 때 다른 프로젝트 것이 나왔다.

미해결 수와 해석 시간은 그대로다. **「깨졌나」가 아니라 「어디로 가나」의 문제였다.**

## 미룬 질문 — `supersedes` 는 필요한 필드인가

회고 중 두 번째 질문.

> supersedes 가 이미 삭제된 파일을 참조하고 있다면 굳이 필요한 field 인가

재봤다.

```
죽은 문서를 가리키는 supersedes    3건
그 죽은 이름을 가리키는 본문 링크   1건
```

이 필드가 살 수 있는 유일한 실용 근거는 **전달 표**다 — `[[옛 문서]]` 라는 깨진
링크를 만나면 「이제 이걸 보라」고 알려준다. 그 값이 1건이다.

**그래도 지금 지우지 않는다.** 구분해야 할 게 있다 — **쓸모없는 필드인가, 그 작업을
안 한 건가.**

정본의 마이그레이션 계획표에서 `supersedes` 가 생기는 자리는 Phase 3(분리·통합 실행)
이고 규모가 「후보 수에 따라」다. 3건이라는 건 **통합·분리를 3번 했다**는 뜻이지
필드가 안 쓰인다는 뜻이 아니다.

정보 자체는 유일하다. **git 은 파일이 지워진 건 알지만 누가 그 자리를 물려받았는지는
모른다.**

**판정을 Phase 9 로 미룬다.** 거기서 「추론이 필요한가」를 정하기로 했고,
`supersedes` 3건으로는 추론할 게 없다. 그때 「이 관계를 온톨로지에 넣을 값어치가
있나」를 같이 본다. 그 전에 분리·통합을 실제로 돌린다면 숫자가 달라진다.
