# 정규식 — 이 프로젝트에서 실제로 쓴 것만

Phase 1~5 는 표준 라이브러리만 쓴다. 파서를 손으로 짜니 정규식이 계속 나온다.
**여기는 문법 교재가 아니라, 우리 코드에 실제로 들어간 조각의 사전이다.**
Phase 가 늘 때마다 여기에 더한다.

---

## 조각 사전

| 조각 | 하는 일 | 우리 코드 |
|---|---|---|
| `^` | 문자열의 처음. `re.M` 이 있으면 **각 줄의 처음** | `fm_get` · `FENCE` |
| `$` | 문자열의 끝. `re.M` 이면 **각 줄의 끝** | `fm_get` |
| `.` | 개행 **말고** 아무 글자 하나. `re.S` 를 주면 개행도 포함 | `FRONTMATTER` |
| `*` | 앞의 것 0번 이상 | `[ \t]*` |
| `+` | 앞의 것 1번 이상 | `[^\[\]]+` |
| `?` | 앞의 것 0번 또는 1번 | `!?` (임베드의 `!`) |
| `*?` | 0번 이상인데 **가능한 한 적게** (비탐욕) | `FRONTMATTER` 의 `(.*?)` |
| `[abc]` | a·b·c 중 하나 | `[ \t]` |
| `[^abc]` | a·b·c 가 **아닌** 글자 하나 | `` [^`]* `` |
| `(...)` | 묶고 **꺼낼 수 있게** 한다 (`group(1)`) | 전부 |
| `(?:...)` | 묶기만 하고 안 꺼낸다 | `(?:[ \t]+-[ \t].*\n?)+` |
| `(?<!x)` | **바로 앞이 x 가 아닐 것.** 글자를 소비하지 않는다 | `LINK` 의 `(?<!\\)` |
| `\|` `\[` | 특수 글자를 글자 그대로 | `\[\[` |
| `{4,}` | 4번 이상 | `` `{4,} `` |

## 플래그

| 플래그 | 하는 일 | 조심할 것 |
|---|---|---|
| `re.M` | `^` `$` 가 줄 단위로 붙는다 | 없으면 문자열 전체의 처음·끝만 |
| `re.S` | `.` 이 개행도 먹는다 | **넣으면 안 되는 데가 있다.** 아래 참조 |

## 찾는 방법 셋

| 함수 | 어디서 찾나 |
|---|---|
| `re.match` | **문자열 맨 앞에서만.** 안 맞으면 바로 실패 |
| `re.search` | 아무 데서나. 첫 번째 하나 |
| `finditer` | 아무 데서나. 전부, 하나씩 |

`split_frontmatter` 가 `match` 를 쓰는 이유가 여기 있다. frontmatter 는 **파일 맨
앞에만** 있다. 정규식에 `^` 를 넣어 강제할 수도 있지만, **호출 방식으로 강제하는
쪽**을 골랐다.

## 밟은 함정 — 이게 진짜 내용이다

### 1. `\s` 는 개행을 먹는다

```python
re.search(r"^summary:\s*(.+)$", fm, re.M)     # 틀렸다
re.search(r"^summary:[ \t]*(.+)$", fm, re.M)  # 맞다
```

`summary:` 가 비어 있으면 `\s*` 가 줄을 넘어가 **다음 줄을 값으로 읽는다.**
`re.M` 에서 `^` `$` 는 줄 단위인데 `\s` 는 여전히 `\n` 을 포함한다. **이 둘이
어긋난다.** 그래서 이 프로젝트는 `\s` 를 안 쓴다.

### 2. `re.S` 는 필요한 데와 해로운 데가 갈린다

| 함수 | `re.S` | 왜 |
|---|---|---|
| `split_frontmatter` | **필요** | `---` 사이에 개행이 있다. `.` 이 넘어야 한다 |
| `fm_list` | **넣으면 깨진다** | `.*` 가 개행을 먹어 항목 하나가 나머지 전부를 삼킨다 |

`fm_list` 도 여러 줄에 걸치는데 `re.S` 없이 된다. **개행을 `.` 에 맡기지 않고
`\n` 을 직접 적었기** 때문이다. `re.S` 는 「`.` 이 개행을 먹느냐」만 정한다.
명시적으로 쓴 `\n` 은 언제나 개행에 붙는다.

### 3. 탐욕적 매칭이 옆 것까지 먹는다

기본은 **가능한 한 많이** 먹는다. `[[A]] and [[B]]` 에서 `\[\[(.+)\]\]` 는
가운데 전부를 하나로 잡는다. 막는 방법이 둘이다.

```python
r"\[\[(.+?)\]\]"       # 비탐욕 — 가능한 한 적게
r"\[\[([^\[\]]+)\]\]"  # 문자 클래스 — 대괄호를 못 넘는다
```

**문자 클래스가 더 강하다.** 비탐욕은 "적게" 지만 필요하면 늘어난다. 문자 클래스는
**넘어갈 수 없다.** 우리는 세 자리에서 이렇게 막았다.

| 어디 | 막은 방법 |
|---|---|
| `FRONTMATTER` | `(.*?)` 비탐욕 |
| `INLINE` | `` `[^`]*` `` |
| `LINK` | `[^\[\]]+` |

### 4. 구분자에 포함 관계가 있으면 긴 것부터

이건 정규식만의 얘기가 아니라 **자르는 순서**의 문제다.

```
문서\|별칭
```

`|` 를 먼저 자르면 `문서\` 가 남는다. 역슬래시가 붙어 나온다. `\|` 를 먼저 잘라야
`문서` 가 나온다. **짧은 쪽(`|`)이 긴 쪽(`\|`) 안에 들어 있어서** 짧은 쪽을 먼저
처리하면 긴 쪽을 알아볼 기회가 사라진다.

같은 구조가 `strip_code` 에도 있다. `` ``` `` 안에 `` ` `` 가 들어 있으니
**펜스를 먼저** 지운다. 인라인 코드를 먼저 벗기면 백틱 셋 중 둘이 「빈 인라인
코드」로 먹히고 하나만 남아 펜스가 사라진다.

세 자리를 나란히 놓으면 이렇다.

~~~
\|   vs  |       →  \| 를 먼저 자른다         link_target
```  vs  `       →  ``` 를 먼저 지운다        strip_code
(.+) vs  [^x]+   →  아예 못 넘게 막는다       LINK · INLINE
~~~

앞의 둘이 「긴 것부터」이고 셋째는 「넘지 못하게」다. 목적은 같다 —
**옆 것을 먹지 않게 한다.**

### 5. 후방탐색은 글자를 소비하지 않는다

```python
r"(?<!\\)!?\[\[([^\[\]]+)\]\]"
```

`\[[CIDR]]` 은 링크가 아니다. 앞의 `\` 가 막는다.

`[^\\]\[\[` 처럼 **글자를 소비하는** 방식으로 짜면 문자열 맨 앞의 링크를 못 잡는다.
앞에 아무 글자도 없으니까. `(?<!\\)` 는 **위치만 검사**하므로 맨 앞에서도 성공한다.
"앞에 백슬래시가 없다" 는 사실이 참이기 때문이다.

### 6. 키 이름은 `re.escape` 를 통과시킨다

```python
re.search(rf"^{re.escape(key)}:[ \t]*(.+)$", fm, re.M)
```

`key` 에 `.` 이나 `+` 가 들어 있으면 정규식 특수 글자로 해석된다.
`re.escape` 가 전부 글자 그대로로 만든다.

## 자주 쓰는 관용구

```python
raw.split(sep, 1)[0]
```

첫 구분자에서 한 번만 자르고 앞쪽. **구분자가 없으면 원본이 그대로** 나오므로
「있나 없나」를 묻는 분기가 필요 없다.

```python
text.split("\n")   →  "\n".join(lines)
```

`splitlines()` 가 아니다. `splitlines()` 는 `\v` · `\f` · `\u2028` 도 줄바꿈으로
보고, `"a\n".splitlines()` 는 마지막 개행을 잃는다. `split("\n")` 은
**정확히 되돌아온다.**
