# Phase 10 — 문제 계약과 역량 질문

> 3부의 출발점. 구현보다 먼저 무엇을 답해야 하는지 고정한다.

## 왜 이 Phase가 먼저인가

Phase 6~9는 문서·폴더·태그를 형식 온톨로지로 표현했지만, SQLite로 답하지
못하던 질문을 새로 열지는 못했다. 3부에서 같은 실수를 반복하지 않으려면 클래스나
엔진보다 **역량 질문(competency question)** 이 먼저다.

Phase 10은 코드를 거의 만들지 않는다. 대신 이후 Phase가 무엇을 만들고 무엇을
만들지 않을지 판정할 계약을 만든다.

## 시작 기준선

```bash
uv sync
uv run pytest -q       # 2026-08-25 기준 241 passed
```

- Markdown은 정본이다.
- SQLite 그래프는 기존 문서 질의의 운영 구현으로 유지한다.
- RDF/OWL 산출물은 없애지 않는다.
- VectorDB는 별도 작업 축이다. 3부는 인터페이스 경계만 기록하고 구현하지 않는다.
- Phase 1~9의 결론은 실패가 아니라 3부의 대조군이다.
- 적용 범위는 개발 지식만이 아니라 개인 경험·성찰·가치·철학·커리어·생활을 포함한
  Vault 전체다. 다만 모든 문서를 처음부터 전수 annotation하지 않는다.

## Step 1 — 질문 후보를 실제 사용 장면에서 모은다

> **절차는 [`part3-decisions.md`](part3-decisions.md)의 D5에 있다.** Claude가
> 증거 등급 A·B만 써서 발굴하고, 토마토가 승인·기각한다. 근거 경로 없는 후보는
> 목록에 못 들어온다. 최대 광맥은 `500 Mind Compiler`의 질문 63개이며, 삶의
> 질문을 역량 질문으로 **변환**해서 쓴다.

최소 20개를 작성한다. 추상적인 "지식을 더 잘 찾는다"가 아니라 입력과 기대 답이
보이는 질문이어야 한다.

예:

- 이 원칙은 어떤 사건과 주장에 근거하는가?
- 이 결정을 반박하는 근거가 생기면 무엇을 다시 검토해야 하는가?
- 사건에서 얻은 교훈이 어떤 원칙과 절차로 이어졌는가?
- 폐기된 자료에 의존하는 현재 유효한 문서는 무엇인가?
- 원칙 하나를 바꾸면 어떤 절차와 프로젝트가 영향을 받는가?
- 개인 경험에서 반복된 판단 기준이 개발 원칙에도 나타나는가?
- 어떤 철학이나 가치가 기술·커리어 결정에 영향을 주었는가?
- 개발 사건의 교훈과 삶의 원칙이 서로 보강하거나 긴장하는 지점은 어디인가?
- 같은 믿음이 시간에 따라 어떻게 변했고 어떤 경험이 변화를 일으켰는가?

### 영역 표본 규칙

- 000·100·200·300·400·500·600·700 대역에서 질문을 적어도 하나씩 만든다.
- 적어도 다섯 질문은 서로 다른 대역을 잇는다.
- 개발 지식 질문이 전체의 절반을 넘지 않게 시작한다.
- Hub·Template·단순 Log처럼 의미 추출이 불필요한 문서를 허용한다.

확정됐다. Phase 10은 이를 전제로 질문을 쓴다.

## Step 2 — 질문마다 담당 계층을 판정한다

| 담당 | 판정 기준 |
|---|---|
| 기존 SQLite | 문서·태그·링크·경로만으로 정확히 답할 수 있다 |
| 온톨로지 | 개체 종류와 관계 의미가 있어야 답할 수 있다 |
| SHACL | 존재해야 할 값이나 허용할 구조를 검사한다 |
| 운영 규칙 | 상태 변경, 재검토, 우선순위처럼 절차적 판단이다 |
| Vector | 의미 유사 후보를 찾아야 한다. 3부 구현 범위 밖이다 |

한 질문에 여러 계층이 필요할 수 있지만, 각 계층의 책임은 분리해 쓴다.

## Step 3 — 정답과 반례를 먼저 쓴다

각 질문은 다음 필드를 가진다.

```text
ID
질문
사용 장면
최소 입력
기대 답
답에 포함할 근거
반례
담당 계층
현재 구현으로 가능한가
성공 측정법
```

"관련 문서가 나온다"는 정답이 아니다. 어떤 문서와 어떤 관계 경로가 나와야
하는지까지 적는다.

## Step 4 — 3부의 비목표를 고정한다

- 검색 품질 향상을 이유로 OWL 공리를 늘리지 않는다.
- VectorDB·임베딩·청킹을 구현하지 않는다.
- 전체 Vault를 자동 의미 추출하지 않는다.
- 저장 엔진을 먼저 교체하지 않는다.
- 에이전트에게 쓰기 권한을 주지 않는다.
- 트리플 수와 클래스 수를 성공 지표로 삼지 않는다.

## Step 5 — 위험 장부를 만든다

각 위험에 발생 조건, 관측 방법, 완화책, 중단 조건을 붙인다. 최소 항목은 다음과
같다.

- 문서 유형과 실제 지식 개체의 혼동
- 안정 ID 부재와 문서 이동
- 의미 라벨링 비용
- 자동 추출 오탐
- OWA 추론과 닫힌 세계 검증의 혼동
- 추론 결과의 철회와 출처 추적
- 기존 CLI·RDF와의 호환성 파괴
- 제안 기능이 실제 작업보다 더 많은 검토 부담을 만드는 위험
- 기술적 `Claim`과 개인적 `Belief`·`Value`·`Interpretation`을 같은 것으로 만드는 위험
- 교차 영역 연결을 늘리기 위해 근거 없는 관계를 승인하는 위험
- 민감한 개인 문서가 외부 모델·로그에 노출되는 위험

## 난이도와 위험

**난이도: 중간. 구현 난이도는 낮지만 판단 난이도는 높다.**

Phase 1~5는 입력과 출력이 명확했다. 여기서는 잘못 고른 질문이 이후 모든 구현을
쓸모없게 만들 수 있다. 테스트가 초록이어도 질문 자체가 필요 없으면 실패다. 따라서
이 Phase의 GREEN은 코드 통과가 아니라 **실제 사용 장면과 정답이 합의된 상태**다.
Vault 전체를 다루므로 한 영역에서 자연스러운 의미 구분을 다른 영역에 성급하게
일반화하지 않는 것도 이 Phase의 핵심 판단이다.
