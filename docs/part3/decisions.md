## D1 — 라벨링 비용 시험을 설계 앞으로 당긴다

> 2026-08-26에 번호를 다시 매겼다. 아래 번호는 **당시의 계획 번호**다.
> 현재 번호는 [`part3-open-decisions.md`](open-decisions.md)의 결정 2에 있다.

### 문제

원래 계획은 이 순서였다.

```
(구) Phase 11   안정 ID 설계        비가역
(구) Phase 12   온톨로지 kernel 0.1  비가역
(구) Phase 13   gold set 50개  ← "비용이 감당 안 되면 중단한다"
```

중단 스위치가 가장 비싼 설계 두 개 **뒤에** 있다. 그리고 그 둘은 「의미의 최소
단위가 무엇인가」를 **추측해서** 만들게 된다. 그 단위를 실제로 알려주는 것은
손으로 라벨링해보는 일이다.

2부에서 이미 같은 교훈을 얻었다. Phase 9의 「추론이 유용한 새 사실을 0개
만들었다」는 결론은 **돌려봤기 때문에** 나왔다.

### 결정

[`phase11.md`](../phases/phase11.md) — 문서 8~10개짜리 라벨링 파일럿을 Phase 10 직후에
둔다. 정식 어휘 없이, 임시 표기로. 산출물은 데이터가 아니라 숫자 세 개다.

```
문서 하나 라벨링에 몇 분 걸리는가
의미 단위가 문서인가 섹션인가 블록인가
일주일 뒤 다시 라벨링했을 때 같은 답이 나오는가
```

세 번째가 가장 크다. **기준 자체가 흔들리면 이후 평가가 전부 무의미하다.**

Phase 13·14는 이 숫자를 입력으로 받아 설계한다.

## D2 — 3부의 종착점은 Phase 18이다

### 결정

**읽기 전용 도구까지 만든다.** 질의하고 근거를 설명하는 데서 멈춘다.

| Phase | 상태 |
|---|---|
| 10 ~ 18 | 3부의 범위 |
| 19 제안·승인·철회 | **보류.** Phase 18의 2주 실사용 결과를 보고 다시 판단 |
| 20 제한 운영 | **보류.** 19가 정당화되지 않으면 시작하지 않는다 |

### 근거

phase20가 스스로 적어둔 문장이 그대로 근거다.

> 유용한 읽기 전용 도구로 끝나는 것도 정당한 결론이며, 자동 쓰기는 필수 성공
> 조건이 아니다.

쓰기·제안·승인 기계를 만드는 순간 문제가 정확도에서 **거버넌스**로 바뀐다.
승인된 의미 사실이 틀리면 이후 추론이 연쇄 오염되고, 그때부터는 상태 분리·감사·
철회가 기능의 본체가 된다. 읽기 전용 도구가 실제로 쓸모 있다는 증거가 나오기
전에 그 부담을 질 이유가 없다.

19·20의 가이드 문서는 지우지 않는다. 판단이 바뀌면 그대로 쓴다.

## D3 — 900 Archive는 밴드가 아니라 문서 단위로 참여한다

### 실측 (2026-08-25)

```
900 Archive    210개 파일
  type: 있는 파일           0개
  --- 로 시작하는 파일       0개
```

frontmatter가 **하나도 없다.** 자동 빌드에 넣으면 빈 노드 210개가 생길 뿐이다.

### 결정

- `vault.graph.EXCLUDED_ZONES`는 그대로 둔다. 900은 문서 그래프에서 계속 빠진다.
- 역량 질문이 특정 과거 문서를 필요로 할 때, **그 문서만** 손으로 의미 그래프에
  넣는다. 이때 archived 상태와 시점을 함께 적는다.
- archived 사실이 현재 유효한 asserted 사실로 자동 승격되지 않는다.

즉 참여 여부를 밴드가 아니라 **질문이** 결정한다. 계보를 물어야 할 이유가 생긴
문서만 들어온다.

### 하지 않기로 한 것

900의 210개에 frontmatter를 채우는 선행 작업. 3부와 별개의 vault 정비이고,
분량이 3부 자체보다 클 수 있다. [`vault-backlog.md`](../backlog/vault-backlog.md)의 항목으로
남긴다.

## D4 — 100 Private Log는 참여시킨다 (2026-08-26 개정: 읽기 제한 해제)

> **처음 결정을 뒤집었다.** 「Claude가 원문을 열지 않는다」로 정했다가, 경로
> 규칙으로는 프라이버시가 지켜지지 않는다는 것이 확인돼(D6) 축을 바꿨다.
> **읽기는 자유, 쓰기 경계만 지킨다.** 아래 표의 「원문 읽기」·「라벨링」 행은
> 폐기됐고 D6의 규칙이 그 자리를 대신한다.

### 실측 (2026-08-25)

```
100 Private Log    154개 파일 — 전부 frontmatter 있음
  type: log          81
  type: reflection   69
  type: reference     4
```

3부가 노리는 「경험 → 성찰 → 원칙」 계보가 실제로 여기 있다. 빼면 교차 영역
질문의 절반이 죽는다.

### 결정 — 운영 규칙

| | |
|---|---|
| 밴드 참여 | **한다.** gold set과 역량 질문에 포함 |
| ~~원문 읽기~~ | ~~열지 않는다~~ → **제한 없음** (2026-08-26 개정) |
| ~~라벨링~~ | ~~토마토가 직접~~ → **Claude가 초안을 만들어도 된다** |
| 사적 내용을 옮기는 것 | **금지** — docs·커밋 메시지·learnings·후보 목록·제안 로그 (D6) |
| 근거 표기 | **경로만.** 인용하지 않는다 |
| 적용 범위 | Claude 본인과 subagent·workflow 전부 |

`Person/` 태그의 가족 이름, 감정, 관계가 여기 있다. 임베딩 A/B에서 OpenAI를
후보에서 뺀 것과 같은 판단이며, 그때는 대량 반출이 문제였고 여기서는 열람
자체가 문제다.

### 개정 뒤에도 남는 것

**100 대역 문서 2개를 파일럿에 넣는다.** 읽기 제한이 풀렸으니 목적이 바뀌었다 —
「규칙이 유지 가능한가」가 아니라 **「개인 문서의 라벨링이 기술 문서와 얼마나
다른가」**를 잰다. 관점·시점·해석 변화가 얹히므로 비용 구조가 다를 수 있다.

## 묻지 않고 정한 것

### 어휘 네임스페이스 — 기존 문서 어휘를 개명한다

> **2026-08-26 뒤집었다.** 처음에는 phase13 Step 1의 2번(개명하지 않고 새
> 네임스페이스)으로 정했다. 근거는 「개명이 `.vault.ttl` 소비자와 테스트
> 241개를 깨뜨린다」였다. **그 근거가 실측으로 무너졌다.**

```
잰 것 1   .vault.ttl 을 읽는 코드          0곳    깨뜨릴 소비자가 없다
잰 것 2   클래스 이름을 쓰는 테스트          4개    46개로 추정했던 것이 4개였다
잰 것 3   현재 의미 사실                    0개    마이그레이션할 데이터가 없다
```

「기존 RDF 소비자 호환성」은 Step 1의 판정 기준 셋 중 하나였는데, **실제로는 비어
있는 기준이었다.** 남은 두 기준(질의 명료성·마이그레이션 비용)은 둘 다 개명 쪽이다.
그리고 지금이 가장 싸다 — gold set 50개를 만든 뒤엔 훨씬 비싸진다.

```
v:Principle          →  v:PrincipleDocument     문서 13종 전부 Document 접미
bare v:Principle                                 지식 개체 몫으로 비워둔다
```

**호환 공리는 두지 않는다.** phase13 Step 1의 1번은 「개명하고 호환 공리를 둔다」
였지만, `owl:equivalentClass v:Principle`을 두면 Phase 9의 OWL RL 닫힘이 모든
문서를 다시 `v:Principle`로 타입한다. 없애려던 모호함이 추론 그래프에서 그대로
되살아난다. 소비자가 0곳이라 둘 이유도 없다.

`project-doc` 하나만 예외다. 기계적으로 붙이면 `ProjectDocDocument`가 되어
`v:ProjectDocument`로 한다. `rdf.py`의 `_class_name`에 주석과 함께 적혀 있다.

## D5 — 역량 질문은 Claude가 발굴하고 토마토가 승인한다

> 2026-08-25 정정. 처음에는 「토마토가 쓴다」로 정했다가 뒤집었다.

### 왜 뒤집을 수 있었나

vault를 실제로 조사한 뒤다. `500 Mind Compiler`에 **질문으로 조직된 문서 63개**가
있다. 파일명이 곧 질문이고, `_Insights`·`_Patterns`에는 교차 연결과 근거 위치가
이미 손으로 적혀 있다.

즉 지어낼 필요가 없다. **캐내면 된다.** 원래 「토마토가 쓴다」로 정한 이유는
Claude가 실사용 장면을 지어내면 Phase 10 전체가 허구 위에 올라가기 때문이었는데,
그 위험은 저자를 바꿔서가 아니라 **증거 규칙으로** 막는다.

### 증거 등급 — D는 목록에 못 들어온다

| 등급 | 증거 | 채택 |
|---|---|---|
| A | 문서에 질문 문장이 실제로 적혀 있다 | ✅ |
| B | 같은 판단이 여러 문서에 반복된다 | ✅ |
| C | 구조가 암시한다 (`## 관련` · supersedes 체인) | 후보만 |
| D | Claude가 그럴듯해서 만들었다 | ❌ |

**모든 후보는 근거 경로를 단다.** 경로가 없으면 후보가 아니다.

### 삶의 질문과 역량 질문은 다르다

500의 63개는 그대로 쓸 수 없다. 변환한다.

```
삶의 질문     "나의 핵심 가치는 무엇인가?"              ← vault가 답하려는 것
    │  이 질문에 진전을 보려면 무엇을 알아야 하는가
역량 질문     "어떤 가치가 서로 다른 대역의 결정에
              반복해 나타났고, 각각의 근거는 무엇인가?"   ← 도구가 답해야 하는 것
```

아래 것만 3부의 대상이다. 위의 것은 근거다.

### 판정은 종이가 아니라 실행으로 한다

「온톨로지가 필요해 보인다」로 판정하지 않는다. 기존 SQLite로 **실제로 돌려본다.**

```
답이 나온다      → 3부 목표에서 제외
답이 안 나온다   → 왜인지 적는다
                  관계 의미 없음 → 온톨로지    값 없음 → SHACL
                  상태 판단      → 운영 규칙    의미 유사도 → Vector (범위 밖)
```

2부가 여기서 넘어졌다. 다 만든 뒤에 「SQLite로 이미 된다」가 나왔다.

### 2단 통과

```
1차   후보 40~50개 · 4필드      질문 · 근거 경로 · 최소 입력 · 기대 답의 형태
판정   돌려보고 걷어낸다
2차   살아남은 20개+ · 전체 필드  phase10 Step 3의 10필드
```

한 번에 10필드짜리를 쓰면 절반을 버리게 된다.

### 토마토의 몫

승인과 기각. 그리고 **100 대역 질문은 여전히 직접** 쓴다 (D4).

## D6 — 100 Private Log의 내용은 500에도 있다

### 문제

D4를 「`100 Private Log/` 아래를 열지 않는다」로 적었는데, 그것으로는 막히지 않는다.
`500 Mind Compiler`의 `_Patterns.md`가 100의 문장을 **직접 인용**한다.

```
패턴 5 … [[2026.05.31 친구]] 4행 — "…" 라고 직접 포착
```

경로 규칙으로 프라이버시를 지키려던 시도의 한계다. 사적인 내용은 대역 경계를
따라 얌전히 머무르지 않는다.

### 결정

500을 읽지 않는 것은 선택지가 아니다. 역량 질문의 최대 광맥이고, 3부의 교차 영역
목표가 통째로 여기 걸려 있다.

| | |
|---|---|
| `100 Private Log/` 원문 | 열지 않는다 (D4 유지) |
| 500의 `_Insights`·`_Patterns`·`By Subquestion` | **읽는다** |
| 거기서 본 사적 내용 | **밖으로 옮기지 않는다** — docs·커밋 메시지·learnings·후보 목록 |
| 후보 질문의 근거 | **경로만** 적는다. 인용하지 않는다 |

즉 규칙의 축을 「어디를 읽는가」에서 **「무엇을 옮기는가」**로 옮긴다. 읽기 경계는
새지만 쓰기 경계는 안 샌다.

## Phase 13 선행 관측 — 정체성

phase13은 「3부에서 가장 먼저 만나는 비가역적 설계 결정」이라고 스스로를 소개한다.
조사 결과 그 압박이 **예상보다 작다.** 대신 다른 곳이 어렵다.

### 관측 1 — 마이그레이션할 데이터가 0개다

```
판단 타입끼리의 관계 (템플릿이 만든 decision↔tradeoff 제외)   8건
근거를 나타내는 관계                                        없음
supersedes                                        5건, 전부 미해결
```

ID를 잘못 고르면 「이후 모든 relation과 provenance를 마이그레이션해야 한다」는
것이 phase13의 위험 서술이다. **지금은 마이그레이션할 relation이 없다.**
gold set을 만들기 전까지 ID 정책은 사실상 되돌릴 수 있다.

→ Phase 13에 시간을 덜 쓰고 Phase 11·12에 더 쓴다.

### 관측 2 — 이미 쓰는 앵커가 가장 부서지기 쉬운 것이다

`500 Mind Compiler/Q7. Who Am I/_Patterns.md`가 근거를 이렇게 가리킨다.

```
[[문서 이름]] 4행
```

**행 번호다.** 위쪽에 한 줄만 추가돼도 어긋난다. 사용자가 이미 하고 있는 방식이
곧 좋은 방식이라는 뜻은 아니라는 반례다.

→ Phase 13은 「무엇을 쓰고 있나」가 아니라 **「그것이 편집을 견디나」**를 시험해야
한다. 행 번호 앵커를 시나리오 테스트에 반드시 넣는다.

### 관측 3 — 완벽한 시험 사례가 vault에 있다

`900 Archive/Mind Compiler/`의 Q3가 phase13 Step 3의 시나리오를 한꺼번에 만족한다.

```
경로가 바뀌었다        500 Mind Compiler → 900 Archive
상태가 바뀌었다        진행 중 → 답 확정 (v1.0, 2026-02-01)
개체는 살아 있다       결론이 현재 Q7·Q2 에서 계속 작동한다
링크는 없다           두 문서 사이에 아무 관계도 안 적혀 있다
```

**artifact는 이동했고 knowledge entity는 유지됐다.** phase13이 요구하는
`delete artifact but retain knowledge entity` 시나리오의 실물이다.

→ 가상 fixture를 만들기 전에 이 사례로 먼저 시험한다.

### 관측 4 — frontmatter 기반 ID는 900에 못 쓴다

`900 Archive` 210개 전부 frontmatter가 없다. 명시적 ID를 frontmatter에 두는
후보는 archive를 편입하는 순간 작동하지 않는다.

→ ID 정책은 frontmatter **단독**에 의존할 수 없다. 아니면 편입 시 frontmatter를
붙이는 비용을 정책에 포함해야 한다.

## Phase 14 선행 관측 — 어휘

### 관측 5 — 어휘 후보 목록이 vault와 어긋난다

phase14가 나열한 클래스 후보와 실제 vault의 `type` 사용량을 대보면 이렇다.

| phase14 후보 | vault 실제 |
|---|---|
| Concept | `concept` **568** ✅ |
| Decision | `decision` **45** ✅ |
| Principle | `principle` **94** ✅ |
| Procedure | `procedure` **149** ✅ |
| Event | `case` 31 로 존재 (이름이 다르다) |
| Project | `project-doc` 771 ✅ |
| **Claim** | **없다** |
| — | **`tradeoff` 44 — 후보 목록에 없는데 실제로 쓰인다** |

`Claim`은 phase14·13·16이 계속 쓰는 중심 개념인데 vault에 대응물이 없다.
`tradeoff`는 44개가 실재하고 `decision`과 140건으로 이어져 있는데 후보에 없다.

→ Phase 14는 **`Claim`을 도입할 근거와 `Tradeoff`를 뺄 근거를 각각 대야 한다.**
어느 쪽도 지금은 없다.

### 관측 6 — 관계 어휘는 12개 후보 중 실제로 쓰이는 것이 0개다

```
phase14 관계 후보
  expresses · supports · contradicts · derivedFrom · observedIn
  appliesTo · requires · operationalizedBy · supersedes
  invalidates · hasEvidence · affects

vault 실제
  links_to    9,544   의미 없음
  builds_on     419   선수과목. principle 중 1개, decision 중 1개만 보유
  supersedes      5   전부 미해결
```

**12개 중 `supersedes` 하나만 이름이 겹치고, 그것도 작동하지 않는다.**

→ 클래스는 기존 `type`을 승격하는 문제이고, 관계는 **백지에서 만드는 문제**다.
난이도가 다르다. Phase 14의 무게는 클래스가 아니라 관계에 있다.

### 관측 7 — vault의 메타 원칙이 문서로 있다

`000 Index/Maintenance/디렉토리 철학/`의 9개 문서가 **전부 `type: principle`**이다.
각 대역이 무엇을 담아야 하는지가 원칙으로 적혀 있다.

→ kernel을 설계할 때 이 9개가 1차 자료다. 새 어휘를 짓기 전에 **이미 적힌 원칙이
무엇을 요구하는지** 먼저 읽는다.

### 관측 8 — 인식적 지위 분리의 선례가 대역에 있다

```
600  필사      "저자가 이렇게 말했다"
400  결정      "나는 이렇게 판단했다"
200  원칙      "나는 이것을 지킨다"
```

phase14가 「기술적 `Claim`과 개인적 `Belief`의 진리 조건이 다르니 섞지 말라」고
경고한 그 분리를, vault는 디렉토리로 이미 하고 있다.

→ Phase 14는 이 구분을 **형식화**하는 것이지 새로 만드는 것이 아니다. 난이도
판정이 「높음」에서 한 단계 내려간다.
