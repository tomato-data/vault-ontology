## 1. 어디에 적는가

Phase 11이 문서 11개에 세 형식을 실제로 대봤다. 결과로 정본이 정해졌다.

| | 정본인가 | 왜 |
|---|---|---|
| **frontmatter** | ✅ | 파서 한 줄로 타입 있는 엣지가 된다. 기존 `builds_on`과 같은 자리 |
| **sidecar** | ✅ | 문서 안의 항목을 가리킬 수 있다 |
| 본문 섹션 | ❌ | `links_to`로만 보인다. **관계 이름이 파서에서 사라진다** |

### 둘의 경계

```
문서 단위 관계        →  frontmatter
문서 안의 항목        →  sidecar
```

**항목 단위가 필요한 문서는 vault 전체에서 13개(0.3%)뿐이다.**

```
500 Mind Compiler   Q1~Q7 의 _Insights 6 · _Patterns 6
900 Archive         Q3 의 _Insights · _Patterns
                                                    항목 147개
```

그 13개는 **이미 항목 번호를 갖고 있다.** 「인사이트 10」이 그대로 앵커이고,
그 번호로 가리키는 관행도 이미 있다(파일럿 10번에서 4건 확인). 새 ID를 만들지 않는다.

### 본문 산문은 그대로 둔다

정본이 아니라는 것이지 쓰지 말라는 것이 아니다. 이미 잘 쓰이고 있다.

```
「관통 원칙은 [[A]]와 [[B]]」          4번 문서
「[[X]] — 판단하지 않으려는 마인드의 근원」   10번 문서
```

**사람이 읽는 자리는 산문이고, 기계가 읽는 자리는 frontmatter다.** 둘이 같은 것을
말해도 된다. 산문이 정본을 대신하지 못할 뿐이다.

## 2. 상태 — asserted · proposed · inferred

### 어디에 두는가

```yaml
---
type: principle
derived_from:              # asserted — 기본값
  - "[[사례 - 간헐적 500 에러]]"
proposed:                  # 미승인
  derived_from:
    - "[[Day Note 2026-04-28]]"
  diverges_from:
    - "[[Chapter 19 소프트웨어 트렌드]]"
---
```

**승인은 한 줄을 위로 옮기는 것이다.** Phase 19(제안·승인 workflow)를 보류했으므로
승인은 손으로 한다. 그러니 동작이 최대한 단순해야 한다.

| 상태 | 자리 |
|---|---|
| `asserted` | frontmatter 최상위 · sidecar 항목 라벨 |
| `proposed` | frontmatter의 `proposed:` 블록 · sidecar의 `## 제안` 절 |
| `rejected` | **sidecar에만.** 문서의 사실이 아니라 작업 이력이다 |
| `inferred` | **안 적는다.** 질의 시점에 계산한다 |

### `inferred`를 안 적는 이유

Phase 9에서 쟀다. OWL RL 물질화가 트리플을 **2.81배**로 늘렸는데 질적으로 새로운
유용한 사실은 **0개**였다. 그리고 물질화하면 입력이 철회돼도 **낡은 결과가 남는다.**

계산할 수 있는 것은 계산한다.

### `rejected`를 남기는 이유

`phase12.md`가 요구한다.

> 거절한 제안도 모델·시점·이유와 함께 남겨 **반복 제안을 막을** 수 있어야 한다.

거절 이유를 frontmatter에 남기면 문서가 지저분해지고, 무엇보다 **그건 문서에 관한
사실이 아니라 우리가 한 작업의 기록**이다.

```markdown
## 제안 — 거절됨

- ~~derived_from → [[테스트 스위트 성능…]]~~
  2026-08-26 거절. 이 문서는 원칙의 **근거**가 아니라 **적용 사례**다
```

## 3. 무엇이 asserted 인가

파일럿에서 네 경로가 나왔다.

| 경로 | 상태 |
|---|---|
| 문서에 이미 있던 것을 형식화 | **asserted** |
| Claude 제안 → 사람이 명시 승인 | **asserted** |
| Claude 제안 → 사람이 **위임** | **proposed** |
| 사람이 직접 판단 | **asserted** |

**세 번째가 핵심이다.** 「적절한 걸로 해놓아주세요」는 승인이 아니라
**「일단 해두고 나중에 볼게」**다 (2026-08-26 확인).

### 파일럿 라벨의 소급 분류

```
asserted    11
proposed    37     77%
```

가장 큰 덩어리는 5번 문서의 **챕터 매핑 14개**다. 「챕터로 합시다」는 방향 승인이었고
12개 절을 어느 챕터에 대는지는 Claude가 판단했다. **틀렸어도 지금은 알 방법이 없다.**

이 비율 자체가 이 절이 필요한 이유다.

## 4. 값의 종류 — 링크만이 아니다

파일럿에서 대상이 문서가 아닌 경우가 두 번 나왔다.

```yaml
derived_from:
  - "[[사례 문서]]"        링크        가장 흔하다
  - experience            키워드      실무에서 나왔다. vault에 문서가 없다
  - "ext:ai-ops-skills/2-verification/tdd"    vault 밖
```

**파서가 이 셋을 갈라야 한다.** 키워드와 외부 참조를 「깨진 링크」로 세면 이미
1,191건인 미해결 더미에 섞인다.

| | 뜻 |
|---|---|
| `[[문서]]` | vault 안의 문서 |
| 키워드 | 문서가 아닌 출처. `experience` 등 |
| `ext:경로` | vault 밖. 실재하지만 링크할 수 없다 |
| `source_unknown: true` | **찾아봤고 없었다.** 「안 적었다」와 다르다 |

### 산문으로 적힌 출처를 갈라 넣는다 — 2026-08-31

`299 Principles` 86개 중 40개가 「원본」을 적어놨는데 **절반이 문서가 아니라 산문**
이었다. 그 20개를 갈라보니 한 종류가 아니었다.

| 갈래 | 개수 | 실체 | 값 |
|---|---|---|---|
| 1 | 3쯤 | **문서가 있는데 링크를 안 걸었다** — `A Philosophy of Software Design` 은 601에 있다 | `[[문서]]` |
| 2 | 13쯤 | **문서 없는 사건** — `E-Project 백엔드 테스트 최적화 (2026-04-29)` | **사건 문서를 쓴다.** 그 전까지는 `experience` |
| 3 | 4쯤 | **사건이 아니라 갈래** — 「실무 정립」·「실무 착안」 | `experience` |

**산문을 그대로 값에 넣지 않는다.** 문자열이 식별자가 아니라 인용문 한 문단인
경우가 있다 — `> - DuoAcademy (2026-07-30): 통합 테스트 61s. "SymPy가 느리다"는
가설을 프로파일로 **기각** …`. frontmatter 값으로 쓸 수 없다.

**갈래 2를 `experience` 로 두는 것은 되돌릴 수 있다.** 본문의 `> 원본:` 이 남아
있어, 사건 문서가 생기면 `[[문서]]` 로 바꾸면 된다. 사건 문서의 자리와 강제 시점은
볼트 쪽 숙제로 넘겼다 — `000 Index/Dots/ontology → vault TODO — 사건 문서와
프로젝트 관리`.

> **같은 사건이 원칙 여럿을 낳는다.** `E-Project 백엔드 테스트 최적화` 하나가 3개,
> `E-Project 모바일 통합 테스트 도입` 이 2개다. **문서 하나를 쓰면 여러 개가 한
> 번에 이어진다** — 사건 문서를 먼저 쓰는 것이 값이 큰 이유다.

`source_unknown`은 열린 세계 가정에서 **부재를 적극적으로 기록하는** 방법이다.
트리플을 안 쓰면 「모른다」지만 이 값을 적으면 「찾아봤고 없었다」가 된다.

## 5. 시점 — `as_of`

파일럿에서 대상이 **둘**로 갈렸다.

```
사건이 일어난 때        10번 2026-03-16 · 11번 2026-02-14
적은 때                 10번 2026-03-22 · 11번 2026-02-23
                        6일 차이            9일 차이
```

**둘 다 적는다.** `created`가 이미 「적은 때」이므로, `as_of`는 **사건이 일어난 때**로
정한다. 둘이 같으면 생략한다.

문서 안의 항목마다 시점이 다르면 frontmatter에 못 적는다 — sidecar 몫이다.
파일럿 8번에서 한 문서 안에 서로 다른 날짜가 **4개** 나왔다.

---

## 6. 안 하기로 한 것

- **본문 산문을 정본으로 삼지 않는다.** 관계 이름이 파서에서 사라진다
- **`inferred`를 문서에 적지 않는다.** 계산한다
- **`rejected`를 frontmatter에 적지 않는다.** sidecar의 작업 이력이다
- **새 앵커 문법을 만들지 않는다.** 13개 문서의 항목 번호를 그대로 쓴다
- **Obsidian block ID(`^abc123`)를 쓰지 않는다.** 편집 부담과 노이즈가 크고,
  이미 있는 항목 번호로 충분하다
