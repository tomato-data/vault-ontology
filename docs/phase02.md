# Phase 2 — 위키링크 파서

> 모듈: `vault/links.py` · scope: `links`

## 큰 그림

vault의 링크 24,969개는 **그래프 엣지의 압도적 다수**다 (답안지 실측: `links_to` 10,702 / 전체 12,266). Phase 1이 명시적 관계 387개를 읽었다면, 여기서는 나머지 전부를 읽는다.

산출물은 함수 셋.

```
strip_code(text)   →  코드블록·인라인 코드를 지운 텍스트
link_target(raw)   →  `[[...]]` 안쪽 문자열 → 링크 대상 이름
iter_links(text)   →  본문에서 링크 대상을 차례로 내놓는다
```

## 이전 Phase와의 연결

`split_frontmatter`가 준 **본문만** 본다. frontmatter의 `builds_on`을 위키링크로 또 세면 같은 관계가 두 번 들어간다 — 답안지 README의 함정 표에 「frontmatter 중복 / 링크는 본문만 본다」가 그것이다.

## 핵심 개념

### 1. 파싱 함정이 곧 통계 오류다

이 Phase의 함정들은 크래시를 내지 않는다. **조용히 숫자를 틀리게 만든다.** 그게 더 위험하다.

| 함정 | 잘못 세면 |
|---|---|
| 표 안의 `\|` | `[[문서\|별칭]]` 타깃 끝에 역슬래시가 남아 **멀쩡한 링크가 깨진 것으로** 잡힌다 |
| 코드블록 안의 `[[...]]` | 예제 코드가 **가짜 엣지**를 만든다 |
| 헤딩 앵커 `[[문서#절]]` | 같은 문서를 가리키는 링크가 **다른 노드로** 갈라진다 |
| 블록 참조 `[[문서^blockid]]` | 같음 |

실제 사고가 있었다. 스키마 정본에 이렇게 적혀 있다.

> 표 안의 이스케이프된 파이프 `\|`를 반드시 처리해야 한다. 안 하면 표로 정리된 인덱스 문서의 링크를 전부 깨진 것으로 세고, **반대로 그 링크가 가리키는 문서를 고아로 오판한다** (500 Mind Compiler를 45.7% 고아로 오측정한 원인).

하나의 파싱 실수가 두 개의 통계를 반대 방향으로 망가뜨렸다.

### 2. 위키링크 문법의 전체 모양

```
[[문서]]                    가장 단순
[[문서|별칭]]                별칭 — 화면에는 별칭이 보인다
[[문서\|별칭]]               표 안. 파이프를 이스케이프해야 표가 안 깨진다
[[문서#헤딩]]                문서 안의 절
[[문서#헤딩|별칭]]
[[문서^blockid]]            블록 참조
[[폴더/문서]]                경로 포함
![[문서]]                   임베드 — 링크이기도 하다
\[[문서]]                   이스케이프 — 링크가 아니다
```

**타깃은 첫 구분자 앞까지다.** `\|` → `|` → `#` → `^` 순서로 자른다. 순서가 중요하다 — `|`를 먼저 자르면 `\|`의 역슬래시가 남는다.

### 3. 코드를 지우는 것과 파싱하지 않는 것

코드블록 안의 `[[...]]`는 링크가 아니다. 두 가지 접근이 있다.

| 방법 | 문제 |
|---|---|
| 링크를 찾을 때 코드 안인지 판정 | 위치 계산이 얽힌다 |
| **먼저 코드를 지운 텍스트를 만든다** | 단순하다. **줄 번호가 보존돼야 한다** |

답안지는 후자다. 펜스 블록을 **빈 줄로 치환**한다 — 줄을 삭제하지 않는다. 나중에 "몇 번째 줄의 링크"를 보고할 수 있어야 하기 때문이다.
