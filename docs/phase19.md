# Phase 19 — 제한된 지식 운영

> 온톨로지의 결과를 실제 작업에 연결하되, 권한과 의미를 분리한다.

## 목표

온톨로지 기반 판단을 읽기 전용 보고서에서 가역적인 작업 제안으로 연결한다.
"무엇이 사실인가"를 정의하는 온톨로지와 "무엇을 실행해도 되는가"를 정의하는 정책은
별도 계층으로 유지한다.

초기 운영 후보:

- 폐기된 근거에 의존하는 문서 경고
- 원칙 변경의 영향 문서 목록 생성
- 누락된 evidence·relation 수정안 제시
- 중복·충돌 후보 검토 큐 생성
- 원칙 승격 후보의 초안 생성
- 개인 경험·철학과 개발·커리어 판단 사이의 검토 가능한 접점 제안

## Step 1 — 권한과 정책을 명시한다

각 작업에 다음을 둔다.

- 읽을 수 있는 경로
- 변경 가능한 파일과 필드
- 승인 필요 여부
- 예상 diff 상한
- 되돌리기 방법
- 감사 기록
- 실패 시 중단 조건
- 허용되는 Vault 대역과 민감도

온톨로지 공리로 파일 쓰기 권한을 표현하지 않는다.

## Step 2 — shadow mode로 시작한다

최소 2주 동안 실제 변경 없이 다음만 기록한다.

- 시스템이 제안했을 작업
- 제안 근거
- 토마토가 실제로 선택한 작업
- 오탐과 누락
- 예상 diff

shadow mode에서 유용성이 확인되지 않으면 쓰기 기능으로 넘어가지 않는다.

## Step 3 — preview와 승인 후 가역적 변경만 허용한다

초기 허용 범위는 작은 Markdown patch로 제한한다.

- 새 semantic relation 한 건 추가
- 상태 한 건 변경
- 검토 큐 문서 갱신

대량 rename·삭제·자동 merge는 범위 밖이다. 모든 변경은 diff를 보여주고 명시적으로
승인받으며 Git으로 되돌릴 수 있어야 한다.

## Step 4 — 의미 변경과 파일 변경을 함께 감사한다

한 작업에 다음을 묶는다.

```text
어떤 역량 질문에서 시작했는가
어떤 asserted/inferred 사실을 사용했는가
어떤 정책이 허용했는가
누가 승인했는가
어떤 Markdown/RDF diff가 생겼는가
어떻게 되돌리는가
```

## Step 5 — 운영 가치를 측정한다

- 실제로 처리한 검토 항목 수
- 승인된 제안 중 유효했던 비율
- 놓친 영향 관계 수
- 작업당 절약 시간
- 잘못된 변경과 복구 시간
- 4주 후에도 반복 사용했는가

## 산출물

- action policy
- shadow-mode 보고서
- diff preview·승인·적용·rollback 흐름
- provenance 기반 audit log
- 4주 운영 가치 평가

## 완료 조건

- [ ] 온톨로지와 실행 권한이 별도 계층이다.
- [ ] shadow mode에서 실제 유용성이 확인됐다.
- [ ] 자동 실행 없이 모든 변경을 preview할 수 있다.
- [ ] 승인된 작은 변경만 적용한다.
- [ ] 모든 변경이 감사 가능하고 되돌릴 수 있다.
- [ ] 4주 실제 사용에서 순효용이 확인됐다.
- [ ] 전 영역 적용이 사생활·관점·시점 맥락을 제거하지 않는다.

## 난이도와 위험

**난이도: 매우 높음. 기술적 완성보다 안전한 운영이 어렵다.**

Phase 1~9의 산출물은 파생 DB라 지우고 다시 만들면 됐다. Phase 19는 Markdown 정본에
영향을 줄 수 있다. 따라서 정확도뿐 아니라 권한·감사·rollback·diff 상한이 완료 조건이다.
유용한 읽기 전용 도구로 끝나는 것도 정당한 결론이며, 자동 쓰기는 필수 성공 조건이 아니다.
