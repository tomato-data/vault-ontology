# 역량 질문 — 1차 후보

> Phase 10 Step 1. 절차는 [`part3-decisions.md`](part3-decisions.md)의 D5.
>
> **상태: 1차 후보. 승인되지 않았다.** 판정(Step 2)과 전체 필드 작성(Step 3)은
> 아직이다.

## 규칙

- 모든 후보는 **근거 경로**를 단다. 경로 없는 후보는 목록에 못 들어온다.
- 등급 **A** 문서에 질문이 실제로 적혀 있음 · **B** 같은 판단이 반복됨 ·
  **C** 구조가 암시함. **D(지어낸 것)는 금지**.
- 사적 내용은 옮기지 않는다. 근거는 **경로만** 적고 인용하지 않는다 (D6).
- 삶의 질문이 아니라 **도구가 답해야 하는 질문**을 적는다.

## 진행

| | |
|---|---|
| 1차 후보 | **30개** |
| 승인 | 0 — 토마토의 판단을 기다린다 |
| 판정 완료 | **30 / 30** |
| 100 대역 | **0 — 토마토가 직접 써야 한다** (D4) |

> **목표를 40~50개에서 30개로 낮췄다.** 전수 판정 결과 30개 중 18개가 같은
> 갈래(작성 계약)로 떨어졌다. 더 캐도 같은 답이 반복될 뿐, 판단이 달라지지
> 않는다. 개수는 Phase 10의 완료 조건(20개 이상)을 이미 넘었다.

### 판정에서 배운 것

첫 판정(C12)이 **네 번째 결과**를 냈다. 판정 표는 세 갈래를 가정했다.

```
기존 도구로 된다        → 제외
관계 의미가 필요하다     → 온톨로지
값이 없다              → SHACL
```

실제로 나온 것은 **「그 사실이 vault에 기록되지 않는다」**였다. 어느 계층의 문제도
아니고, Phase 13의 작성 계약 문제다. 판정 갈래에 이것을 추가한다.

| 판정 | 뜻 |
|---|---|
| 기존 도구 | SQLite·grep으로 답한다. 3부 목표 아님 |
| 온톨로지 | 개체 종류와 관계 의미가 필요하다 |
| SHACL | 있어야 할 값을 검사한다 |
| 운영 규칙 | 상태 변경·재검토 판단이다 |
| Vector | 의미 유사 후보. 3부 범위 밖 |
| **작성 계약** | **그 사실을 적는 방법부터 없다. Phase 13 선행** |

## 200 Dev Knowledge Base — 원칙

### C04 · 이 원칙은 어떤 사건에 근거하는가?

- **근거 [A]** — `200 Dev Knowledge Base/209 Principles/`의 문서들이 전부 명령문이다. 「재현되지 않는 이슈는 추측으로 닫지 말고 관측 장치를 심어 장기 추적하라」 같은 문장은 **그런 일이 있었음을 함의**한다. 사건은 `400 Logic Forge/403 Case Studies/`와 `300 Runtime/`에 있다.
- **최소 입력** — 원칙 문서 경로
- **기대 답의 형태** — 사건 문서 목록 · 각 사건이 원칙의 어느 부분을 지지하는가 · 근거 위치

#### 실측 — 이 후보가 가장 강하다 (2026-08-25)

```
type: principle          94
  그중 case 를 가리키는 것   1     (1%)
type: case               31
  그중 principle 을 가리키는 것  1

principle 이 다른 문서에서 인용됨   81/94  (86%, hub 발 링크 제외)
```

**원칙은 널리 쓰이는데 근거는 적혀 있지 않다.** 94개 중 사례로 이어진 것이 한 개다.
「이 원칙은 어디서 왔는가」가 vault 안에 답이 없는 상태다. 3부가 겨냥할 자리다.

### C05 · 적용 사례가 하나도 없는 원칙은 무엇인가?

- **근거 [B]** — 실측하니 `principle` 94개, `case` 31개다. **원칙이 사례의 3배**이고, 둘을 잇는 링크는 1건뿐이다(C04 실측). 검증되지 않은 원칙이 섞여 있을 가능성이 구조적으로 있다.
- **최소 입력** — 없음 (전수)
- **기대 답의 형태** — 원칙 목록 · 각각에 연결된 사례 수 · 0인 것들
- **처음 셈이 틀렸다** — 「209 Principles 20개 이상 vs Case Studies 5개」로 적었는데, 폴더 목록 앞부분만 본 수였다. vault 전체로는 94 대 31이다.

### C06 · 서로 긴장하는 원칙이 있는가?

## 000 Index — 운영 지식

### C11 · 가이드라인끼리 모순되는 지점이 있는가?

- **근거 [A]** — `000 Index/Maintenance/가이드라인/`에 문서가 9개 있고, 갱신이 한쪽에만 반영된 일이 실제로 있었다. 2026-08-25에 태그 체계를 바꾸면서 여러 문서를 함께 고쳐야 했던 것이 그 증거다.

- **기대 답의 형태** — 모순하는 규칙 쌍 · 각각의 문서와 위치 · 최종 갱신 시점

### C12 · 폐기된 문서에 의존하는, 현재 유효한 문서는 무엇인가?

- **근거 [A]** — `000 Index/Maintenance/깨진 링크 전수조사 (2026-07-31).md`가 존재한다는 것 자체가 이 질문을 이미 물었다는 증거다.
- **최소 입력** — 없음 (전수)
- **기대 답의 형태** — 문서 목록 · 어떤 폐기 문서에 의존하는가 · 의존의 종류

#### 판정 — **기각.** 답할 수 없어서가 아니라 데이터가 없어서 (2026-08-25)

돌려본 결과다. 예상은 「SQLite로 이미 된다」였고, 틀렸다.

```
깨진 링크                   1,192건   links_to 중 dst 없음
supersedes 엣지                 5건
그 대상을 가리키는 링크           0건   ← 폐기 의존이 한 건도 없다
node 테이블의 상태 컬럼         없음   path·name·zone·dir·type·summary·created·bytes
```

「폐기된 문서에 의존한다」가 성립하려면 **폐기됐다는 상태가 어딘가 적혀 있어야**
한다. vault에는 그 상태가 없다. `supersedes`가 그 역할에 가장 가까운데 5건뿐이고,
그 5건의 대상을 가리키는 링크는 0건이다.

깨진 링크 1,192건은 「폐기된 문서에 의존」이 아니라 **「가리키는 곳이 없다」**다.
다른 질문이다.

**따라서 이 질문은 온톨로지 문제가 아니라 작성 계약 문제다.** Phase 13에서
「폐기」를 어떻게 적을지 정하기 전에는 어느 계층으로도 답할 수 없다. 그 계약이
생기면 다시 후보로 올린다.

> **부수 관측** — `vault lint`는 `link unresolved`를 368건으로 보고하는데 그래프는
> 1,192건이다. 3배 이상 차이 난다. 첨부 처리 규칙과 lint 제외 설정 중 무엇이
> 원인인지 확인하지 않았다. 별건으로 봐야 한다.


경고한 그 분리를, vault는 **디렉토리로 이미 하고 있다.** Phase 11·12의 설계는

표본으로 읽은 `601 Books/개발/A Philosophy of Software Design/Chapter 04 …`는
순수 필사였다. 저자의 주장만 있고 사용자의 반응이 없었다. **표본 하나다.**

## 구조적 공백 — 후보를 짜내지 않고 찾아낸 방법

지금까지 나온 좋은 후보가 전부 같은 모양이었다. **「A도 있고 B도 있는데 둘을
잇는 기록이 없다」**. 그래서 손으로 짜내는 대신 `type → type` 링크 행렬을 만들어
공백을 기계로 찾았다. hub 발 링크는 목록 나열이라 뜻이 없어 제외했다.

### 판단 타입 4종의 상호 연결

```
                                    양방향 링크 수
  decision  ←→ tradeoff                    140     ✅
  principle ←→ case                          5
  principle ←→ decision                      2
  decision  ←→ case                          1
  principle ←→ tradeoff                      0     완전 단절
  tradeoff  ←→ case                          0     완전 단절
```

```
다른 판단 타입과 전혀 안 닿는 문서
  principle    88 / 94   (94%)
  case         29 / 31   (94%)
  decision      2 / 45   ( 4%)
  tradeoff      1 / 44   ( 2%)
```

### 유일한 예외는 사람이 만든 관계가 아니다

decision ↔ tradeoff의 140건은 `000 Index/Templates/Decision Node Template.md`와
`Trade-offs Matrix Template.md`가 **짝으로 만들게 강제한 결과**다. 발견한 관계가
아니라 생성 규칙이다.

**즉 vault에는 사람이 발견해서 적어둔 판단 사이의 관계가 사실상 없다.**

### 그런데 시간축과 작업축으로는 이어져 있다

```
log         → principle 59 · decision 22 · tradeoff 22 · case 8
project-doc → principle 110 · decision 54 · tradeoff 19 · case 9
```

일지는 「언제 이걸 건드렸다」를, 프로젝트 문서는 「이 원칙을 따랐다」를 적는다.
**계보의 재료는 있는데 계보 자체가 안 적혀 있다.** 이것이 3부가 겨냥할 자리다.

### 관계 어휘의 실제 사용량

```
links_to     9,544    본문 위키링크. 방향은 있고 의미는 없다
builds_on      419    개념 선수과목. 200 내부가 91%. 최대 깊이 8
supersedes       5    전부 미해결 — 대상 문서가 없다
```

`builds_on`을 가진 문서는 295개(7.3%)이고, 그중 `principle`은 **1개**,
`decision`도 **1개**다. 근거를 나타내는 관계는 vault에 **없다.**
