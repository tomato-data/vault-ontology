# Phase 4 — 검증은 거부다

> 모듈: `vault/schema.py` · `vault/lint.py` · scope: `lint`

## 큰 그림

Phase 1~3이 읽는 쪽이었다면 여기는 **판정하는 쪽**이다. 스키마 정본의 제약을 코드로 옮기고, 위반을 검출하는 CLI를 만든다.

```
vault/schema.py    TYPES · SUMMARY_MAX · BUILDS_ON_MAX · validate()
vault/lint.py      vault 전체 순회 + 보고 + 종료 코드
vault/__main__.py  CLI 진입점 (argparse)
```

## 이전 Phase와의 연결

Phase 1~3의 함수를 처음으로 **전부 한자리에 모아** 쓴다. 여기서 코드가 실제로 도구가 된다.

## 핵심 개념

### 1. 경고는 무시된다

스키마 정본에 근거가 실측으로 적혀 있다.

> Phase 2에서 summary 80자 초과가 14% 나왔다. 프롬프트에 "80자 이내"라고 적었지만 **강제가 아니었기 때문**이다.

> hex 태그는 v2.37에서 청소했는데 다시 쌓였다. **규칙은 배출구를 못 이긴다.**

그래서 위반은 전부 **거부**다. 예외는 하나뿐 — 라우팅(`--dir` vs `--type`) 경고. 디렉터리와 타입의 대응이 완전하지 않기 때문이다.

### 2. 생성과 검사가 같은 함수를 쓴다

이 프로젝트의 설계 불변식이다.

```
vault new   → 검증 통과한 문서만 생성
vault lint  → 검증 실패한 문서 검출
                  ↑ 같은 validate()
```

따로 만들면 반드시 어긋난다. 공유하면 **"만든 것은 반드시 검사를 통과한다"**가 구조적으로 보장된다. (`vault new`는 이 로드맵의 범위 밖이지만, `validate()`를 그 전제로 설계한다.)

### 3. 검사할 제약 목록

| 규칙 | 근거 |
|---|---|
| `type`이 13값 밖 | 스키마 정본 |
| 판단 구간 타입인데 `summary` 없음 | |

### 4. 의도치 않은 태그 — 네 번 고친 검출기

본문에 `#` 뒤 공백 없이 영숫자가 붙으면 Obsidian이 **태그로 만든다.** hex 색상(`#6B4E8C`), 작업 번호(`#15`)가 대표적 오염원이다.

**이 넷은 태그가 아니다.** 하나씩 잘못 잡고 고쳤다.

```
[EC2](#ec2-elastic-…)   마크다운 링크 목적지
https://…#_oidc         URL 조각
#Stack/Python           사람이 다는 계층 태그 — 건드리지 않는다
#729651                 순수 숫자 — Obsidian은 태그로 만들지 않는다
```

그리고 **태그만 있는 줄은 통째로 사람의 태그 줄로 본다.** 태그는 유저가 직접 단다(CLAUDE.md 규칙 3).

검출기를 짤 때 "무엇을 잡을까"보다 **"무엇을 잡으면 안 되나"**가 어렵다. 오탐 하나가 사용자 문서를 망가뜨린다 — 실제로 에이전트가 `#729651`(포럼 글번호)을 이스케이프해 본문을 오염시킨 사고가 있었다.

### 5. 제외 규칙은 설정 파일로, 그리고 커밋한다

vault 루트의 `.vault-lint.json`이 정한다.

```json
{
  "sources": ["300 Runtime/301 Day Notes", "800 TRPG", "900 Archive"],
  "targets": ["...", "참조", "파일명"],
  "files":   ["000 Index/Templates/Daily Template.md"]
}
```

- `sources` — 여기서 나온 깨진 링크는 **고칠 오류가 아니라 당시를 가리키는 흔적**이다. Day Note가 끝난 일의 계획서를 링크하는 건 자연스럽다
- `targets` — 템플릿 자리표시자
- `files` — 파일 통째 제외

**이 파일은 커밋한다.** 무엇을 왜 뺐는지가 감사 대상이기 때문이다. 코드에 하드코딩하면 "왜 뺐는지"가 사라진다.

### 6. 종료 코드

```
0  이상 없음
1  위반 발견
2  사용법 오류
```

CI와 pre-commit 훅이 이걸 읽는다. `print`로만 보고하는 도구는 자동화에 못 넣는다.

### 7. 온톨로지와의 연결 — 미리 알아둘 것

여기서 쓰는 제약(`builds_on`의 대상은 문서여야 한다, `type`은 13값 중 하나)은 Phase 8에서 **RDFS/OWL로 다시 표현**하게 된다.

```
Phase 4    if t not in TYPES: reject()            명령형 · 코드
Phase 8    :type rdfs:range :DocumentType .       선언형 · 데이터
```

그리고 결정적 차이가 하나 있다. **Phase 4의 lint는 닫힌 세계 가정(CWA)**이다 — 없으면 위반. **OWL은 열린 세계 가정(OWA)**이다 — 없으면 모를 뿐, 위반이 아니다. 같은 제약을 적어도 결과가 정반대로 나온다. Phase 9에서 이 차이를 실제 데이터로 확인했다.

**지금은 그냥 명령형으로 짠다.** 대조본이 있어야 차이를 볼 수 있다.
