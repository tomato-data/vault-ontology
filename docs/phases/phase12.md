# Phase 12 — 의미 작성 계약과 기준 데이터

> 풍부한 어휘보다 먼저, 사람이 실제로 유지할 수 있는 입력 방식을 만든다.

> **전제** — 이 Phase는 [`phase11.md`](phase11.md)의 파일럿이 「감당 가능」
> 판정을 낸 뒤에만 시작한다. 문서당 시간·의미 단위·재라벨링 일치율이 이미 측정된
> 상태로 들어온다. 50개라는 수 자체가 파일럿 결과에 따라 조정될 수 있다.

## 왜 별도 Phase인가

현재 RDF 사실은 frontmatter·위키링크·경로에서 결정론적으로 나온다. 그러나
`supports`, `contradicts`, `derivedFrom`은 본문에 단어가 등장한다고 확정할 수 없다.
입력 계약이 없으면 온톨로지는 어휘만 있고 인스턴스가 없는 빈 설계가 된다.

Phase 12은 **어떤 의미 사실을 어디에 어떻게 적고 승인할지**를 정하고, 대표 문서
50개를 사람이 직접 라벨링하여 정답 집합을 만든다.

## Step 1 — 작성 방식 후보를 비교한다

| 방식 | 장점 | 위험 |
|---|---|---|
| frontmatter 확장 | 눈에 보이고 Git diff가 명확함 | 문서 단위 이상으로 세밀해지기 어렵다 |
| Obsidian block ID | 본문의 근거 위치를 직접 가리킴 | 편집 부담과 ID 노이즈가 생긴다 |
| 별도 sidecar | 본문을 깨끗하게 유지 | Markdown과 의미 데이터가 어긋날 수 있다 |
| 전용 semantic section | 사람이 읽고 편집 가능 | 문법과 파서가 새로 필요하다 |
| 외부 annotation store | 도구화가 쉽다 | Markdown 정본 원칙과 충돌할 수 있다 |

한 방식을 미리 고정하지 않는다. 5~10개 문서에 같은 사실을 각 후보로 표현해
수정성·가독성·diff·rename 내성을 비교한다.

## Step 2 — 명시 사실과 제안을 구분한다

최소 세 상태가 필요하다.

```text
asserted    사람이 명시하거나 승인한 사실
proposed    규칙·LLM이 제안했지만 미승인인 사실
inferred    asserted 사실과 공리에서 계산된 사실
```

제안을 확정 사실과 같은 frontmatter 필드에 바로 쓰지 않는다. 거절한 제안도 모델·
시점·이유와 함께 남겨 반복 제안을 막을 수 있어야 한다.

## Step 3 — Vault 전 영역에서 대표 문서 50개를 선정한다

문서 `type`과 Vault 대역을 동시에 층화한다. 한 축만 맞추면 개발 지식에 편향된
기준 데이터가 된다.

초기 50개 최소 대역 분포:

- 000 Index — 메타 원칙·가이드·운영 지식 3개
- 100 Private Log — 경험·성찰 6개
- 200 Dev Knowledge Base — 개념·원칙·절차 9개
- 300 Runtime — 프로젝트·커리어 경험과 판단 8개
- 400 Logic Forge — 결정·tradeoff 6개
- 500 Mind Compiler — 질문·철학·자기 해석 6개
- 600 Content Observatory — 외부 출처와 내 해석 4개.
  **601 Books의 챕터 필사 914개는 제외한다.** 저자의 말이지 내 주장이 아니다.
  604 YouTube(인용률 71%)와 602 Frames(31%), 책 대표노트에서 고른다
- 700 Life Stack — **할당 없음.** 실측 결과 이 대역은 판단이 아니라 사전이다
  (`reference` 111 · `concept` 51 · 철학 1). 밖으로 나가는 링크가 8개뿐이다.
  질문이 개별 문서를 지목하면 그때 들어온다
- 900 Archive — **밴드 할당 없음.** Phase 10의 질문이 이름으로 지목한 문서만
  들어온다 ([`part3-decisions.md`](../part3/decisions.md) D3). 0개일 수도 있다

700·600에서 뺀 자리는 **400 Logic Forge와 200 Dev Knowledge Base로 옮긴다.**
인용률이 각각 73%·47%로 가장 높고, `principle` 94개 중 근거 사례를 가리키는
것이 1개뿐이라 3부가 겨냥할 공백이 거기에 있다.

100 Private Log의 6개는 토마토가 직접 라벨링한다 (D4). Claude는 원문을 열지 않고
결과 annotation만 본다. 이 6개의 소요 시간을 따로 재둔다 — 나머지 44개와 비용
구조가 다르다.

최소 의미 분포:

- 사건·경험
- 주장·믿음·해석
- 결정·tradeoff
- 원칙·가치
- 절차·개념·외부 출처

정확한 수는 Phase 10 질문에 맞춰 조정하되, 개발 대역이 전체의 절반을 넘지 않는다.
적어도 10개는 다른 대역의 문서와 근거 있는 관계를 가진 사례로 고른다.

쉬운 문서만 고르지 않는다. 다음 난점을 일부러 포함한다.

- 한 문서에 여러 주장
- 서로 충돌하는 문서
- `supersedes` 관계
- 근거가 불명확한 원칙
- 문서 이동 또는 이름 변경 이력
- 같은 개념을 다른 용어로 표현한 사례
- 한국어와 영어가 섞인 사례
- 같은 경험을 과거와 현재가 다르게 해석한 사례
- 개인 가치가 개발·커리어 결정에 영향을 준 사례
- 기술 원칙과 삶의 철학이 보강하거나 긴장하는 사례

## Step 4 — 사람이 기준 그래프를 작성한다

각 문서에서 다음을 확정한다.

- artifact와 knowledge entity의 ID
- 표현된 주장·사건·결정·원칙·절차
- 관계와 정확한 근거 위치
- assertion 상태
- 기대되는 SHACL 위반
- 기대되는 추론과 질의 답

라벨링을 한 번에 끝내지 않는다. 일정 간격을 두고 10개 이상을 다시 라벨링해 자기
일관성을 확인한다. 기준 자체가 흔들리면 자동화 평가도 의미가 없다.

## Step 5 — annotation 비용을 측정한다

문서당 다음을 잰다.

- 최초 라벨링 시간
- 수정 시 갱신 시간
- 관계당 승인 시간
- 애매하여 보류된 비율
- 문서 독해를 방해하는 정도

50개조차 유지하기 어렵다면 전체 Vault 적용을 중단하거나 의미 단위를 더 거칠게
조정한다.

## 산출물

- `docs/semantic-authoring.md`
- 대표 문서 50개 manifest
- 사람이 승인한 gold graph
- 애매한 사례와 판정 근거 목록
- annotation 비용 측정 결과

## 완료 조건

- [ ] 의미 사실의 정본 위치가 하나로 정해졌다.
- [ ] asserted·proposed·inferred 상태가 섞이지 않는다.
- [ ] 모든 관계에서 원문 근거 위치로 돌아갈 수 있다.
- [ ] 50개 문서의 기준 그래프와 기대 답이 있다.
- [ ] 000~700 대역과 교차 영역 사례가 합의한 분포로 포함된다.
- [ ] 900 표본이 있다면 질문이 지목한 문서이고, archive 상태·시점을 보존한다.
- [ ] 100 대역 6개가 D4 규칙 아래에서 라벨링됐고 소요 시간이 따로 기록됐다.
- [ ] 반복 라벨링에서 치명적인 의미 불일치가 없다.
- [ ] 유지 비용이 실제 사용 가능한 수준이다.

## 난이도와 위험

**난이도: 매우 높음. 이전 Phase와 가장 다른 종류의 작업이다.**

파서 테스트에는 객관적인 정답이 있었지만 의미 라벨은 경계가 모호하다. 자동화보다
사람의 판단과 편집 경험이 병목이 된다. 라벨링 비용을 측정하지 않으면 전체 Vault에
적용한 뒤 유지할 수 없는 시스템을 만들 위험이 크다. 개인적 경험은 기술 문서보다
해석 변화가 잦으므로, "당시의 생각"과 "현재도 유효한 믿음"을 분리하는 비용도 잰다.
