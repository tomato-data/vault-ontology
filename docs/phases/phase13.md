# Phase 13 — 문서와 지식 개체의 분리

> `type: principle`인 파일과 실제 원칙은 같은 것이 아니다.

## 핵심 문제

현재 `v:Concept`, `v:Decision`, `v:Principle`은 모두 Markdown 문서의 유형이다.
3부에서 같은 이름을 실제 개념·결정·원칙에 재사용하면 다음 두 사실이 구분되지 않는다.

```text
문서를 다른 파일에 합쳤다
원칙 자체를 폐기했다
```

> 위는 **개명 전**의 문제 서술이다. Step 1에서 `v:ConceptDocument`처럼 바꿨으므로
> 지금은 재사용할 이름 자체가 없다.

문서는 표현물이고, 지식 개체는 문서가 표현하는 대상이다. Phase 13은 이 둘의
정체성과 수명 주기를 분리한다.

## 목표 모델

```text
KnowledgeArtifact          KnowledgeEntity
├── MarkdownDocument       ├── Concept
└── Section/Block          ├── Claim
                           ├── Event
document expresses ───────→├── Decision
                           ├── Principle
                           └── Procedure
```

이 그림은 방향이지 아직 확정 어휘가 아니다. Phase 10의 질문으로 필요한 것만 남긴다.

## Step 1 — 현재 클래스의 의미를 명시한다

기존 13개 `type`은 문서 역할로 보존한다. 기존 `v:Principle`을 조용히 실제 원칙
클래스로 바꾸지 않는다.

선택지를 비교한다.

1. 기존 클래스를 `PrincipleDocument`처럼 명시적으로 개명하고 호환 공리를 둔다.
2. 기존 문서 어휘 네임스페이스를 유지하고 지식 개체를 새 네임스페이스에 둔다.
3. 문서 `type`을 클래스 대신 역할 값으로 모델링한다.

선택 기준은 기존 RDF 소비자 호환성, 질의 명료성, 마이그레이션 비용이다.

### 결과 — 1번. 다만 호환 공리는 없다 (2026-08-26)

먼저 세 기준을 쟀다.

```
기존 RDF 소비자 호환성    .vault.ttl 을 읽는 코드 0곳       ← 기준이 비어 있었다
질의 명료성               v:Principle 은 「원칙」으로 읽힌다   개명 쪽
마이그레이션 비용          ttl 13줄 · rdf.py 1곳 · 테스트 4개  개명 쪽
                         의미 사실 0개 · 데이터 없음
```

**판정 기준 셋 중 하나가 실제로는 비어 있었다.** 「소비자를 깨뜨린다」가 2번을
택했던 유일한 근거였는데, 깨뜨릴 소비자가 없다. 남은 둘은 둘 다 1번이다.

문서 13종 전부에 `Document` 접미를 붙였다. 일부만 붙이면 어느 규칙이 적용된
이름인지 읽는 쪽이 알 수 없다.

```
concept  → ConceptDocument      log         → LogDocument
procedure→ ProcedureDocument    reflection  → ReflectionDocument
reference→ ReferenceDocument    project-doc → ProjectDocument   ← 예외
principle→ PrincipleDocument    tradeoff    → TradeoffDocument
decision → DecisionDocument     capture → CaptureDocument
case     → CaseDocument         hub         → HubDocument
                                template    → TemplateDocument

> **2026-08-26 갱신.** `template`은 값이 없어졌고 `review`가 들어왔다
> (`v:ReviewDocument`). 위는 개명 당시의 13종이다.
```

`project-doc`만 예외다. 기계적으로 붙이면 `ProjectDocDocument`로 말을 더듬는다.

**호환 공리는 두지 않았다.** Step 1의 1번은 「개명하고 호환 공리를 둔다」였지만,
`v:PrincipleDocument owl:equivalentClass v:Principle`을 두면 Phase 9의 OWL RL
닫힘이 모든 문서를 다시 `v:Principle`로 타입한다. **없애려던 모호함이 추론
그래프에서 되살아난다.** 접미 없는 이름은 비워둔 채로 둔다 — 그것이 Step 2 이후
지식 개체가 쓸 이름이다.

검증:

```
테스트           241 passed          이름만 바뀌고 의미는 그대로다
.vault.ttl       재생성 · 문서 4,021개 전부 새 이름 · 옛 이름 0
OWL RL 닫힘      PrincipleDocument 94 → Content 2,570 → Document 4,021
                 v:Principle 0 · v:Concept 0
```

## Step 2 — 의미 개체의 최소 단위를 정한다

다음 사례를 모두 표현할 수 있어야 한다.

- 한 문서에 주장 세 개가 있다.
- 같은 개념을 여러 문서가 설명한다.
- 한 원칙 문서 안에 원칙과 예외가 함께 있다.
- 문서가 이동하거나 이름이 바뀐다.
- 문서 두 개가 하나로 합쳐지거나 하나가 둘로 나뉜다.
- 같은 문장을 다듬었지만 주장의 정체성은 유지된다.

문장 해시만으로 ID를 만들면 문장 수정 시 정체성이 바뀐다. 파일 경로만 쓰면 이동과
분할을 견디지 못한다. 최소 단위와 ID 수명 주기를 함께 정해야 한다.

### 결과 — 문서. 필요한 데서 제목까지 내려간다 (2026-08-26)

**「최소 단위를 제목으로 바꾼다」가 아니다.** 기본은 문서고, 항목이 독립적으로
존재하는 문서에서만 제목 단위로 내려간다.

```
4,185개 (98.8%)   문서 하나가 한 덩어리. 나눌 것이 없다
   49개 ( 1.2%)   번호 붙은 항목 제목이 3개 이상 · 항목 합계 320
```

파일럿은 이 모집단을 13개 문서 147항목으로 봤다. `인사이트` 계열만 셌기 때문이다.
`패턴`·`교훈`·`사례`·`원칙`·`규칙`까지 넣으면 **49개 320항목, 3.7배**다.

#### 왜 제목인가 — 블록 ID를 실측이 지웠다

Obsidian은 하위 앵커를 둘 지원한다. 둘 다 후보였다.

```
[[문서#제목]]        vault 사용 실적  67건 · 31개 문서
[[문서#^블록ID]]      vault 사용 실적   0건
^블록ID 정의          vault 전체        1건  (사고로 보인다)
```

블록 ID가 한 단계 더 아래 단위다 — 제목이 여는 절 전체가 아니라 문단 하나를
집는다. 더 정밀하지만 **문단마다 손으로 붙여야 하고, 6개월간 한 번도 안 붙었다.**

제목은 반대다. 이미 쓰이고 있고, **그 49개 문서의 항목은 애초에 제목으로 쓰여
있다.** 앵커를 새로 만들 필요가 없다.

```markdown
### 인사이트 1: 코드 품질 = 성능 + 유지보수성
### 인사이트 3: TDD 자동화 = 학습 효율
```

#### 무엇이 달라지는가

같은 파일 안의 서로 다른 두 항목에서 나온 노트 둘이 있다고 하자.

```
문서 단위   <TDD노트>     derived_from  <doc/_Insights>       ┐ 같은 리소스
           <아키텍처노트>  derived_from  <doc/_Insights>       ┘

제목 단위   <TDD노트>     derived_from  <doc/_Insights#인사이트 3>   ┐ 다른 리소스
           <아키텍처노트>  derived_from  <doc/_Insights#인사이트 1>   ┘
```

문서 단위에서는 「근거가 뭐냐」의 답이 **19개짜리 파일**이다. 관계는 남지만 사람이
다시 찾아야 한다. 파일럿 8번이 「잃는 것은 링크가 아니라 출처다」로 잡은 것이 이것.

#### 번호의 안정성 — 정책이 아니라 실적이다

```
_Insights 6개 문서 · 항목 119개 · 커밋 13~16회 · 2026-02 ~ 2026-08

번호가 사라진 적    0회
제목이 바뀐 적      0회
전부 추가뿐
```

번호를 고정하겠다고 정한 적이 없는데도 6개월간 순수 append-only였다. 문장 해시가
못 지키는 「같은 주장을 다듬어도 정체성 유지」를 항목 번호는 지킨다.

#### 문장·주장 단위는 만들지 않는다

앵커가 없다. 문장 해시는 편집에 부서지고, 줄 번호는 그보다 더 부서진다
(`500/Q7/_Patterns.md`가 실제로 `[[문서]] 4행`으로 가리키고 있다 — 가장 취약한 사례).

#### 코드로는 한 곳이다

```python
# vault/links.py:18 — 지금은 # 에서 잘라 항목 정보를 버린다
for separator in ("\\|", "|", "#", "^"):
    target = target.split(separator, 1)[0]
```

vault에 이미 있는 `[[문서#제목]]` 67건이 전부 여기서 문서로 뭉개진다. Phase 15에서
`#` 뒤를 살려 별도 리소스로 만든다. Step 2는 **그렇게 한다는 결정까지**다.

## Step 3 — 안정 ID 정책을 실험한다

후보:

- Markdown frontmatter의 명시적 ID
- Obsidian block ID
- 섹션 anchor + 문서 ID
- 별도 sidecar manifest
- 승인 시 발급하는 불투명 ID

평가 시나리오:

```text
rename document
move document
edit claim text
split document
merge documents
delete artifact but retain knowledge entity
```

각 시나리오에서 어떤 IRI가 유지되고 어떤 provenance 이벤트가 생기는지 테스트한다.

### 결과 — 새 ID를 만들지 않는다. wikilink가 ID다 (2026-08-26)

#### 문제가 계획이 상정한 것보다 작다

```
.vault.ttl 은 vault rdf 를 돌릴 때마다 통째로 새로 만든다
→ 저장돼 있는 IRI가 없다
→ 경로가 바뀌어도 매달려 있다 끊어질 참조가 없다
```

vault 밖에 남는 참조가 없다. 살아남아야 하는 유일한 참조는 **vault 안에 사람이 쓴
`[[문서]]`** 뿐이고, 그건 Obsidian이 관리한다. 그래서 질문이 좁아진다.

```
✗  새 ID를 무엇으로 발급할 것인가
✓  의미 사실이 가리키는 대상을 무엇으로 적을 것인가
```

#### 개명은 아무도 안 가리키는 문서에 일어난다

```
파일명이 바뀐 사건        555건 (전체 이동 9,890 중 5.6%)
전 기간 흩어 뽑은 표본     93건

  가리키는 링크가 있었다    12   12.9%
     └ Obsidian이 고쳤다    4
     └ 깨진 채로 남았다      8
  가리키는 링크가 없었다    81   87.1%
```

`Untitled`·날짜 이름·스터디 초고 같은 것들이다. **참조되는 지식 문서는 거의 개명되지
않는다.**

> 신뢰도 주의. 깨진 8건 중 `[[Untitled]]` 97곳짜리는 오탐이다 — grep이 앞부분만
> 맞춰 `[[Untitled 2]]` 같은 다른 파일까지 셌다. 12건은 표본으로도 작다.
> **「Obsidian이 1/3만 고친다」는 믿지 않는다. 믿는 것은 87.1% 쪽이다.**

#### 후보 다섯의 실측 결과

```
Obsidian 블록 ID          사용 0건               ← Step 2에서 탈락
frontmatter 명시 ID       vault에 id 필드 없음
                         212개 문서는 frontmatter 자체가 없다 (900 Archive)
별도 sidecar manifest     경로로 가리켜야 한다 → 이동 9,890번에 전부 깨진다
불투명 ID (승인 시 발급)    시간축 기록이 생길 때 필요. 지금 데이터 0개
섹션 anchor + 문서         ← 이것. Step 2가 고른 형태
```

#### 대신 세 가지를 건다

**1 · 중복 이름은 경로로 한정한다.**

```
이름이 겹치는 것   43개 이름 · 파일 194개 (4.6%)
   17  SKILL       16  Hub       15  Worklog       7  _Insights
```

`_Insights` 7개가 중복인데 **Step 2에서 고른 바로 그 문서들이다.** 그래서 이 49개
문서는 `[[_Insights#...]]`가 아니라 `[[Q1. Better Developer/_Insights#...]]`로 적는다.

**2 · 의미 사실의 깨짐은 본문 링크보다 강하게 잡는다.**

```
frontmatter 링크     427건   못 찾음    44   10.3%
본문 링크         11,749건   못 찾음 3,969   33.8%
```

본문 링크가 깨지는 것은 감수한다 (첨부·이미지가 섞여 실제보다 부풀려진 수치다).
**의미 사실이 깨지는 것은 감수하지 않는다.** `lint`에 별도 규칙으로 단다.

**3 · 불투명 ID는 Phase 19로 미룬다.**

「문서는 지웠는데 지식 개체는 남긴다」는 wikilink로 못 한다. 파일이 없으면 링크가
끊긴다. 그런데 그것이 필요해지는 때는 제안·승인 기록이 시간축을 가질 때이고, 그건
보류된 Phase 19다. 지금 만들면 쓸 데가 없다.

## Step 4 — IRI와 네임스페이스 계약을 정한다

최소한 다음 공간을 구분한다.

- 문서·섹션 같은 산출물
- 개념·주장·사건·원칙 같은 지식 개체
- 어휘와 공리
- 제안·승인·추론 활동

현재 path 기반 `doc_iri`는 문서 그래프의 호환 경로로 남길 수 있다. 새 지식 개체의
ID까지 path 기반으로 만들지는 않는다.

### 결과 — 섹션만 새로 만든다 (2026-08-26)

#### 지식 개체 공간은 만들지 않는다

Step 1은 「접미 없는 이름을 지식 개체 몫으로 비워둔다」고 했고 Step 3은 「새 ID를
만들지 않는다」고 했다. 부딪히는지 실측했다.

```
대상 없는 링크                     826개 이름 · 1,135건
3개 이상 문서가 가리키는 미작성 대상    34개
```

그 34개도 대부분 TRPG 세계관 미작성분(`2-1 연금 백과사전`)이거나 스킬 디렉터리
이름(`vault-new` — `.md`가 아니다)이다. **문서 없이 떠다니는 지식 개체가 사실상
없다.** 지식 개체는 항상 어딘가에 적혀 있고 그 자리가 정체성이다. 안 부딪힌다.

> 이 측정은 처음에 틀렸었다. `index`를 손으로 만들면서 NFC 정규화를 빼먹어
> 1,399개 이름 / 3,138건이 나왔다. Phase 3이 잡았던 그 함정이다. `vault.scan`을
> 그대로 쓰자 826 / 1,135로 줄었다. **직접 만든 index는 다시 만들지 않는다.**

#### 섹션 IRI는 fragment 로 한다

```
A  fragment       <doc/…/_Insights#인사이트 3: TDD 자동화 = 학습 효율>   ← 이것
B  별도 네임스페이스  <section/…/_Insights%23인사이트 3: …>
C  경로 세그먼트     <doc/…/_Insights/인사이트 3: …>
```

B는 `#`을 `%23`으로 묶어야 해서 읽기만 나빠지고 얻는 것이 없다. C는 위험하다 —
`X.md`와 `X/` 폴더가 공존할 수 있는 vault에서 문서 IRI 뒤에 `/`를 붙이면 폴더
IRI와 충돌한다.

A는 웹 표준 그대로다. fragment가 리소스의 일부를 가리키고 `[[문서#제목]]`과 1:1이다.
`ESCAPES`는 `#`을 `%23`으로 바꾸므로, **구분자 `#` 하나만 이스케이프에서 빼고 제목
안의 문자는 그대로 이스케이프한다.**

#### 앵커는 정본을 쓰되 링크는 번호만으로도 닿는다

```
IRI     문서에 실제로 적힌 제목 전체        문서에서 뽑는다. 정본
링크    [[doc#인사이트 3]]                 이것도 찾아간다
        [[doc#인사이트 3: TDD 자동화 = 학습 효율]]
```

Step 2가 남겨둔 「제목을 수정하면 앵커가 깨진다」의 답이다. `resolve_link`가 경로에
이미 베푸는 관용과 같은 종류다.

**앞부분 일치로 하면 안 된다.**

```
[[doc#인사이트 1]]  →  인사이트 1: 코드 품질 …
                      인사이트 10: …          ← 둘 다 걸린다
```

앞부분이 아니라 **첫 `:` 앞부분과의 정확 일치**다. `인사이트 1` ≠ `인사이트 10`.

#### 조용한 실패를 미리 잡았다 — isPartOf 를 쓰면 안 된다

```turtle
dcterms:isPartOf rdfs:range v:Folder .     # 이미 vault-ontology.ttl 에 있다
```

```
<섹션> dcterms:isPartOf <문서>
   → 추론기가 <문서> a v:Folder 를 만든다
```

**Phase 9가 폴더 764개를 Document로 잘못 타입했던 것과 같은 사고다.** 그때는 domain
때문이었고 이번엔 range다.

> **2026-08-26 정정.** 여기서 새 속성 `v:section_of`를 만들기로 했으나 Phase 14
> Step 2가 뒤집었다. 방향을 뒤집어 **`dcterms:hasPart`** 를 쓴다 — dcterms를
> import 하지 않으므로 외부 공리가 없고, `rdfs:range v:Section` 지역 선언 하나로
> 섹션이 자동 타입된다. 표준으로 되는 일에 로컬 어휘를 만들지 않는다.

#### 네 공간의 계약

```
산출물        doc:        문서                       있다
             doc:…#제목   섹션                       ← 새로 만든다
             folder:      폴더                       있다
             tag:         태그                       있다
지식 개체      별도 공간을 만들지 않는다                 실측 근거 (위)
어휘·공리      v:                                    있다
제안·승인·추론  만들지 않는다                           Phase 19 보류 (D2)
```
