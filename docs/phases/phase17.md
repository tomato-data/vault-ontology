# Phase 17 — 목적 제한 추론과 운영 규칙

> 트리플 증가량이 아니라 새 역량 질문으로 추론의 가치를 판정한다.

## 핵심 구분

모든 파생을 OWL에 넣지 않는다.

| 종류 | 예 | 구현 후보 |
|---|---|---|
| 형식 의미 | 하위 클래스, 역관계 | RDFS/OWL |
| 그래프 경로 | 사건 → 주장 → 원칙 → 절차 | SPARQL property path/CONSTRUCT |
| 검증 | 원칙에 근거가 없음 | SHACL |
| 운영 판단 | 폐기 근거에 의존하므로 재검토 | 명시적 rule/SQL/SPARQL |
| 검색 후보 | 내용이 비슷함 | Vector 외부 축 |

운영 상태는 시간이 지나며 철회될 수 있다. OWL의 단조 추론만으로 `NeedsReview`를
영구 사실처럼 물질화하지 않는다.

## Step 1 — 질문에 연결된 규칙만 선정한다

초기 후보:

- 무효화된 주장에 근거한 원칙을 재검토 후보로 계산
- 사건 → 주장 → 원칙 → 절차의 계보 계산
- 서로 모순되는 주장에 의존하는 결정 표시
- 선행 조건을 따라 실행 준비 상태 계산
- 원칙 변경의 절차·프로젝트 영향 범위 계산
- 개인 경험에서 나온 가치가 개발·커리어 결정에 미친 계보 계산
- 서로 다른 영역의 원칙이 같은 사건을 보강하거나 긴장시키는 지점 계산

각 규칙은 하나 이상의 Phase 10 질문을 새로 통과시켜야 한다.

### 후보 일곱을 재니 셋이 0건이었다 (2026-08-31)

```
R1  무효화된 근거에 선 원칙 (C03·C30)        0
R2  사건 → … → 원칙 계보 2단 (C04·C28)      0
R3  모순되는 근거에 선 결정 (C03·C06)         0
R4  builds_on 2단 사슬 (C11)            253
R5  이 원칙을 적용한 것들 (C21·C29)            2
R6  개인 → 기술 계보 (C09·C15)               5
R7  같은 근거를 공유하는 원칙 쌍 (C05·C06)        5
```

**Phase 17이 앞세운 세 규칙이 아무것도 못 답한다.** 왜인지가 이 Step의 답이다.

#### 의미 그래프는 사슬이 아니라 평평하다

```
의미 엣지 159 · 노드 275
   나가는 사슬 깊이 0    138   잎
                  1    133
                  2      4
   중간 노드(들어오고 나가는)  5 / 275

비교 — builds_on 엣지 433 · 중간 노드 94
```

**275개 노드 중 5개만 중간에 선다.** 133개 문서가 138개 출처를 가리키는 이분 그래프에
가깝고, `derived_from`이 151건이라는 숫자는 **151개의 따로 노는 한 홉**이다.

`contradicts`가 1건이라 R1·R3은 재료 자체가 없다.

#### R2는 규칙이 맞고 좁힌 곳이 틀렸다

클래스 조건(`?p a v:PrincipleDocument`)을 빼니 **2홉 사슬이 8개** 나왔다.

```
Decision Node - JWT vs Session  →  Trade-offs - JWT vs Session  →  인증 방식 벤치마크
Decision Node - Pragmatic vs Clean  →  Trade-offs - Pragmatic vs Clean  →  Conclusion
Decision Node - Live Activity 종료 폴링  →  Trade-offs - Celery vs APScheduler  →  앱 강제 종료 시 …
모든 정답은 일시적이다  →  이방인의 뫼르소와 나  →  2026.01.25 다양한 가능성과 변화
```

**앞의 셋이 C02를 글자 그대로 답한다** — 「이 결정의 근거가 된 tradeoff와 출처는
무엇인가」. 계보는 원칙이 아니라 **결정**에 있었다.

넷째는 다른 종류다. `informed_by → derived_from`으로 **개인 일기에서 성찰을 거쳐
철학적 입장까지** 이어진다. C09·C15가 묻던 교차 영역 계보이고, **어떤 단일 질의도
이걸 답한 적이 없다.**

### 남긴 규칙 넷

| 규칙 | 답하는 질문 | 결과 |
|---|---|---|
| `genealogy` | C02 · C04 · C09 · C15 | 사슬 163 (2홉 8) |
| `impact` | C21 · C29 · 「이걸 고치면 뭐가 영향받나」 | 2 |
| `shared_ground` | C05 · C06 | 묶음 14 |
| `invalidated` | C03 · C30 | **0** |

**`invalidated`를 0건인데도 남겼다.** `answered_by`를 죽이고 `violates`를 뺐던 것과
다른 경우다 — 저 둘은 **질문 자체가 vault의 구조와 안 맞았고**, 이건 규칙이 맞는데
`contradicts`가 1건이라 재료가 얇다. 그 차이를 코드 주석에 적어 뒀다.

`builds_on`은 의미 관계에서 **뺐다.** 253개 사슬이 나오지만 그건 「읽는 순서」이지
「근거의 사슬」이 아니다. 섞으면 목차가 계보 행세를 한다.

교차 영역 관계는 의미 유사성만으로 추론하지 않는다. 공통 단어, Vector 점수, 같은
태그만으로 `informs`·`motivates`·`contradicts`를 확정하지 않고, 승인된 assertion이나
명시적인 관계 경로가 있을 때만 운영 판단에 사용한다.

## Step 2 — asserted와 derived를 분리한다

- 규칙 입력은 승인된 asserted graph만 사용한다.
- 결과는 inferred/derived graph에 쓴다.
- 규칙 ID와 버전, 사용한 입력 assertion을 기록한다.
- 입력 철회 시 결과를 전부 재계산할 수 있어야 한다.
- 결과를 Markdown에 자동 기록하지 않는다.

## Step 3 — 설명 가능한 derivation을 만든다

결과만 반환하지 않는다.

```text
원칙 P08 — 재검토 후보
  because Claim C31 was invalidated by Evidence S19
  P08 derivedFrom C31
  Procedure R12 operationalizes P08
```

각 결과에서 사용한 관계 경로와 원문 근거를 재구성할 수 있어야 한다.

## Step 4 — 무추론 기준선과 비교한다

각 질문을 세 방식으로 비교한다.

1. 원본 asserted graph 질의
2. query-time path/rule 계산
3. materialized inference

정답, 설명 가능성, 갱신 비용, 실행 시간을 비교한다. Phase 9처럼 질의 시점 계산이
충분하면 물질화하지 않는다.

### 세 방식 실측 (2026-08-31 · `tools/measure_phase17.py`)

```
① 원본 asserted 1홉 질의     0.00s   151쌍 — 중간 문서를 못 돌려준다
② query-time 걷기          0.00s   사슬 163 · 2홉 이상 8
③ OWL RL 물질화           15.28s   트리플 80,018 · derived_from 151
```

**③이 트리플을 51,582개 더 만들고 `derived_from`은 한 건도 못 늘렸다.**
`v:derived_from`은 `prov:wasDerivedFrom`의 하위 속성일 뿐 이행적이지 않아서,
닫힘이 `prov:wasDerivedFrom` 151건과 타입 정보를 복사할 뿐 사슬을 안 만든다.

**Phase 9의 결론이 의미 계층에서 그대로 재현됐다.** 2.81배가 이번엔 2.81배이고,
새로 답해지는 질문은 0개이며, 걷기는 0.00초다.

②만이 **중간 문서를 돌려준다.** ①은 「A가 C에서 나왔다」까지고, C02가 요구하는
「무엇을 거쳐서」는 경로를 들고 있어야 나온다.

**그래서 아무것도 물질화하지 않는다.** 규칙은 전부 질의 시점에 돈다.

## Step 5 — 부정·철회·시간을 시험한다

필수 fixture:

- 근거가 나중에 복구됨
- 모순 주장이 해결됨
- 제안이 거절됨
- 원칙이 supersede됨
- 같은 규칙을 두 번 실행함
- 이전 ontology/rule 버전의 결과가 남아 있음

## 산출물

- 역량 질문에 연결된 규칙 세트
- rule ID·version·provenance
- query-time과 materialization 비교 보고서
- derivation explanation
- 철회·재계산 테스트

## 완료 조건

- [ ] 최소 한 개 이상의 기존 불가능 질문을 정확히 답한다.
- [ ] 모든 파생 결과에 설명 경로가 있다.
- [ ] 입력 철회 후 낡은 결과가 남지 않는다.
- [ ] OWL·SHACL·운영 규칙의 책임이 섞이지 않는다.
- [ ] 개인 관점과 시점을 제거한 전역 사실을 새로 만들지 않는다.
- [ ] 단순 질의로 충분한 파생을 불필요하게 물질화하지 않는다.
- [ ] 성능보다 정답과 유지 비용을 함께 측정했다.

## 난이도와 위험

**난이도: 매우 높음. Phase 9보다 논리 종류와 시간축이 늘어난다.**

Phase 9 추론은 단조적이었다. 사실을 더하면 결과도 늘었다. 운영 판단은 근거가
철회되거나 상태가 바뀌면 결과를 없애야 한다. 이 비단조성을 OWL에 억지로 넣으면
낡은 경고가 남거나 원인을 설명하지 못한다. 규칙과 상태를 명시적 산출물로 다루어야 한다.

### 왜 walk 이고 SPARQL property path 가 아닌가

`?a v:derived_from+ ?b`는 **쌍을 주고 경로를 버린다.** Step 3이 요구하는 것이 정확히
그 버려지는 부분이라, 규칙은 Python 걷기로 썼다. 성능이 이유가 아니다 — 둘 다
0.00초다.
