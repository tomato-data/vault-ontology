# 채택 — 지금 한다

## D · 스키마 변경 「클래스 × 범위」 분류표 ★

> T4: *"CLAUDE.md가 v2.45까지 오는 동안 스키마가 여러 번 바뀌었고, 그때마다
> 마이그레이션 규모를 **즉흥 판단**했을 것이다."*

**맞다. 지난주에만 네 번 했고 매번 그때 판단했다.**

| 무엇 | 클래스 | 범위 | 실제 작업 |
|---|---|---|---|
| 문서 클래스 13개 개명 (`v:Principle`→`v:PrincipleDocument`) | C1 동의어 | 전역 | 기계적. **데이터 0개라 공짜였다** |
| `rdfs:domain` 11개 삭제 | C5 분할·병합 | 전역 | **추론 결과가 바뀜.** 오타이핑 27개 해소 |
| `template` 값 제거 | C5 분할·병합 | **14문서** | 전 문서 재판정을 안 했다 — **경로가 범위를 좁혔다** |
| `review` 값 추가 | C3 Key 추가 | **141문서** | 판정 필요. 실측이 대상을 정했다 |

**세 번째가 판정표에 축을 하나 더 요구한다.** C5는 원래 「전역 재판정」인데 실제로는
14개였다. 범위를 좁혀준 것은 **경로 규칙**이었다.

```
클래스 × 범위 × 「범위를 좁혀주는 구조가 있는가」
```

vault에서 범위를 좁히는 구조는 셋이다 — **경로**(`000 Index/Templates/`),
**파일명**(`*Template*`), **frontmatter 값**(`type:`). 셋 중 하나가 대상을
결정론적으로 집어내면 C5도 전역이 아니다.

**산출물**: [`schema-change-impact.md`](schema-change-impact.md) — 표 한 장.
실사례 4건으로 채운다.

## M · coverage 측정 — 부착률·채택률·기각률

> T4: *"CLAUDE.md 규칙 3이 이미 selective prediction이다. 그런데 커버리지가
> 얼마인지 측정하지 않는다."*

**안 재고 있다.** 오늘도 태그를 하나 붙였고(`Stack/AI-Ops`) 보고는 했지만,
세션이 끝나면 숫자가 남지 않는다.

**볼트판으로 옮기면 태그가 아니라 관계가 대상이다.**

```
관계를 붙인 문서 / 만든 문서            부착률
제안 → 승인                            채택률
제안 → 기각                            기각률   ← 높으면 어휘가 부족하다는 뜻
```

**기각률이 A(잔차)로 이어진다** — T4가 짚은 연결이 관계 어휘에서도 그대로 성립한다.

**적용**: 볼트의 `000 Index/Dots/의미 라벨 5일 관찰 — 신규 작성 비용.md` 기록 블록에
세 숫자를 추가한다. **비용 0** — 이미 세고 있는 것을 적기만 하면 된다.

> 파일럿에서 이미 한 번 쟀다. 라벨 48개를 소급 분류하니 **asserted 11 · proposed 37(77%)**
> 이었다. 그게 M의 첫 측정이었는데 이름을 안 붙였다.

## C · 판별력 — 다만 태그가 아니라 `type` 에

> T4: *"값이 전부 같은 Key는 정보량 0이라 필터로 못 쓴다."*

**원안(태그)보다 `type`에서 더 잘 듣는다. 오늘 실제로 통했다.**

```
2026-08-26 이전   600 안에서 capture   1,252 / 1,258      판별력 ≈ 0
                                                            그 구역에서 아무것도 안 가른다
review 신설 후                capture 1,119 · review 141
```

`review`를 만든 판단이 사후적으로 **판별력 회복**이었다. 그때는 그 이름을 몰랐다.

**주의 — T4의 P3-c도 함께 가져온다.** 판별력 0인데 그래도 필요한 값은
「속성이 아니라 그 묶음의 정의」다. `601 Books` 안에서 `capture`가 946/1,052인 것은
**결함이 아니라 601의 정의**다. 삭제가 아니라 **디렉토리 경계 문제**로 읽어야 한다.

**적용**: 코드로 만들지 않는다. **스키마 변경을 판단할 때 쓰는 진단 절차**로 D의
판정표 옆에 적어둔다. 상시 명령이 될 만큼 자주 쓰지 않는다.

## A · 잔차 — 원안은 기각, 변형은 채택

**원안(태그 어휘 확장 신호)은 기각한다.** 전제가 정본과 부딪힌다.

> 스키마 정본: **「태그 체계는 유지·검수만 한다. 새 축을 태그로 만들지 않는다.」**

「언제 태그를 늘려야 하는지 알려주는 신호가 없다」는 지적은 맞지만, **늘리지 않기로
이미 정했다.** 신호를 만들면 정해둔 억제를 흔든다.

**변형은 채택한다 — 관계 어휘의 잔차.** 이건 이미 관측되고 있다.

```
5일 관찰 1일차:  「영상이 밖에서 공명시킨다」
                 derived_from 도 informs 도 아니다 — 셋 다 말이 된다
Phase 14 Step 1: 「패턴」 135항목을 요구하는 역량 질문이 없다 (기록된 공백)
```

**둘 다 「현재 어휘로 설명되지 않는 덩어리」다.** 임베딩이 필요 없다 — 5일 관찰의
로그가 곧 잔차 표본이다. **2라운드 연속 새 덩어리가 없으면 어휘가 덮고 있다**는
T4의 종료 조건을 그대로 쓴다.

# 조건부 — 재고 나서 정한다

## N · 상태 계약 — 이미 돌고 있다. 스키마 밖에서

T4가 짚은 빈 자리는 정확했다. 우리 상태 4개는 전부 「이 문서/사실이 **어떤가**」이고
「다음 공정이 **먹어도 되는가**」를 말하지 않는다.

**그런데 실측하니 계약이 이미 있었다. `elevate:` 블록 안에.**

```
elevate 블록을 가진 문서   102   전부 300 Runtime
   verdict: promoted      66
   verdict: skip          11
   verdict: merged         4
   verdict 없음            21    touched 만 — 검토 대기
   pending: true            0    문서화됐지만 한 번도 안 쓰임
```

`monthly-elevate`가 `touched > reviewed` 한 줄로 소비 가부를 판정한다. **작동한다.**

### 그래서 남는 질문은 다르다

```
✗  상태 계약을 만들 것인가
✓  이미 도는 계약을 스키마가 알아야 하는가
```

지금 상태:

| | |
|---|---|
| 스키마 정본 | `elevate:`를 **모른다.** 필드 목록에 없다 |
| `vault/schema.py` | 검증하지 않는다 |
| `vault-ontology.ttl` | 모델하지 않는다 |
| 적용 범위 | **300 Runtime 뿐.** 다른 대역엔 승격 개념이 없다 |
| `pending` | 문서화됐지만 0건 |

### 판정을 미루는 이유

**Phase 14 Step 1의 규칙에 걸린다 — 「질문이 하나도 연결되지 않는 어휘는 삭제한다」.**
역량 질문 30개 중 「이 문서를 다음 공정이 먹어도 되는가」를 묻는 것이 **없다.**

T4가 든 위험(덜 익은 Learnings가 승격됨)은 실재할 수 있지만 **아직 사고 사례를
확인하지 못했다.** 그리고 그 사고는 온톨로지 문제가 아니라 **스킬 워크플로 문제**다.

### 먼저 잴 것

```
1  덜 익은 Learnings 가 승격된 사례가 실제로 있나
   → verdict: promoted 66건 중, touched 와 reviewed 간격이 며칠인가
2  pending 이 0건인 이유가 「필요 없어서」인가 「몰라서」인가
3  300 밖(200·400·500)에도 소비 계약이 필요한 자리가 있나
```

**1번이 나오면 채택, 안 나오면 스킬 문서에만 남긴다.**

# 기각

## P · feedback poisoning — 현시점 기각

**방지할 대상이 아직 없다.** 편집 로그를 중요도 신호로 쓰지 않는다.
쓰기 시작하면 그때 꺼낸다. 원칙 한 줄만 남긴다.

> 「자주 편집한 문서 = 중요한 문서」를 신호로 쓰면 **오탈자를 여러 번 고친 문서**가
> 올라온다.

**경계가 미묘한 사례가 하나 있었다.** Phase 13 Step 2에서 `_Insights` 6개 문서의
커밋 13~16회를 앵커 안정성의 근거로 썼다. 그건 **편집 횟수가 아니라 「내용이 안
바뀌었다」를 본 것**이라 poisoning이 아니다. 같은 데이터를 다르게 읽으면 함정이
된다는 것만 기억한다.
