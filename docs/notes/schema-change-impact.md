## 재처리 물량 = 클래스 × 범위 × 좁히는 구조

```
클래스     무엇을 다시 뽑아야 하나
범위       몇 개 문서에 걸리나
좁히는 구조  대상을 결정론적으로 집어낼 수 있나        ← 볼트에서 추가한 축
```

세 번째가 볼트 고유다. 커머스에는 상품을 좁혀줄 구조가 없지만, 볼트에는 **경로 ·
파일명 · frontmatter 값** 셋이 있고 그중 하나가 대상을 정확히 집어내면 「전역」이
「14개」로 줄어든다.

### 클래스

| | 뜻 | 재작성 필요 |
|---|---|---|
| **C0** | 제약만 완화 (상한 ↑, 필수 → 선택) | 없음. 위반이 저절로 해소 |
| **C1** | 이름 변경·동의어 | 없음. 치환 |
| **C2** | 값 하나의 정의 조정 | 경계 문서만 |
| **C3** | 값 추가 | 새 값에 해당하는 것만 판정 |
| **C4** | 제약 강화 (선택 → 필수, 상한 ↓) | 위반 전부 채워야 함 |
| **C5** | 값 제거 · 분할 · 병합 | 그 값을 쓰던 것 전부 재판정 |

### 범위

| | 뜻 |
|---|---|
| **S0** | 특정 값을 가진 문서만 |
| **S1** | 한 대역 또는 한 디렉터리 |
| **S2** | 전역 |

### 좁히는 구조

| | 예 | 효과 |
|---|---|---|
| **경로** | `000 Index/Templates/` · `_Template/` | S2 → S0 |
| **파일명** | `*Template*` · `Decision Node *` | S2 → S0 |
| **frontmatter 값** | `type: template` 인 것만 | S2 → S0 |
| **없음** | — | 범위 그대로 |

**좁히는 구조가 있으면 C5도 전역이 아니다.** 이것이 판정표에서 가장 자주 틀리는
자리다 — 클래스만 보고 「전역 재판정」이라 겁먹고 미룬다.

## 실사례 — 2026-08-26 하루에 넷

| 무엇 | 클래스 | 범위 | 좁히는 구조 | 실제 작업 |
|---|---|---|---|---|
| 문서 클래스 13개 개명 (`v:Principle` → `v:PrincipleDocument`) | **C1** | S2 | frontmatter 값 (`type:`) | ttl 13줄 · `rdf.py` 1곳 · 테스트 4개. **의미 사실이 0개라 데이터 마이그레이션이 없었다** |
| `rdfs:domain` 11개 삭제 | **C5** | S2 | 없음 | **추론 결과가 바뀐다.** 오타이핑 27개 해소, 트리플 −66. 문서는 안 고침 |
| `template` 값 제거 | **C5** | S2 → **S0** | **경로 + 파일명** | **14문서.** 전 문서 재판정을 안 했다 |
| `review` 값 추가 | **C3** | S2 → **S0** | **경로 + 본문 절 존재** | **141문서.** 실측이 대상을 정했다 |

### 셋째 줄이 이 표를 만든 이유

`template` 제거는 클래스만 보면 **C5 × S2 = 최악**이다. 「전 문서 재판정 + 과거 값
폐기」. 그런데 실제로는 **14개**였다.

```
type: template 인 문서                      14
그중 경로가 Templates 계열                   14
낳을 문서의 type 을 형제 파일이 이미 말해줌     14
```

**대상이 결정론적으로 좁혀졌고, 각각의 답도 옆 파일이 갖고 있었다.** 추측이 하나도
없었다 — `adr/`의 실제 ADR 17개가 전부 `project-doc`이고, Levit 공고도 `project-doc`.

### 넷째 줄 — C3이 언제 비싸지나

`review` 추가는 C3(값 추가)이라 「새 값에 해당하는 것만 판정」이다. 문제는
**「해당하는 것」을 어떻게 찾느냐**였다.

```
처음 계획   602 Frames 120 + 604 그 외 24 = 244
실측 후     602 Frames 116 + 603 게임 대표 25 = 141

604 YouTube 90개 중 감상 절을 가진 것이 0개였다
603 Game 공략 76개는 남의 공략을 옮긴 것이라 source-note 가 맞았다
```

**계획의 절반이 실측으로 바뀌었다.** C3의 진짜 비용은 값을 더하는 것이 아니라
**대상을 판별하는 규칙을 찾는 것**이다.

## 바꾸기 전에 묻는 것

```
1  클래스는 무엇인가                         C0~C5
2  범위는 어디까지인가                       S0~S2
3  좁히는 구조가 있는가                      경로 · 파일명 · frontmatter 값
4  대상을 판별하는 규칙이 결정론적인가         「감상 절이 있는가」 같은
5  마이그레이션할 데이터가 실제로 있는가        의미 사실 0개면 C1은 공짜다
6  판별력이 올라가는가 내려가는가              아래
```

**5번을 항상 먼저 잰다.** Phase 13이 클래스 13개를 공짜로 개명할 수 있었던 이유가
그것이다 — 재고 나서 정했다.

## 판별력 진단 — 값을 더할지 뺄지 판단할 때

> 출처: 직무과제 2-1 §3 P3-b ([`reverse-import-t4.md`](reverse-import-t4.md) 항목 C).
> *"값이 전부 같은 Key는 정보량 0이라 필터로 못 쓴다."*

**전역 빈도가 아니라 「그 구역 안에서의 분포」를 본다.**

```
2026-08-26 이전   600 안에서 source-note   1,252 / 1,258     ← 아무것도 안 가른다
review 신설 후                source-note 1,119 · review 141
```

`review`를 만든 판단이 사후적으로 **판별력 회복**이었다. 그때는 이 이름을 몰랐다.

### 반대 방향의 함정 — 판별력 0인데 옳은 경우

```
601 Books 안에서 source-note   946 / 1,052
```

**이건 결함이 아니라 601의 정의다.** 601은 「책에서 옮긴 것」을 모으는 자리이므로
그 안이 전부 `source-note`인 것이 맞다.

```
판별력 0 + 그래도 필요하다
   →  속성이 아니라 그 묶음의 정의다
   →  값을 쪼갤 게 아니라, 디렉터리 경계를 볼 문제다
```

**둘을 가르는 질문**: 그 구역 안에서 **다르게 취급하고 싶은 문서가 있는가.**
602 Frames는 있었다(감상 vs 인덱스). 601 Books는 없다.

### 이 진단은 코드로 만들지 않는다

상시 명령이 될 만큼 자주 쓰지 않는다. **스키마를 바꿀지 판단할 때만** 이 표를 펴고
그 구역의 분포를 한 번 센다.
