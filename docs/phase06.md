# Phase 6 — RDF로 다시 모델링한다

> 모듈: `vault/rdf.py` · scope: `rdf` · **2부 시작**

## 큰 그림

Phase 5까지 만든 건 **지식 그래프**다. 온톨로지가 아니다. 스키마 정본이 스스로 그렇게 적어뒀다.

> 속성 그래프(Neo4j) ≠ 온톨로지. 형식 의미론도 추론기도 없다. 온톨로지를 배우려면 RDF 계열이 맞다.

여기서 **같은 vault를 두 번째로 모델링**한다. 데이터는 그대로, 모델만 바꾼다. 그게 이 프로젝트가 한 단계에 변수 하나씩만 바꾸는 이유다 — Phase 5의 SQLite 그래프가 회귀 대조본이 된다.

```
vault/rdf.py     마크다운 → RDF 트리플
                 Turtle 직렬화 (.vault.ttl)
```

**여기서 `rdflib` 의존성이 들어온다.** Phase 1~5의 「표준 라이브러리만」 제약은 파서를 손으로 짜기 위한 것이었고, 그 목적은 달성됐다.

```bash
uv add rdflib
```

## 핵심 개념

### 1. 왜 트리플인가

SQLite에서는 사실의 종류마다 자리가 달랐다.

```
type 은 node 테이블의 컬럼
builds_on 은 edge 테이블의 행
태그는 tag 테이블의 행
```

RDF에는 **자리가 하나뿐**이다. 모든 사실이 `(주어, 술어, 목적어)` 셋이다.

```turtle
<doc/CIDR>  :type       :Concept .
<doc/CIDR>  :summary    "How CIDR works" .
<doc/CIDR>  :builds_on  <doc/Network-layer> .
<doc/CIDR>  :tagged     <tag/Stack-Python> .
```

**대가와 이득이 있다.**

| | SQLite | RDF |
|---|---|---|
| 스키마 변경 | `ALTER TABLE` | 그냥 새 술어를 쓰면 된다 |
| 새 관계 추가 | 컬럼/테이블 설계 | 트리플 하나 |
| 병합 | JOIN 설계 필요 | **집합 합집합.** 그게 전부다 |
| 타입 안전 | 컬럼 타입이 강제 | 없다. 뭐든 어디든 들어간다 |
| 질의 | SQL — 익숙 | SPARQL — 배워야 함 |

세 번째 줄이 RDF의 진짜 강점이다. **다른 출처의 그래프를 합치는 데 설계가 필요 없다.** 웹 규모 데이터 통합을 위해 만들어진 모델이라 그렇다.

### 2. IRI 설계 — 이 Phase의 진짜 어려움

RDF의 모든 주어와 술어는 **IRI**(국제화된 URI)여야 한다. 전역 식별자다.

Phase 3에서 겪은 문제가 여기서 결정을 강요한다. **무엇을 문서의 식별자로 삼을 것인가?**

| 후보 | 장점 | 문제 |
|---|---|---|
| 파일 경로 | 지금 확실히 유일 | 문서를 옮기면 **다른 것이 된다.** vault는 계속 재배치된다 |
| 파일 이름 | 위키링크가 이걸 쓴다 | **동명이인.** `Hub.md`가 여러 개 |
| 새 안정 ID (UUID) | 이동·개명에 안 흔들림 | md에 심어야 함. frontmatter 필드가 하나 늘어난다 — 스키마 정본의 「필드 상한 6」과 충돌 |
| 내용 해시 | 자동 | 문서를 고치면 다른 것이 된다. 최악 |

**정답이 없다. 그래서 이게 학습이다.** 실용적 출발점은 경로 기반이되, 그 선택이 무엇을 깨뜨리는지 문서에 적어두는 것이다.

```
https://tomato.vault/doc/200%20Dev%20Knowledge%20Base/…/CIDR
```

IRI는 **주소가 아니라 이름**이다. 실제로 접속되지 않아도 된다 — 그래서 도메인을 소유하지 않아도 쓸 수 있다. 하지만 **전역 유일해야** 하므로 자기 네임스페이스를 정한다.

> 여기서 `w3id.org`나 `purl.org` 같은 영구 식별자 서비스가 왜 존재하는지 이해하게 된다.

### 3. 네임스페이스 — 800 TRPG 문제가 풀린다

> **2026-08-23 갱신.** `800 TRPG` 는 이제 vault 밖에 있다 → [`800-trpg-split.md`](800-trpg-split.md).
> 문제 설정이 약해진 게 아니라 **강해졌다** — vault 안의 이질적 폴더가 아니라
> **출처·어휘·관리 주체가 다른 독립 코퍼스**가 됐다. RDF 가 원래 풀려던 문제가 이것이다.

Phase 5에서 800 TRPG를 통째로 제외했다. `type:`을 게임 아이템 분류로 써서 축이 깨지기 때문이었다.

RDF에서는 그럴 필요가 없다.

```turtle
@prefix v:    <https://tomato.vault/schema/> .
@prefix trpg: <https://tomato.vault/trpg/> .

<doc/CIDR>       v:type    v:Concept .
<doc/현자의돌>    trpg:type trpg:완제품 .
```

**같은 이름, 다른 네임스페이스, 충돌 없음.** 이게 RDF가 "어휘 충돌"을 푸는 방식이고, SQLite 컬럼에서는 불가능했던 것이다. Phase 5에서 통째로 버린 2,238개 문서를 여기서 되찾을 수 있다.

**그 2,238개는 이제 다른 디렉토리, 다른 git repo에 있다.** 그래서 이 절은 폴더 하나를 다시 넣는 이야기가 아니라 **두 그래프를 합치는 이야기**가 된다. `scan_vault` 가 루트를 인자로 받으므로 실습 자체는 그대로 된다 — 두 번 훑어 트리플을 만들고, 네임스페이스로 갈라 한 그래프에 넣는다.

> 되찾을지는 판단이다. 지금 당장 필요한 질의가 없으면 안 넣는다 — 스키마 정본의 원칙.
>
> 후보는 이미 있다. 분리 전 실측에서 **`800 TRPG` 와 `600 .../도해 연금술/` 이 양방향 113+1회로 묶여 있었다.** 원전과 게임 정합을 한 질의로 훑을 수 있느냐가 「합쳐야 답이 나오는 질의」인지의 시험대다.

### 4. 리터럴 vs 리소스

이 구분이 RDF 모델링의 첫 갈림길이다.

```turtle
<doc/CIDR> v:summary  "서브넷 마스크로 호스트 수를 세는 법" .   ← 리터럴. 끝. 더 말할 게 없다
<doc/CIDR> v:builds_on <doc/Network-layer> .                 ← 리소스. 이것에 대해 또 말할 수 있다
```

**"이것에 대해 나중에 더 말할 일이 있는가?"** 있으면 리소스, 없으면 리터럴.

태그가 애매하다. `"Stack/Python"` 문자열로 둘 수도, `<tag/Stack-Python>` 리소스로 둘 수도 있다. 리소스로 하면 **태그끼리 관계를 맺을 수 있다** — `Stack/Python`이 `Stack`의 하위라는 사실을. Phase 8의 SKOS `skos:broader`가 정확히 그 자리다.

**지금 결정하고 근거를 남긴다.**

### 5. 리터럴의 타입과 언어

```turtle
<doc/CIDR> v:created "2026-08-10"^^xsd:date .          ← 날짜다. 문자열이 아니다
<doc/CIDR> v:summary "서브넷 마스크로…"@ko .            ← 한국어다
```

Phase 4에서 `date.fromisoformat`으로 검사했던 것을 여기서는 **데이터 자체가 선언한다.** 검증기가 아니라 모델이 아는 것 — 2부 내내 반복될 주제다.
