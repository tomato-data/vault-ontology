# 로드맵 — vault-cli 재구현에서 의미 지식 운영까지

> **Phase 1~9는 2026-08-25에 완료됐다.** 그 결론을 보존한 채, 같은 저장소에서
> 문서 온톨로지를 지식·판단 온톨로지로 확장하는 **3부 Phase 10~19를 새로 시작한다.**
> 2부의 최종 판단은 [`../learnings/verdict.md`](../learnings/verdict.md), 현재 재개
> 지점은 [`NEXT.md`](NEXT.md)에 있다.

## 이 프로젝트가 답하려는 질문

Obsidian vault의 문서 4,204개는 위키링크 11,624개로 이미 연결돼 있다. 사람 눈에는 그래프지만 기계가 읽을 수 있는 구조는 없다. `vault-cli`가 이를 SQLite로 추출해 주지만, **동작 원리를 직접 이해하고 검증하기 위해 처음부터 다시 구현했다.**

그래서 두 가지를 동시에 한다.

1. **손으로 다시 짠다** — 파서·검증·그래프 빌더를 백지에서 구현한다. 기존 `vault.py`는 회귀 대조본이다
2. **온톨로지를 제대로 배운다** — 같은 vault를 RDF로 다시 모델링하고, SPARQL로 질의하고, 추론기를 돌린다

두 번째가 이 저장소의 존재 이유다. 스키마 설계 문서에 이미 적어둔 문장 때문이다.

> **속성 그래프(Neo4j) ≠ 온톨로지.** 형식 의미론도 추론기도 없다. 온톨로지를 배우려면 RDF 계열이 맞다.

즉 지금 `vault.py`의 `build`/`q`는 **지식 그래프이지 온톨로지가 아니다.** Phase 1~5로 그걸 재현하고, Phase 6~9에서 진짜 온톨로지로 넘어간다. 같은 데이터로 두 번 모델링해봐야 그 차이가 말이 아니라 경험으로 남는다.

## 큰 그림

```
                  ┌──────────── 마크다운 4,204개 (원본) ────────────┐
                  │                                                │
   Phase 1~3      │  파싱                                          │
   ─────────      │    frontmatter · 위키링크 · 파일 인덱스          │
                  │         ↓                                      │
   Phase 4        │  검증          "만든 것은 반드시 검사를 통과한다"  │
   ─────────      │         ↓                                      │
                  │    ┌────┴─────┐                                │
   Phase 5        │ SQLite 그래프  │  ← 여기까지가 vault.py 재현      │
   ─────────      │ node/edge/tag │     (속성 그래프)                │
                  │               │                                │
   Phase 6~9      │         RDF 트리플  ← 온톨로지 본론              │
   ─────────      │         SPARQL · RDFS/OWL/SKOS · 추론           │
                  │                     ↓                          │
   Phase 10~19    │  문서와 지식 개체 분리 · 의미 사실 · SHACL       │
   ───────────    │  목적 제한 추론 · 설명 · 제안/승인 · 제한 운영     │
                  └────────────────────────────────────────────────┘
```

**한 단계에 변수 하나씩만 바꾼다.** Phase 5까지의 산출물이 Phase 6~9의 대조본이 된다. 같은 질문("A를 이해하려면 뭘 먼저 읽어야 하나")을 재귀 CTE로 한 번, SPARQL property path로 한 번 푼다. 답은 같아야 하고, 표현력은 달라야 한다.

3부는 2부를 부정하지 않는다. 2부가 만든 것은 **문서·폴더·태그의 형식 온톨로지**다.
3부는 문서를 지식 그 자체와 분리하여, 문서 안의 주장·사건·결정·원칙·절차와 그
근거를 모델링한다. 대상은 개발 지식에 한정하지 않는다. 개인 경험·성찰·가치관·철학·
커리어·생활 지식을 포함한 **Vault 전체**를 적용 범위로 두고, 서로 다른 영역이 실제로
영향을 주는 접점을 찾는다. VectorDB는 별도 작업 축이며 3부에서는 연동 계약만 정의한다.

### Vault 전체라는 말의 의미

- 모든 대역이 의미 모델에 참여할 수 있다.
- 모든 문서에 의미 개체를 억지로 만들지는 않는다.
- 개발 지식과 개인 철학을 같은 진리 조건으로 평평하게 만들지 않는다.
- 개인적 생각은 관점·시점·경험·주체를 함께 보존한다.
- 공통 kernel 위에 필요한 영역별 vocabulary/profile을 얹는다.
- 개발 원칙과 삶의 원칙, 개인 경험과 기술 결정처럼 **영역 사이의 연결**을 주요
  역량 질문으로 다룬다.
- 전체 자동 변환이 아니라 영역별 표본에서 시작해 가치가 확인된 범위로 확장한다.
- 현재 그래프에서 제외된 900 Archive도 과거 생각과 판단의 계보를 위해 적용 범위에
  넣되, 현재 유효한 지식과 섞지 않는 read-only/archive 경계를 먼저 설계한다.

## 3부가 이전보다 어려운 이유

| Phase 1~9 | Phase 10~19 |
|---|---|
| 파일·문자열·링크가 입력 | 주장·근거·결정 같은 의미가 입력 |
| 대부분 결정론적 정답 | 경계가 애매하고 사람의 판정이 필요 |
| 파일 경로가 노드 ID | 편집·이동·분할을 견디는 의미 ID 필요 |
| 파생 DB를 지우고 재빌드 | 승인·거절·철회 이력과 provenance 보존 |
| 단조 추론 | 상태 변화에 따라 결과를 거두는 운영 규칙 |
| 테스트 fixture가 정답 | 사람이 만든 gold set 자체도 검증 대상 |
| 틀리면 질의 결과가 틀림 | 틀린 사실이 후속 추론과 작업 제안을 연쇄 오염 |
| 개발 지식의 비교적 명시적 주장 | 개인 경험·믿음·가치·철학의 관점과 시간성 |

가장 큰 위험은 기술 선택이 아니다. **의미 사실이 Vault에 들어오는 경로가 아직 없다.**
`supports`나 `contradicts`를 자동으로 확정할 수 없으므로 Phase 13에서 작성 계약과
사람 기준 데이터를 먼저 만든다. 이 비용이 감당되지 않으면 전체 Vault 확대를 중단한다.

### 구현 전에 해결할 선행 결정

1. 현재 `v:Principle`(원칙 유형 문서)과 실제 원칙 개체의 이름·네임스페이스를 분리한다.
2. 문서 안 주장·사건·원칙의 최소 단위와 안정 ID를 정한다.
3. 의미 annotation을 Markdown, block ID, sidecar 중 어디에 둘지 실험한다.
4. asserted·proposed·inferred graph의 저장 경계와 provenance를 정한다.
5. OWL 추론, SHACL 검증, 철회 가능한 운영 규칙의 책임을 분리한다.
6. 기존 Phase 1~9 API·IRI·테스트의 호환 정책을 정한다.
7. 자동 제안보다 사람의 검토 비용을 먼저 측정한다.
8. `Claim`·`Belief`·`Value`·`Interpretation`의 경계를 전 영역 사례로 검증한다.
9. 민감한 개인 문서가 외부 모델·로그로 나가지 않도록 extraction 정책을 정한다.

### 전체 중단 규칙

- 역량 질문이 없는 클래스·관계는 추가하지 않는다.
- Vector 유사도는 온톨로지 사실로 승격하지 않는다.
- 승인되지 않은 제안은 확정 질의와 Markdown에 영향을 주지 않는다.
- 추론 결과를 Markdown에 자동으로 쓰지 않는다.
- 측정된 병목 없이 RDF 저장 엔진을 교체하지 않는다.
- gold set에서 통과하지 않은 기능을 전체 Vault에 적용하지 않는다.
- annotation·검토 비용이 얻는 가치보다 크면 의미 단위를 줄이거나 중단한다.
- shadow mode에서 가치가 확인되지 않으면 쓰기 자동화로 넘어가지 않는다.
- 교차 영역 edge 수를 목표로 삼지 않는다. 원문 근거가 있는 연결만 승인한다.
- 개인적 믿음과 해석을 객관적 사실 관계로 자동 승격하지 않는다.

## 진행 방식

**TDD — RED → GREEN → REFACTOR.** 테스트를 먼저 쓰고, 실패를 보고, 최소로 통과시키고, 정리한다.

파서는 TDD가 특히 잘 맞는다. 함정이 전부 "이 입력에 대해 이 출력"의 형태이기 때문이다. `vault-cli` README의 **"이 자리에서 네 번 잘못 셌다"** 표가 그대로 테스트 케이스 목록이다.

| 함정 | 증상 | Phase |
|---|---|---|
| 표 안의 `\|` | `[[문서\|별칭]]` 타깃 끝에 역슬래시가 남는다 | 2 |
| `splitext` | `No.013 현자의 돌` → `No` + `.013 현자의 돌` | 3 |
| 유니코드 정규화 | macOS는 파일명을 NFD로 저장한다. 본문 링크는 NFC | 3 |
| 대소문자 | macOS는 `python`과 `Python`을 구분하지 않는다 | 3 |
| `\s*(.+)$` | `\s`가 개행을 먹어 빈 `summary:`가 다음 줄을 읽는다 | ✅ 1 |
| `2026-13-99` | 형태는 맞는데 없는 날짜다 | 4 |

각 Phase는 다음 순서로 진행했다.

```
RED       테스트를 쓴다 → 실패 메시지를 함께 읽는다
GREEN     최소 구현 → 통과 → 커밋
REFACTOR  개선점 검토 (없으면 "없다"고 판단하는 것도 결과) → 있으면 별도 커밋
실측       실제 vault에 돌려 답안지 출력과 대조
```

마지막 줄이 중요하다. **단위 테스트가 전부 초록이어도 실제 데이터에서 숫자가 다르면 틀린 것이다.**

## 성공 기준

"코드가 돌아간다"는 성공 기준이 아니다. 도구를 하나 더 만드는 것으로 끝날 위험이 실재하고, 원본 프로젝트 문서도 그 위험을 스스로 적어뒀다 — **지식 정리 자체가 목적이 되어 실제 행동을 미루는 기계가 되는 것**. 그 위험을 알고 시작했다.

- [x] Phase 5 — 실측값 표를 **손으로 짠 코드로** 재현했다
- [x] Phase 8 — `type`의 13가지 값에는 의미별 계층보다 **Content·Imported·Structural이라는 3역할 계층**이 유용하다고 결론냈다
- [x] Phase 9 — 추론이 만든 사실을 측정했다. **SQLite로 얻을 수 없던 유용한 사실은 0건**이었다
- [x] 최종 — **재귀 CTE로 충분하다.** rdflib 상시 운용은 하지 않고, Oxigraph는 학습 목적이 생길 때까지 보류한다

3부의 성공 기준은 별개다.

- [ ] 기존 SQLite로 답할 수 없던 역량 질문을 정확히 답한다.
- [ ] 모든 의미 사실과 파생 결과가 원문 근거로 돌아간다.
- [ ] 문서 이동·분할 뒤에도 지식 개체의 정체성이 유지된다.
- [ ] SHACL 검증과 추론, 운영 규칙이 서로의 역할을 침범하지 않는다.
- [ ] 제안은 승인 전까지 확정 사실과 분리되며 철회 가능하다.
- [ ] 실제 사용에서 annotation·검토 비용보다 큰 순효용이 확인된다.
- [ ] 쓰기 기능은 shadow mode·preview·승인·감사·rollback을 모두 통과한다.
- [ ] 000~700·900 대역의 대표 표본과 교차 영역 질문에서 모델이 유효하다.
- [ ] 개발 지식·개인 경험·철학의 서로 다른 인식적 지위와 시간 맥락이 보존된다.

마지막 항목이 진짜 산출물이다. 자세한 근거와 최종 결정은 [`learnings/verdict.md`](../learnings/verdict.md)에 정리했다.
