# 로드맵 — vault-cli 재구현과 온톨로지 학습

## 이 프로젝트가 답하려는 질문

vault 문서 6,289개는 위키링크 24,969개로 이미 연결돼 있다. 사람 눈에는 그래프인데 기계가 읽을 구조가 없다. `vault-cli`가 그걸 SQLite로 뽑아냈다 — **동작한다. 하지만 Claude가 짰다.**

그래서 두 가지를 동시에 한다.

1. **손으로 다시 짠다** — 파서·검증·그래프 빌더를 백지에서. 기존 `vault.py`가 회귀 대조본이다
2. **온톨로지를 제대로 배운다** — 같은 vault를 RDF로 다시 모델링하고, SPARQL로 질의하고, 추론기를 돌린다

두 번째가 이 저장소의 존재 이유다. 스키마 정본에 이미 적혀 있는 문장 때문이다.

> **속성 그래프(Neo4j) ≠ 온톨로지.** 형식 의미론도 추론기도 없다. 온톨로지를 배우려면 RDF 계열이 맞다.

즉 지금 `vault.py`의 `build`/`q`는 **지식 그래프이지 온톨로지가 아니다.** Phase 1~5로 그걸 재현하고, Phase 6~9에서 진짜 온톨로지로 넘어간다. 같은 데이터로 두 번 모델링해봐야 그 차이가 말이 아니라 손에 남는다.

## 큰 그림

```
                  ┌──────────── 마크다운 6,289개 (원본) ────────────┐
                  │                                                │
   Phase 1~3      │  파싱                                          │
   ─────────      │    frontmatter · 위키링크 · 파일 인덱스          │
                  │         ↓                                      │
   Phase 4        │  검증          "만든 것은 반드시 검사를 통과한다"  │
   ─────────      │         ↓                                      │
                  │    ┌────┴─────┐                                │
   Phase 5        │ SQLite 그래프  │  ← 여기까지가 vault.py 재현      │
   ─────────      │ node/edge/tag │     (속성 그래프)                │
                  │               │                                │
   Phase 6~9      │         RDF 트리플  ← 온톨로지 본론              │
   ─────────      │         SPARQL · RDFS/OWL · 추론                │
                  └────────────────────────────────────────────────┘
```

**한 단계에 변수 하나씩만 바꾼다.** Phase 5까지의 산출물이 Phase 6~9의 대조본이 된다. 같은 질문("A를 이해하려면 뭘 먼저 읽나")을 재귀 CTE로 한 번, SPARQL property path로 한 번 푼다. 답이 같아야 하고, 코드 길이와 표현력이 달라야 한다.

## Phase 목록

### 1부 — v0 재현 (답안지 있음)

| Phase | 만드는 것 | 배우는 것 | 답안지 |
|---|---|---|---|
| **1** | frontmatter 파서 | 텍스트를 구조로 — 정규식의 한계선 | `split_frontmatter` `fm_list` |
| **2** | 위키링크 파서 | 파싱 함정과 그것이 만드는 통계 오류 | `LINK` `strip_code` `link_target` |
| **3** | vault 스캔 · 링크 해석 | 이름 해석은 왜 어려운가 (NFC · 대소문자 · 동명이인) | `scan_vault` `resolve_link` |
| **4** | 검증 = 거부 | 제약을 검사 가능한 형태로 적기 | `validate_frontmatter` `cmd_lint` |
| **5** | SQLite 그래프 | 노드·엣지 모델링, 재귀 CTE 이행 폐쇄 | `cmd_build` `cmd_q` |

### 2부 — 온톨로지 (답안지 없음)

| Phase | 만드는 것 | 배우는 것 |
|---|---|---|
| **6** | RDF 트리플로 재모델링 | IRI 설계 · 리터럴 vs 리소스 · Turtle · rdflib |
| **7** | SPARQL 질의 | 기본 패턴 · property path `:builds_on+` · CTE와의 비교 |
| **8** | 어휘 설계 (RDFS/OWL/SKOS) | **스키마를 데이터로 적는다** · 클래스 계층 · domain/range · inverseOf |
| **9** | 추론 (owlrl) | 추론이 실제로 만들어내는 것 · 폭발 측정 · v2로 갈지 판단 |

## 진행 방식

**TDD — RED → GREEN → REFACTOR.** 테스트를 먼저 쓰고, 실패를 보고, 최소로 통과시키고, 정리한다.

파서는 TDD가 특히 잘 맞는다. 함정이 전부 "이 입력에 대해 이 출력"의 형태이기 때문이다. `vault.py` README에 적힌 **"이 자리에서 네 번 잘못 셌다"** 표가 그대로 테스트 케이스 목록이다.

| 함정 | 증상 |
|---|---|
| 표 안의 `\|` | `[[문서\|별칭]]` 타깃 끝에 역슬래시가 남는다 |
| `splitext` | `No.013 현자의 돌` → `No` + `.013 현자의 돌` |
| 대소문자 | macOS는 `python`과 `Python`을 구분하지 않는다 |
| `\s*(.+)$` | `\s`가 개행을 먹어 빈 `summary:`가 다음 줄을 읽는다 |
| `2026-13-99` | 형태는 맞는데 없는 날짜다 |

각 Phase는 이렇게 돈다.

```
RED       테스트를 쓴다 → 실패 메시지를 함께 읽는다
GREEN     최소 구현 → 통과
REFACTOR  개선점 검토 (없으면 "없다"고 판단하는 것도 결과)
실측       실제 vault 6,289개에 돌려 기존 vault.py 출력과 대조
```

마지막 줄이 중요하다. 단위 테스트가 전부 초록이어도 실제 데이터에서 숫자가 다르면 뭔가 틀린 것이다.

## 성공 기준

원본 프로젝트 문서(`Vault 온톨로지 — 지식베이스 그래프화`)가 스스로 못박은 위험이 있다.

> vault가 통찰을 소비함으로써 **행동을 유예하는 기계**로 일부 전락.

같은 함정을 여기서도 피한다. 그래서 이 프로젝트의 성공 기준은 "코드가 돌아간다"가 아니다.

- [ ] Phase 5 끝 — 실측값 표를 **손으로 짠 코드로** 재현했는가
- [ ] Phase 8 끝 — vault의 `type` 13값에 **실제로 계층이 있는지** 답을 냈는가 (없다면 없다고 결론내는 것도 답)
- [ ] Phase 9 끝 — 추론이 **SQLite로는 못 얻던 사실을 하나라도** 만들어냈는가
- [ ] 최종 — 스키마 정본의 미결 판단에 답한다: **"재귀 CTE로 부족한가?"** → v1/v2로 갈지 결정

마지막 항목이 진짜 산출물이다. 정본에는 "2주 써보고 정한다. 지금은 아니다"로 열려 있다.
