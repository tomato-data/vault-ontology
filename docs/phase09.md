# Phase 9 — 추론, 그리고 판단

> 모듈: `vault/inference.py` · scope: `inference` · **마지막**

## 큰 그림

Phase 8이 어휘를 선언했다. 이제 **추론기를 돌린다.** 선언한 것들이 실제로 무슨 트리플을 만들어내는지 보고, 그것이 SQLite로는 못 얻던 것인지 판정한다.

```bash
uv add owlrl
```

그리고 이 프로젝트가 처음부터 열어둔 미결 질문에 답한다.

> **판단 기준은 하나다** — 재귀 CTE로 부족해서 SPARQL property path나 추론이 필요해지는가. 2주 써보고 정한다. 지금은 아니다. — 스키마 정본 v1.6

## 핵심 개념

### 1. 추론기가 하는 일

추론기는 **선언된 규칙으로 새 트리플을 만들어 그래프에 넣는다** (물질화, materialization).

```turtle
# 원래 있던 것
<A> v:builds_on <B> .
<B> v:builds_on <C> .
v:builds_on a owl:TransitiveProperty .

# 추론기가 추가한 것
<A> v:builds_on <C> .        ← 아무도 안 적었는데 참이다
```

`rdfs:subClassOf`도 같다.

```turtle
v:Concept rdfs:subClassOf v:Document .
<doc/CIDR> a v:Concept .
→  <doc/CIDR> a v:Document .     ← 추론
```

**한 번 물질화하면 그 뒤 질의는 평범한 패턴 매칭이다.** property path `+`조차 필요 없어진다. 계산 시점이 질의에서 빌드로 옮겨간 것이다.

### 2. 열린 세계 가정 (OWA) — 가장 큰 개념 차이

**Phase 4의 lint와 OWL은 세계관이 정반대다.** 이걸 모르면 OWL이 "고장난 것처럼" 보인다.

| | 가정 | `summary`가 없으면 |
|---|---|---|
| **lint (Phase 4)** | **닫힌 세계 (CWA)** — 적히지 않은 것은 거짓 | **위반이다** |
| **OWL (Phase 8~9)** | **열린 세계 (OWA)** — 적히지 않은 것은 **모를 뿐** | 위반이 아니다. 아직 모를 뿐 |

그래서 **OWL로는 "summary가 없으면 거부"를 표현할 수 없다.** 카디널리티 제약(`owl:minCardinality 1`)을 걸어도 위반을 신고하는 게 아니라, "그럼 summary가 하나 있는 거네"라고 **추론해버린다** (익명 노드를 만들어서).

이건 결함이 아니라 설계다. OWL은 **웹**을 위해 만들어졌다 — 웹에서는 내가 못 본 데이터가 어딘가에 있는 게 정상이다.

**실무적 결론: 검증에는 SHACL을 쓴다.** OWL은 추론용, SHACL은 검증용이다. Phase 4의 lint가 사실 SHACL이 하는 일이었다는 걸 여기서 알게 된다.

> SHACL 구현까지는 이 로드맵의 범위 밖이다. **차이를 이해하는 것**이 목표다.

### 3. 고유 이름 가정이 없다 (No UNA)

OWL은 **다른 IRI가 다른 것을 가리킨다고 가정하지 않는다.** `<doc/A>`와 `<doc/B>`가 같은 문서일 수도 있다 — 누가 `owl:sameAs`로 이었다면.

Phase 3의 동명이인 문제(`Hub.md`가 여러 개)가 여기서 다시 온다. 반대 방향으로. SQLite에서는 "이름이 같으면 못 고른다"가 문제였는데, OWL에서는 "IRI가 달라도 같은 것일 수 있다"가 기본값이다.

### 4. 추론의 대가 — 폭발을 잰다

이게 이 Phase의 핵심 실측이다.

```
추론 전 트리플     ?
추론 후 트리플     ?
증가 배수          ?
추론 시간          ?
```

`builds_on` 387개 · 최대 깊이 7이면 이행 폐쇄가 만드는 트리플은 예측하기 어렵다. **재본다.**

`links_to` 10,702개에 `inverseOf`를 걸면 최소 2배다. 여기에 `subClassOf` 계층까지 곱해지면 어디까지 가나.

**폭발이 크면 그 자체가 답이다** — "추론은 개념 학습용이고 실전에는 질의 시점 계산이 낫다"는 결론도 정당한 결론이다.

### 5. 추론이 실제로 만들어낸 것 — 성공 기준

숫자만 재고 끝내면 안 된다. **질적으로 새로운 사실이 나왔는가**를 본다.

체크리스트.

- [x] `subClassOf` 추론으로 **상위 타입 질의**가 가능해졌는가 (`?d a v:Document`로 전부 잡히나)
- [x] `inverseOf`로 역링크가 **데이터가 됐는가** (질의 기교가 아니라)
- [x] `domain`/`range` 추론이 **이상한 것을 만들어냈는가** — 이게 중요하다. 잘못된 데이터가 잘못된 타입 추론으로 번지는 걸 실물로 본다
- [x] **SQLite로는 얻을 수 없던 사실이 하나라도 있는가**

마지막 항목이 이 프로젝트 전체의 성공 기준이다. **0건이면 0건이라고 적는다.** 그것도 결론이고, 정직하게 적어야 v1/v2 판단이 흐려지지 않는다.
