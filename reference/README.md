| 파일 | 내용 |

| `vault-cli-README.md` | 그 도구의 설계 문서. **밟은 함정과 그 이유가 적혀 있다** |

## 쓰는 법

**막히기 전에는 열지 않는다.**

TDD 사이클을 도는 동안은 테스트가 명세다. 답안지를 먼저 보면 "왜 이렇게 짜야 하는가"를 건너뛰고 "어떻게 짰는가"만 남는다. 이 프로젝트가 존재하는 이유가 사라진다.

여는 시점은 셋이다.

| 시점 | 이유 |
|---|---|
| 30분 이상 막혔을 때 | 학습이 아니라 소모다 |
| **Phase 5 대조** | 같은 vault에 둘 다 돌려 숫자가 일치하는지 본다. **필수 단계** |
| Phase가 끝난 뒤 | 내 구현과 비교. 다르면 왜 다른지 |

Phase 5 대조는 이렇게 한다.

```bash
python3 reference/vault.py build      # 답안지 — 오늘 기준
uv run python -m vault build           # 내 코드
```

노드·엣지·태그·kind별 개수가 **전부 일치**해야 한다. 하나라도 다르면 파서가 다른 것이고, 어느 Phase에서 갈렸는지 역추적한다.

> 답안지의 README에 적힌 실측(`노드 3,919 · 엣지 12,266`)은 **2026-08-11 기준**이다. vault는 계속 자라므로(5일 만에 +163개) 그 숫자와 직접 비교하지 않는다. **같은 날 둘 다 돌린 결과끼리** 비교한다.

## 답하지 못하는 것

**답안지는 Phase 1~5까지만 유효하다.**

```
Phase 1~5   파서 → 검증 → SQLite 그래프      ← 여기까지가 vault.py의 범위
Phase 6~9   RDF → SPARQL → RDFS/OWL → 추론   ← 답안지 없음
```

2부는 이 저장소가 처음 가는 길이다. 대조할 것은 답안지가 아니라 **Phase 5에서 내가 만든 SQLite 그래프**다. 같은 질문에 같은 답이 나오는지로 검증한다.

## 이 파일들은 갱신하지 않는다

vault-cli가 나중에 더 발전하더라도 여기는 그대로 둔다. **고정된 기준선이라야 대조본 구실을 한다.** 갱신이 필요하면 새 디렉토리를 만들고 출처를 다시 적는다.
